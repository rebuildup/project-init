# ADR-0013: Worktrunk as the Default WSL/Linux Worktree Operations Layer

- Status: Accepted
- Date: 2026-09-13
- Extends: ADR-0003, ADR-0004, ADR-0008
- Superseded by: None

## Context

project-init already requires one isolated mutable runtime per implementation worker and explicitly rejects a Git worktree by itself as an execution-isolation boundary.

At the same time, local WSL/Linux development still needs a consistent way to create, enter, inspect, review, and remove multiple worktrees without hand-maintaining paths and shell commands. Parallel worktrees also introduce shared-host operational friction: dev servers can contend for the same host port, long-running processes can survive after a worktree is removed, and reviewers need a low-friction way to materialize a PR without disturbing another task.

Worktrunk is a Git worktree manager that addresses those workspace-lifecycle concerns while remaining built on normal Git branches and worktrees. It also provides deterministic branch-derived ports through `hash_port` and process lifecycle binding through `wt step tether`.

## Decision

### 1. Use Worktrunk as the preferred worktree frontend on WSL/Linux

For local WSL2/Linux and Linux developer environments, project initialization SHOULD configure Worktrunk as the preferred interface for routine worktree operations when the repository uses concurrent ticket/review worktrees.

The standard operations are:

- `wt switch` for entering an existing branch worktree
- `wt switch --create <branch>` for creating a worktree for a new branch
- `wt list` / `wt list --full` for worktree and branch-state inspection
- `wt switch pr:<number>` for isolated PR review checkout where supported
- `wt remove` for worktree cleanup after the branch is no longer needed

Native `git worktree` remains a valid fallback when Worktrunk is unavailable.

### 2. Worktrunk does not change branch or GitHub delivery semantics

Worktrunk is a workspace-operations adapter, not a replacement for project-init's Git/GitHub delivery model.

Existing invariants remain canonical:

- release branch: `release-<major>-<minor>-<patch>`
- ticket branch: issue number only
- GitHub Issue dependency graph is the durable dependency SoT
- ticket PRs target the release branch or their immediate stacked predecessor
- active durable ticket branches require canonical remote publication and a Draft PR
- protected `main` changes only through the authorized release-PR path
- PR merge remains a separately authorized side effect

Commands such as `wt merge main` MUST NOT be used to bypass the repository's PR/release integration policy.

### 3. Keep shared Worktrunk behavior project-local

When Worktrunk is selected for a repository, initialization SHOULD create and commit `.config/wt.toml` for repository-specific hooks, aliases, and list metadata.

Machine-level installation and shell integration remain user/toolchain prerequisites, for example:

```bash
cargo install worktrunk
wt config shell install
```

A repository that manages its developer toolchain through Nix or another reproducible environment MAY provide Worktrunk there instead. The policy does not require one global installation mechanism.

### 4. Compile the dev-server hook from the actual project stack

If multiple worktrees can run services on the same WSL/Linux host network, initialization SHOULD give each host-exposed dev server a deterministic branch-derived port using Worktrunk's `hash_port` filter.

The canonical shape is:

```toml
# .config/wt.toml
[post-start]
server = "wt step tether -- <project-specific-dev-command using {{ branch | hash_port }}>"

[list]
url = "http://localhost:{{ branch | hash_port }}"
```

The initializer MUST derive the actual command and port override from the detected framework/runtime instead of blindly copying an npm/Vite-specific command.

If the application reads an environment variable rather than a CLI flag, the hook may set that variable. If the service is inside a container or another isolated runtime, `hash_port` applies to the host-published port only; identical internal ports remain valid.

`hash_port` is a deterministic allocation mechanism, not a proof that no two branches or unrelated host processes can ever choose the same port. Startup/runtime logic MUST surface bind conflicts instead of treating the template as a uniqueness guarantee; a project that needs strict reservation must add an explicit reservation/collision-resolution mechanism.

### 5. Bind long-running local processes to the worktree lifecycle

For shared-host development processes started from Worktrunk hooks, use `wt step tether -- <command>` where appropriate so the process group is stopped when the worktree is removed.

This reduces orphaned dev servers and stale host-port ownership, but it is process lifecycle management rather than a security boundary.

### 6. Preserve runtime isolation requirements

A Worktrunk worktree plus a unique `hash_port` is not sufficient implementation-worker isolation.

The existing sandbox/runtime policy remains responsible for:

- process/security boundary
- writable mutable state
- network policy
- DB / Redis / queue isolation
- application local state
- mutable build/test artifacts
- credential boundaries

When a database or similar host-shared service is intentionally used by multiple worktrees, the project-specific runtime adapter MUST allocate a unique database/schema/container/socket/host port as appropriate. Worktrunk template values such as `sanitize_db` and `hash_port` MAY be used as deterministic identifiers, but the repository must validate the actual service semantics.

### 7. Prefer Linux-filesystem worktrees under WSL

For Windows-hosted development using WSL2, Worktrunk worktrees SHOULD live in the WSL Linux filesystem rather than `/mnt/c` or another Windows-mounted path for high-frequency build/watch workloads.

Native Windows Worktrunk support is not made a first-class project-init requirement by this decision. It can be added later without changing the WSL/Linux workflow.

### 8. Worktree lifecycle is recoverable from Git state

Worktrunk convenience state must not become a new canonical SoT.

A fresh agent or developer must still be able to recover the task from Git refs, GitHub Issue/PR state, committed project configuration, and recorded immutable snapshots. Worktrunk configuration and worktree paths are operational aids around those durable sources.

## Consequences

### Positive

- concurrent ticket and review worktrees become easier to create and navigate
- branch identity remains the primary handle instead of manually managed directory paths
- host dev-server port collisions can normally be avoided with deterministic allocation and explicit bind-conflict detection
- long-running local processes can follow worktree lifecycle
- PR review can occur without replacing the current worktree
- WSL/Linux receives one consistent worktree workflow while preserving existing GitHub delivery rules

### Negative / Trade-offs

- developers need the Worktrunk executable and shell integration for the full UX
- `.config/wt.toml` must be generated from the actual project stack rather than copied as a universal template
- `hash_port` solves host-port allocation, not database/state/security isolation
- another tool is added to the local developer workflow and must be re-evaluated as its interface evolves

## Re-evaluation triggers

Re-evaluate this decision when:

- Worktrunk changes its configuration, hook, port-template, or process-lifecycle semantics materially
- a broadly adopted Git-native worktree UX supersedes the need for Worktrunk
- Windows-native development becomes a first-class project-init target for the same workflow
- the project moves to a runtime model where host worktrees no longer launch local services
- the isolation model in ADR-0003 changes
