# ADR-0013: Replace the Pi Worker slot with Oh My Pi (OMP)

- Status: Accepted
- Date: 2026-11-04
- Related: issue #80, ADR-0012 (supersedes its Pi-route portion), ADR-0008

## Context

The unified launcher in `script/agent.ts` exposes explicit harness × provider
routes from `config/agents.toml`. The Worker slot was Pi: `pi.opencode-go`,
`pi.openrouter`, `pi.openrouter-free`, `pi.deepseek` and `pi.minimax`, with
Pi 1.4.0 from `@earendil-works/pi-coding-agent`. Claude Code remains the
Supervisor in the `claude.*` routes and is not part of this change.

OMP (Oh My Pi) provides the same Worker role through a different native CLI.
It is installed by pc-setup as **OMP 18.16.0** from the `mise` tool
`oh-my-pi` (`github:can1357/oh-my-pi`, bins `["omp"]`) in pc-setup PR #158.
That PR leaves the native Pi binary installed for rollback and native use.

OMP's defaults are not a drop-in equivalent of the Pi slot:

- `tools.approvalMode` defaults to **`yolo`**, and OMP's built-in bash
  critical-pattern override is ignored in that mode.
- Extensions are discovered ambiently, so loading one trusted extension would
  otherwise change which other extensions run.
- Its credential ladder places local stores and config ahead of environment
  variables, while the launcher's guarantee is that the Infisical-backed
  `opencode-go` route uses the injected credential.
- Local `models.yml`/`models.yaml`/`models.json`, auth brokers, profiles and
  implicit-switch settings can redirect a session.

The migration therefore has to preserve the Worker slot's previous
guarantees — explicit provider/model, fail-closed model validation,
process-scoped Infisical credentials, and a narrow tool/permission boundary —
against OMP's defaults.

## Decision

1. **OMP replaces the Pi Worker slot; it is not a fifth harness.** The
   configured harnesses are `claude`, `opencode`, `omp` and `dsh`. The
   `omp.*` routes take over the Worker role formerly held by `pi.*`.
   **The Claude Code Supervisor is unchanged**: no `claude.*` route, adapter
   behavior or credential flow is redefined here.
2. **One canonical config source.** `config/agents.toml` remains the only
   source of truth for harnesses, providers, endpoints, credential names,
   models and routes. The launcher hardcodes none of them. OMP's native
   provider id is declared per provider as `omp_id` (defaulting to the
   provider key); `openrouter-free` maps to OMP's native `openrouter`.
3. **`omp` is the public Worker CLI.** `agent omp <provider>` is the
   supported spelling. `agent pi …` (with or without a provider) fails closed
   with a migration hint pointing at `agent omp <provider>`; it does not fall
   through to another harness. The native `pi` binary itself is untouched and
   remains usable outside the launcher.
4. **Explicit Worker launch contract.** Every OMP route passes
   `--provider <omp_id> --model <id>`, `--tools read,bash,edit,write`,
   `--no-lsp --no-pty --no-title`, and the destructive guard as a trusted
   extension. On `require_infisical` routes it additionally pins
   `--smol/--slow/--plan` to the same `<omp_id>/<model>` selector. `--models`
   is not passed because OMP documents it as Ctrl+P cycling, not an
   allowlist. The launcher never generates `--auto-approve`,
   `--approval-mode` or `--api-key`. For the `omp` adapter the passthrough
   also rejects `--profile`, `--config`, `--cwd` (each would move the
   auth/config source after the launcher's checks), and
   `--smol/--slow/--plan/--prewalk/--prewalk-into/--plan-yolo/--plan-yolo-into`
   (each would re-point or implicitly switch the pinned model roles). OMP's
   own approval flags are not filtered from arguments an operator
   deliberately places after `--`. Every OMP
   child also receives `OMP_SKIP_SETUP=1` so a fresh machine's first
   interactive launch does not block on OMP's setup wizard; `omp setup`
   remains available explicitly outside the launcher.
5. **The destructive guard is the permission boundary.** Because OMP's
   default `yolo` mode ignores the built-in bash critical-pattern override,
   the Pi destructive guard was ported to
   `script/omp-destructive-guard.ts` and is loaded with
   `--trusted-extension`. The launcher resolves the guard path next to itself
   and exits 1 if the file is missing; OMP additionally aborts startup if a
   trusted module is missing or unparseable. The tool surface is limited to
   the former Pi slot's `read,bash,edit,write`, removing OMP's task
   sub-agents, web, browser, python and todo tools.
6. **`--trusted-extension` is explicit and enumerable.** It is repeatable in
   OMP 18.16.0, hidden from `--help`, and disables ambient extension
   discovery. The launcher therefore names every trusted module. When running
   inside Herdr, it requires and passes
   `~/.omp/agent/extensions/herdr-omp-agent-state.ts` in addition to the
   guard; "inside" matches OMP's own detection (`HERDR_ENV=1` or any of
   `HERDR_PANE_ID`/`HERDR_TAB_ID`/`HERDR_WORKSPACE_ID`). A missing
   integration exits 1 with `herdr integration install omp`. Outside Herdr
   only the guard is loaded.
7. **Deterministic model selection and credential source.** Model ids are
   validated against the route/provider allowlist before a process starts;
   the Infisical-backed route pins all model roles and rejects implicit
   switches. For `require_infisical` routes the launcher rejects the local
   file/env sources it inspects that outrank the injected credential under
   OMP's ladder (runtime `--api-key` > `models.yml` `providers.<id>.apiKey` >
   stored OAuth > stored login API key > extension fallback >
   environment/.env > other stored key). The guard rejects ambient or dotenv
   profile/relocated-dir variables, an auth broker, non-empty retry fallback
   chains / advisor / context promotion, provider entries in `models.*` for
   the route provider, and an active `auth_credentials` row for that
   provider. Extension config fallbacks are outside its file-based view (see
   residual risks). It runs before secret fetch and again immediately before
   spawn; a concurrent writer can still race the final instant, so the check
   is not atomic.
8. **Rollback is a revert, not dual maintenance.** The Pi route
   configuration is not kept alongside OMP. Rolling back means reverting the
   migration commit(s); pc-setup already leaves native Pi installed, so no
   reinstall is required. The launcher maintains no persistent state.
9. **No new routes or fallbacks.** `omp.zen` is not added (the Worker slot
   uses OMP's native `opencode-go`, `openrouter`, `deepseek` and `minimax`
   providers), `opencode.opencode-go` remains out of scope, and no automatic
   model/provider/billing fallback is introduced.

## Consequences

- The configured OMP routes are `omp.openrouter`, `omp.openrouter-free`,
  `omp.opencode-go` (default `mimo-v2.6-flash`), `omp.deepseek` (default
  `deepseek-flash`) and `omp.minimax` (default `MiniMax-M3.1-Flash`).
  There are no `pi.*` routes and no `omp.zen`. Shortcut commands become
  `omp-<provider>`.
- Retired `pi-*` shortcut symlinks are not removed automatically:
  `agent shortcuts remove` only iterates names derived from the current
  routes. Invoking a stale link fails closed (exit 2) with a retirement error
  that names the `omp-*` replacement and the exact `rm <bin>/<name>` command;
  `agent pi …` itself prints the `agent omp` hint. Users must remove the old
  links manually (`rm ~/.local/bin/pi-…`).
- OMP package installation and version pinning belong to pc-setup; dotfiles
  owns the launcher and the route contract. pc-setup PR #158 retains native
  Pi for rollback/native use.
- The credential-source guard is scoped to `require_infisical` routes
  (currently `omp.opencode-go`). The other OMP routes rely on explicit
  `--provider/--model` and the route credential flow, but do not reject
  OMP-local stores, brokers or profiles. That is a deliberate scope choice,
  not an accidental omission.
- The approval boundary is an extension over OMP's `bash` tool, not an OS
  sandbox. It blocks the listed recursive/force deletion, force-push,
  hard-reset, forced-clean, checkout/restore, branch/tag deletion and stash
  destruction patterns; it does not make arbitrary destructive commands safe.
  The rule list must stay synchronized with the Claude hook and native Pi
  copy.
- Verification status: OMP 18.16.0 returned a real response and completed a
  bash tool call on OpenCode Go/MiMo and on the OpenRouter free model on
  2026-11-04; the destructive probe was blocked after the guard. DeepSeek
  reached the provider but the account returned HTTP 402 and MiniMax returned
  HTTP 429 on 2026-11-04, so response/tool success for those two routes is
  unverified. macOS was the only platform exercised; Windows native and
  WSL/Linux OMP routes, trusted-extension loading, Herdr and the guard remain
  unverified there.
- Known residual risks:
  - the guard rule table is shared with the Claude hook and native Pi copy;
    two short-form gaps are inherited rather than introduced here
    (`git push -d`, `git branch -d -f`). Closing them is a follow-up that
    must change every copy together;
  - an extension can register a config fallback
    (`keys.setConfig(..., { fallback: true })`) that the file-based guard does
    not inspect;
  - internal helper roles the user configures (for example an advisor or
    subagent role with its own model) are outside the guard, with the
    `--smol/--slow/--plan` pins as defense in depth;
  - the pre-spawn re-check reduces, but cannot eliminate, a TOCTOU race with a
    concurrent writer to `~/.omp`;
  - `--trusted-extension` disables ambient discovery, so any future extension
    the Worker needs must be added to the launcher's explicit list;
  - OMP version/flag semantics (`--trusted-extension` is hidden from
    `--help`) and the ported guard rules must be re-verified on upgrade;
  - the free route's allowlist does not detect the selected id becoming paid
    or retired; an account-side spend limit remains the hard stop.
- Supporting measurements are recorded separately in
  `docs/research/omp-pi-worker-migration-2026-11-04.md`; this ADR records the
  decision, not the measurement log.
- ADR-0012's Pi-specific decisions and consequences are superseded: its
  `pi.opencode-go` route, Pi-local `auth.json`/`models.json` guard, and
  Pi/Go verification notes no longer describe the Worker slot. ADR-0012's
  Claude Code Go route and fixed OpenRouter-free model decisions remain in
  force.
