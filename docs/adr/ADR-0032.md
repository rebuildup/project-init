# ADR-0032: 週次計画とリリース頻度を分離する適応的バッチング

- Status: Proposed
- Date: 2026-10-19
- Revises: ADR-0008 の sprint/version/release 1:1 cadence、ADR-0016 の sprint 基準の SemVer default
- Preserves: ADR-0009 のcost-aware CI、ADR-0017 の層分離、ADR-0027 のrelease merge承認境界
- Related: release scope admission #54
- Superseded by: None

## Context

1週間のスプリントをリリースの必須単位にすると、並列開発が速い週は変更を溜めて統合・検証・切り分けを難しくし、変更が少ない週は小さなrelease専用CI/deployを繰り返す。反対に常時公開すると、release固有のverification/publication costが過剰になる場合がある。

PR検証の頻度とproduction deploymentの頻度は別の変数である。CI実行回数だけ、変更ファイル数だけ、またはGitHub Actionsの無料枠だけでrelease効率を判定しない。測定されたrunner・deploy・待機・リスクを区別する。

## Decision

### 1. Planning cadenceとpublication cadenceを分離

- 1週間は**計画・優先順位見直し・進捗確認**の標準サイクルとして維持する。
- `1 release train = 1 target version = 1 release-* integration branch` は維持する。ただし `1 sprint = 1 release` は廃止する。
- 1つのrelease trainが複数の週次planning windowを跨いでもよく、1週内に承認された複数のreleaseが成立してもよい。
- sprint境界は**release candidateの再評価checkpoint**であり、merge / publishの自動triggerではない。
- release versionは利用者に見えるcontract・互換性・公開意図とexplicitなproject制約で判断する。従来の「通常sprintはminor」は初期参考値に留め、週次の経過をbump理由にしない。

### 2. Release batchingは費用・価値・滞留・変更リスクの総合判断

候補作成の判定では少なくとも、統合済みscope、依存関係/未確定事項、利用者への価値・修正緊急度、最古の未公開変更の待機時間、変更面/リスク、release-only verification時間、deploy実行コスト、復旧可能性を調べる。

- 早期候補化: project-localな変更量/リスク上限、価値ある独立機能の完成、セキュリティ・緊急修正など。
- 延期: 小規模かつ緊急性が低く、待機許容範囲内で、release実行の追加費用が相対的に大きい場合。
- 滞留上限: project-localで定義し、超過時には必ず**release review**を行う。未検証scopeの公開や黙示のuser承認を発生させない。
- 既存のrequired validationはrelease回数の削減を理由に無断で削除/skipしない。
- 固定の普遍閾値（PR数/ファイル数/Actions回数/金額）は設けない。project-specific quality profileと観測可能なrelease policyで定義・校正する。実測不足なら週次reviewをdefaultとする。

### 3. Admission / selection / terminal verificationを区別

- Admission: requirement・acceptance・dependency・validation pathが十分に確定した項目だけをrelease critical pathへ入れる（#54とは責務を重複させない）。
- Selection: release scopeと次releaseへのcarry-overを決め、候補のSHAを確定する。
- Terminal gate: 確定した候補のcurrent SHAに対しapplicableな統合・E2E・publication前検証を実行する。

### 4. Candidate freeze中のlanding制御

- release候補を確定するとき短いintegration freezeを明示し、release trunkの対象SHA/scopeとownerを記録する。freeze中は別ticketの自律landingを一時停止する。ticket実装・レビュー・他の独立workは続けられる。
- 候補へのbugfix等が必要ならownerがfreezeを解除し、変更範囲とcandidate SHAを更新し、影響した検証を全てやり直す。古いgreenを再利用しない。
- freeze前から進行している候補外ticket、stacked PR、依存Issueは失わず、次release trainへ明示的にretarget/rebaseしてdependencyとreview evidenceをreconcileする。旧trunkへの意図しない流入を防ぐ。
- candidateの公開・publication verification後に次release trunkへ移行する。複数branchの同時publicationを暗黙のdefaultにしない。

### 5. Publication authorityは不変

- release PR `release-* -> main` は常に明示的な、current interactionのuser authorizationを必要とする。candidate selection、Ready、週末、budget上限到達、passing CIをpermissionと見なさない。
- 未承認でもcandidate review / evidence準備まで進め、承認なしではrelease merge・production publicationを行わない。
- release mergeとpublished/verifiedを別の状態にし、publication artifactを再取得してcurrent release identityを確認する。

## Consequences

- 開発のスループットとproduction deployment回数を独立に最適化できる。
- sprintとversionが1:1でないため、release planningは複数planning windowおよび同週複数versionを表現できる必要がある。
- freezeは短くすべきで、長期化は次releaseの作業を不必要に阻害する。頻発するfreeze・revalidationは運用見直しの信号にする。
- 公開の判断コストは残る。測定不足を恣意的な閾値や架空の最適解で埋めない。

## Evaluation / re-evaluation

- 週次のrelease reviewと各releaseで、公開までの滞留、release-only runner/deploy usage、重複検証、候補変更による再検証、障害/rollbackの実績を記録し、project-localな閾値を調整する。
- negative: 週末だから自動merge、PR数だけで品質保証、freeze中に候補外ticketをlanding、変更後SHAへ古いgreenを流用、scope不確定なのに公開候補として扱う。
- positive: 小さな変更を意図的に翌週へ持ち越す、変更量増加時に早期候補化、緊急patch、candidateの明示承認待ち。
- release branch管理の追加費用が公開価値を上回るなど、実測で優位が失われたとき本ADRを再評価する。
