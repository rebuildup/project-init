# ADR-0005: Adaptive Stack-Aware Quality Gate Compilation

- Status: Accepted
- Date: 2026-09-05
- Extends: ADR-0001, ADR-0004
- Revises: ADR-0001 sections 4 and related fixed coverage assumptions
- Superseded by: None

## Context

The previous policy defined a strong deterministic completion gate, but its examples and defaults could be interpreted as a mostly fixed bundle: formatter, lint, type-check, dependency analysis, tests, coverage, build, and similar checks.

That is insufficient across heterogeneous projects.

Quality requirements are strongly dependent on the actual language, framework, runtime, application type, platform, architecture, persistence model, and release target. Frameworks also change their recommended testing levels, official tooling, CI examples, and platform-specific validation over time.

For example, a browser application, Rust service, Android application, native macOS application, library, and IaC repository should not inherit the same mechanical gate merely because they share this initialization policy.

The initialization phase is the correct place to resolve those differences because it already inspects the repository and may research current official guidance. Ordinary task sessions should consume a stable project-local gate rather than repeat ecosystem research.

## Decision

### 1. Quality gate is compiled per project

The policy defines meta-invariants, not a universal fixed command bundle.

During initialization, the agent detects the actual stack and compiles a project-specific quality profile from:

1. current framework/runtime/SDK official quality and testing guidance
2. current official examples/templates/starters
3. official first-party CI/Actions guidance where available
4. official language/toolchain guidance
5. coherent existing project configuration
6. established maintained ecosystem tooling
7. custom tooling only when necessary

The compiled profile becomes project-local reproducible configuration.

### 2. Initialization must implement the selected gate

Research alone is not completion.

When justified by the project, initialization may add or repair:

- formatter/linter/static-analysis configuration
- compiler/type-check configuration
- unit/component/integration/E2E test infrastructure
- framework/platform-specific test tooling
- dependency/static analysis
- coverage configuration
- schema/migration validation
- browser/device/OS/architecture matrices
- build/package verification
- security/dependency checks
- project-local Agent Skills for specialized verification
- GitHub Actions workflows and required CI checks

The policy does not require every category in every repository.

### 3. Prefer framework-native semantics

Before adding generic tooling, inspect what the actual framework/runtime already provides or recommends.

Do not duplicate responsibilities without evidence.

When official guidance recommends a specific testing level for a class of behavior, the gate should reflect that guidance rather than forcing a generic unit-test-first model.

### 4. Separate worker, integration, and release gates

The compiled profile should distinguish:

- worker gate: fast focused feedback for an isolated worker
- integration gate: full applicable checks for a ticket PR candidate
- release gate: release-wide validation before `release-x-y-z -> main`

The same project may therefore have different cost/coverage at each boundary while preserving deterministic semantics.

### 5. Keep local and CI semantics aligned

GitHub Actions is normally the CI execution platform, but CI should invoke project-local deterministic entry points instead of hiding unique validation logic in workflow YAML when avoidable.

Initialization should inspect current official GitHub Actions guidance and framework/runtime CI examples before creating workflows.

It should consider, when applicable:

- first-party setup actions
- caching
- matrix testing
- service containers
- browser/device dependencies
- test/artifact reports
- code/dependency scanning
- concurrency/cancellation
- least-privilege permissions
- secrets handling
- trusted vs untrusted pull-request behavior
- action version/pinning policy

Actions are selected because they improve the project's deterministic gate, not because more Actions are inherently better.

### 6. Agent Skills are part of the quality toolchain

When validation requires specialized context or procedures, initialization may create or install a short project-local Agent Skill.

The preference order is:

1. existing deterministic project command
2. framework/runtime official CLI
3. short project-local Skill wrapping deterministic tools
4. native agent capability
5. plugin/MCP only when it has a clear advantage

Large framework-specific instructions should not be copied into the root agent contract.

### 7. Coverage is project-specific, not a universal proxy

Coverage remains useful for meaningful testable source, and 80% may be used as a starting default when appropriate.

However, the final threshold and whether coverage is a meaningful blocking metric are determined from the actual project, framework guidance, risk profile, and existing baseline.

Coverage must not be gamed through broad exclusions, low-value tests, or threshold reduction merely to obtain green CI.

Where coverage is not the appropriate quality signal, replace it with better deterministic validation.

### 8. Quality profile is recompiled on meaningful change

Re-evaluate the profile when:

- framework/runtime major version changes
- official recommended tooling/testing changes
- a new application/platform target is introduced
- architecture boundaries change
- CI/release process changes
- gates become materially flaky or slow
- escaped regressions reveal a missing validation layer

## Consequences

### Positive

- each repository receives checks that match its actual failure modes
- current framework recommendations influence real project configuration instead of remaining documentation notes
- CI and local agent verification share the same semantics
- unnecessary tools and duplicate checks are reduced
- release-level risk can be checked separately from worker feedback
- ordinary agents use a concise precompiled gate without repeated ecosystem research

### Negative / Trade-offs

- initialization performs more research and configuration work
- quality profiles require maintenance as frameworks evolve
- cross-platform projects may require expensive matrix validation
- there is no single universal checklist that can be blindly copied between repositories
- official guidance may be incomplete or intentionally unopinionated, requiring project-specific judgment

## Re-evaluation triggers

Re-evaluate this ADR if:

- frameworks broadly standardize machine-readable quality profiles
- GitHub or another CI platform provides a portable first-party project quality manifest
- agent platforms can reliably infer current framework-specific gates without project-local configuration
- deterministic quality gates become centrally generated by another canonical project system
