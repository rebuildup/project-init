# ADR-0020: Verification Executors and Worktree-Independent Native Validation

- Status: Accepted
- Date: 2026-09-23
- Extends: ADR-0003, ADR-0005, ADR-0007, ADR-0011, ADR-0017
- Related: ADR-0019
- Superseded by: None

## Context

project-init's current local Practice strongly supports WSL/Linux, isolated mutable implementation workers, and Worktrunk-managed worktrees.

That is useful for authoring, but verification has a different shape. Some required environments are singleton or externally owned: Windows-native toolchains, GUI applications, physical devices, signing environments, Apple-native tooling, CI runners, installed applications, or hardware integrations. In some of those environments, creating another worktree/workspace is unavailable, undesirable, or not representative of the thing being verified.

Treating every validator as an implementation worker can force unnecessary branch/worktree lifecycle onto verification and can even make the verification less faithful.

## Decision

### 1. Verification Executor is a non-authoring execution role

A **Verification Executor** evaluates a specific immutable candidate artifact in a specified environment and returns evidence.

By default it does not author source and does not gain implementation/integration authority.

It may be implemented by:

- a native/local agent
- a human operator
- CI
- a device runner
- a GUI/native host session
- an external test service

The logical role is independent from the workspace mechanism.

### 2. Verification does not require a worktree

Worktree creation is required only when the selected implementation Practice needs an independent writable Git workspace.

A verification-only execution may instead consume:

- a commit/SHA materialized in a clean checkout
- a packaged artifact with content identity
- a container/image digest
- an installed build whose provenance is recorded
- a deployment/preview identified by immutable revision
- a device application build identified by package/version/hash

Worktrunk and git worktree are therefore authoring/workspace Practices, not universal verification prerequisites.

### 3. Evidence is bound to candidate identity

Every material verification result records enough provenance to answer:

- what exact candidate was verified?
- in what environment/runtime/device?
- with what procedure/command?
- what result was observed?
- what logs/screenshots/reports/artifacts support it?
- did verification mutate source or the candidate?

A branch name, "latest build", or a mutable deployment label alone is not sufficient identity when a stronger immutable identifier is available.

### 4. Singleton native environments use exclusive ownership

If only one native/GUI/device environment can safely perform a verification at a time, it is treated as a singleton mutable resource.

Use an exclusive lease, serialization, queue, or equivalent mechanism. Parallelism is not a requirement.

The lease protects environment/runtime state; it does not make the validator an implementation worker.

### 5. Source materialization must not corrupt authoring state

Preferred order:

1. verify a packaged/installed immutable artifact without source checkout
2. use a clean dedicated checkout/workspace
3. use a clean disposable clone/snapshot
4. only when unavoidable, serialize access to a singleton source checkout

When using a singleton source checkout:

- reject or checkpoint unrelated dirty changes before switching/materializing
- pin the target commit/artifact identity
- record before/after repository state
- do not silently incorporate verification-side source changes
- restore/reconcile the checkout after verification

A dirty developer workspace is not accepted as proof for a clean candidate merely because the application launched successfully.

### 6. Verification-side mutation invalidates evidence unless explicitly modeled

Unexpected source/config mutation during validation makes the result suspect.

Examples include:

- formatter/editor rewriting tracked source
- build tooling modifying committed config
- GUI tool upgrading project files
- test setup changing checked-in fixtures

If mutation is an expected part of the behavior under test, capture it as an explicit output and evaluate it. Otherwise, discard/re-run against a clean candidate.

Mutable runtime outputs outside candidate source may be allowed when isolated or cleaned according to the environment contract.

### 7. Platform-specific verification remains first-class

Windows-native, WSL/Linux, macOS-native, browser, device, hardware, CI, and remote environments can all satisfy the same Verification Executor contract while using different materialization adapters.

No platform is required to emulate WSL/Linux worktree topology merely to fit policy.

### 8. Verification can escalate into implementation

If a Verification Executor begins modifying source to fix the discovered defect, it stops being verification-only.

That new work requires a Worker execution attempt with the applicable mutable/durable guarantees. The original verification evidence remains tied to the original candidate.

## Consequences

### Positive

- native/GUI/device verification no longer breaks because worktrees are unavailable
- validation remains tied to immutable candidate identity
- implementation isolation remains strong where authoring actually occurs
- singleton environments can be safely serialized rather than artificially parallelized
- platform fidelity improves

### Trade-offs

- quality profiles must describe environment materialization and evidence provenance
- some native/manual verification remains slower and intentionally serialized
- adapters may need environment-specific cleanup/state auditing
- artifact provenance must be explicit for installed/deployed builds

## Re-evaluation triggers

Re-evaluate when:

- native toolchains provide reliable disposable workspace/sandbox APIs
- remote/device farms replace local singleton environments
- artifact attestation/provenance standards make materialization identity automatic
- verification and authoring environments converge enough that separate policy no longer adds value
