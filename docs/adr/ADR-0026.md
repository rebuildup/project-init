# ADR-0026: cf-first Cloudflare CLI with Wrangler compatibility fallback

- Status: Accepted
- Date: 2026-09-29
- Extends: ADR-0017, ADR-0022
- Classification: Current release-driven Operating Model / Practice
- Superseded by: None

## Context

Cloudflare projects have historically used Wrangler as the primary CLI for Worker development and many product-specific workflows. Cloudflare introduced the `cf` CLI as an open beta on 2026-09-28 with a broader API-generated command surface, `cloudflare.config.ts`, and Vite-oriented Worker workflows.

The migration is not yet equivalent to removing Wrangler everywhere. Cloudflare documents that some Worker development and deployment paths continue to delegate from `cf` to Wrangler, and existing Cloudflare documentation still contains many Wrangler-first examples.

A project-wide rule that continues to copy Wrangler commands from documentation would accumulate legacy automation even when `cf` already supports the same operation. A rule that bans Wrangler immediately would fail on compatibility gaps and delegated workflows.

The current Practice therefore needs one primary interface, an explicit fallback boundary, and a way to re-evaluate that boundary as the beta evolves.

## Decision

### 1. Cloudflare projects are cf-first

For projects that use Cloudflare, `cf` is the primary CLI for Cloudflare control-plane operations, resource APIs, and Worker lifecycle operations that it supports.

New repository-controlled scripts, CI, runbooks, and agent instructions SHOULD use `cf` when it can execute the required workflow with equivalent semantics.

Cloudflare-specific tooling is conditional. Projects that do not use Cloudflare MUST NOT add `cf` or Wrangler merely to satisfy project-init policy.

### 2. Wrangler examples trigger capability discovery, not automatic adoption

When upstream documentation or examples describe a workflow with Wrangler, first check the current `cf` surface before adding a Wrangler dependency or command.

`cf cli search` is the default discovery entry point when the equivalent command is not already known.

The spelling used by an older or product-specific document is not itself evidence that Wrangler remains required.

### 3. Wrangler is an explicit compatibility fallback

Wrangler MAY remain when at least one of these applies:

- `cf` does not expose an equivalent workflow
- the `cf` workflow is incompatible with the project's runtime or build path
- `cf` delegates that workflow to Wrangler
- migration would change externally relevant behavior without adequate validation

Each fallback must be bounded to the workflow that requires it. Scripts and instructions must not silently fall back from `cf` to Wrangler in a way that hides which implementation executed.

If `cf` delegates internally to Wrangler, moving the surface command to `cf` does not by itself justify deleting the Wrangler dependency.

### 4. Capability is version-sensitive and must be reconciled

Do not maintain a durable hard-coded list of commands that `cf` does or does not support. That list would decay quickly while the CLI is in active development.

During project initialization, tool upgrades, or relevant Cloudflare maintenance:

1. inventory repository-controlled Wrangler usage
2. check whether the current `cf` version provides an equivalent workflow
3. migrate supported workflows while preserving behavior and validation
4. retain only the fallbacks still required
5. remove obsolete Wrangler-specific automation and dependencies when evidence shows they are no longer needed

Required CLI versions remain subject to the project-local reproducibility rules in ADR-0022 and the current release-driven profile.

### 5. Configuration migration follows behavior, not policy compliance

A project MAY adopt `cloudflare.config.ts`, Vite-based Worker tooling, or other `cf`-native configuration when compatible with its architecture.

Do not rewrite working configuration solely to make the repository look migrated. Configuration changes must preserve the project's build, local development, deployment, binding, environment, and validation semantics.

### 6. Cloudflare CLI choice stays below the Constitution

Neither `cf`, Wrangler, Cloudflare, nor a specific configuration format is a Constitutional invariant.

They are replaceable Practices. A future Cloudflare tool or another provider-specific mechanism may replace them when it preserves or strengthens the applicable Identity, Authority, Evidence, Mutable Ownership, Continuity, Canonical Consistency, and Progress guarantees.

## Consequences

### Positive

- new automation converges on Cloudflare's intended successor CLI instead of extending Wrangler-first debt
- Wrangler remains available where migration is not yet technically complete
- documentation written for Wrangler does not force the repository to preserve an obsolete interface
- capability checks naturally shrink the compatibility layer as `cf` evolves
- non-Cloudflare projects receive no unnecessary tooling

### Negative / Trade-offs

- projects may temporarily carry both `cf` and Wrangler
- agents and maintainers must distinguish surface-command migration from actual dependency removal
- rapidly changing beta behavior requires periodic capability reconciliation
- upstream documentation may lag the preferred repository-local interface

## Verification

For a Cloudflare project, initialization and maintenance should verify that:

- `cf` is used for supported repository-controlled Cloudflare workflows
- Wrangler usage has an identifiable compatibility reason
- documentation examples were not copied into durable Wrangler automation without checking `cf`
- no required delegated Wrangler dependency was removed prematurely
- fallback behavior is explicit rather than silent
- tool versions are reproducible under the project toolchain policy
- Cloudflare-specific tool names have not become Constitutional requirements

## Re-evaluate / supersede

Re-evaluate this ADR when:

- the `cf` beta ends or its compatibility model materially changes
- Cloudflare removes Wrangler delegation from workflows used by maintained projects
- Wrangler reaches end of maintenance for the relevant project set
- another Cloudflare-supported interface supersedes `cf`
- repository evidence shows the fallback rule no longer adds value
