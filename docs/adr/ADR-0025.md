# ADR-0025: Adaptive agent-driven orchestration with Herdr

- Status: Accepted
- Date: 2026-09-27
- Layer: Operating Model + Practice
- Extends: ADR-0019, ADR-0021
- Related: ADR-0010, ADR-0011, ADR-0017, ADR-0020, ADR-0024
- Superseded by: None

## Context

project-init は Worker / Supervisor をlogical roleとして定義し、execution attemptを observational / mutable / durable に分類している。Herdrはその実装候補として、top-level coding agentの起動、prompt、wait、read、attach等を提供するoptional runtime Practiceとして採用済みである。

この境界は安全なmulti-agent executionには十分だが、agent数をどのように増減し、native subagentと独立Herdr Workerをどう使い分け、複数resultをどう比較・収束させるかという optimization policy は明示していない。

Herdrのagent automationは、あるagentが別agentのexecution surfaceを作り、workを送り、stateを観測し、resultを回収できる。これを単なるterminal/session observabilityとして使うだけでは、Supervisor roleが持つdecomposition・routing・fan-out / fan-in能力を十分に利用できない。

一方、agent数を増やすこと自体を目的にすると、dependency、mutable ownership、review independence、human/CI bottleneck、provider limit、context/compute costによってthroughputが悪化し得る。したがって、parallelismは固定fan-outではなく、work structureと観測可能なbottleneckに応じて適応させる必要がある。

## Decision

### 1. Optimize admitted progress, not agent count

orchestrationの目的はactive agent数を最大化することではない。

最適化対象は、current objectiveに対して有効なartifact / evidenceが安全に生成・admitされる速度とqualityである。fan-outは、その追加Workerが独立した有用workまたは意味のある探索diversityを提供できる場合だけ増やす。

mechanical / localized workはsolo executionをdefaultとし、deterministic toolingやfocused validationを優先する。

### 2. Use four fan-out modes

Supervisor / Coordinatorはtask structureに応じて次を使い分ける。

#### Independent decomposition

dependency graph上で互いに独立したnodeを別Workerへ割り当てる。

Ready / stack-readyなworkが複数存在し、mutable ownershipとresult identityを安全に分離できる場合の標準parallelismである。

#### Competitive exploration

同じuncertain problemへ複数のobservational Workerを独立に割り当て、異なるhypothesis、design candidate、diagnosis、optimization candidateを得る。

結果は多数決で選ばない。根拠、artifact identity、reproduction、measurement、applicable validationを比較してfan-inする。

mutable implementationを競争実行する場合は、各attemptが独立したmutable ownership boundaryを持ち、同一base/input identityへpinされ、immutable resultとして比較できる場合だけ許可する。

#### Specialist separation

implementation、review、benchmark、security、research等、異なる責務を独立Workerへ割り当てる。

required independent cold reviewではbuilderのprivate reasoningやself-evaluationをReviewerへ渡さず、objective / rubric / candidate artifact / validation evidenceを入力にする。

#### Speculative execution

predecessorのreviewable immutable snapshotが存在し、後続workを先行させる価値が高い場合に限り、そのexact snapshotへpinして開始できる。

predecessorが変化した場合はresultをstale candidateとしてreconcileし、影響するvalidationを再実行する。

### 3. Start with the smallest useful fan-out and adapt

initial fan-outは、独立して価値を出せる最小数を選ぶ。

追加spawnは少なくとも次を見て判断する。

- Ready / stack-ready workの有無
- unresolved uncertaintyと探索diversityの価値
- active WIPとintegration queue
- provider / model / token / compute limit
- host CPU / memory / disk / build-cache pressure
- human review / CI / external dependency待ち
- retry / blocked / stale attemptの比率
- orchestration overheadとresult回収cost

追加Workerの期待marginal valueが低い、またはintegration/human/CI/resource bottleneckが支配的ならfan-outを増やさない。idle capacityがあるという理由だけでtaskを細分化しない。

### 4. Route native subagents and Herdr Workers by lifecycle needs

短命でtop-level Worker内部に閉じるresearch / review / helperはnative subagentをdefaultとする。

別Herdr Workerへ昇格する標準条件は次のいずれかとする。

- independent mutable ownershipが必要
- parent process/session loss後も継続させる価値がある
- provider / model / toolchainを分離したい
- humanが独立lifecycleを観測・attachする価値がある
- long-running/background executionである
- sibling agentから独立にprompt / wait / readされるtop-level work unitである

Herdr pane数とlogical Worker数を1:1のorganizational invariantにはしない。

### 5. A supervised agent may drive Herdr directly

Herdr-managed environmentでは、Coordinator / Supervisor roleを担うagent自身がHerdr CLI/APIを使用し、sibling top-level Workerを作成・prompt・observe・collectしてよい。

標準loopは次とする。

1. objective / dependency / execution profileを解決する
2. fan-out modeとattempt classを決める
3. required workspace/runtime ownershipを先にmaterializeする
4. Herdr execution surfaceを作成し、returned IDを取得する
5. Worker agentをstartする
6. bounded promptを送り、wait / readで観測する
7. blocked / timeout / ambiguous deliveryをreconcileする
8. result contractとevidenceを回収する
9. current base / fencing / validation / authorityを確認してfan-inする
10. 残workとbottleneckを再評価し、spawn / continue / stopを決める

このloopをrecursiveな無制限spawnにしてはならない。nested delegationも同じWIP / authority / ownership / evidence boundaryに従う。

### 6. Herdr state remains telemetry

Herdrの `working` / `blocked` / `done` / `idle` / `unknown` 等はscheduling signalとして利用できるが、organizational completionやresult admissionの証拠にはしない。

timeoutやprompt-stalledは「instructionが未送信」の証拠ではない。consequential promptをretryする前にagent/pane stateとside effectを確認する。

### 7. Fan-in is evidence-based

複数Worker resultは、result contractへnormalizeしてから比較・統合する。

fan-inでは少なくともapplicableな次を確認する。

- task / attempt identity
- base / input snapshot identity
- fencing / ownership identity
- result artifact identity
- validation / benchmark evidence
- known limitations / unresolved conflict
- required review independence
- integration authority

competitive explorationでは「複数agentが同じ結論を返した」ことだけをcorrectness evidenceにしない。

### 8. Herdr-specific mechanics stay below the organizational contract

Herdr command shape、pane/workspace IDs、agent integration、official Herdr Agent Skill、remote machine addressingはPractice/adapter detailである。

Herdr公式Skillを利用する場合も、project-initのattempt / ownership / evidence / admission semanticsを上書きしない。Skillの導入はproject-local policyに従うか、installed Herdr versionと対応するrelease-matched skill sourceを利用する。

remote machineを利用する場合はtargetを明示し、machine-scoped runtime identityをdurable task identityへ昇格させない。remote failure時に別machine/localへsilent fallbackして同じmutable attemptを継続しない。

## Operational outcome

current release-driven profileでは、cross-boundary / judgment-heavy workのうち独立したtop-level workが複数存在する場合、Herdrをadaptive Supervisor runtimeとして利用できる。

典型形:

```text
Coordinator / Supervisor agent
  ├─ native subagent: short-lived research
  ├─ Herdr Worker A: independent implementation
  ├─ Herdr Worker B: benchmark / alternative exploration
  └─ Herdr Worker C: independent cold review

fan-out -> observe -> collect -> evidence-based fan-in -> re-evaluate
```

parallelismは一度決めた固定値ではなく、各fan-in boundaryで再評価する。

## Consequences

### Positive

- top-level coding agentsを人間が手動でpane管理するだけでなく、agent自身がSupervisorとして活用できる
- independent decompositionとcompetitive explorationを同じ安全contract上で扱える
- native subagentとexternal top-level Workerをlifecycle requirementから選べる
- resource/human/CI bottleneckに応じて過剰fan-outを抑制できる
- provider/modelの異なるWorkerを一つのfan-in contractへ収束できる

### Costs

- Supervisor prompt / wait / result collectionにorchestration overheadが生じる
- multiple candidateを作るcompetitive explorationはcompute/token costを増やす
- mutable competitive executionにはworkspace/runtime isolationが追加で必要
- Herdr command/API changeに合わせたPractice maintenanceが必要

## Re-evaluate

次の場合はこのdecisionを見直す。

- native coding-agent runtimeがcross-agent lifecycle / observability / fan-out / fan-inを同等以上に提供する
- Herdrより標準化されたagent control protocolが利用可能になる
- measured throughputでHerdr orchestration overheadがbenefitを継続的に上回る
- remote/cloud execution中心になりlocal Herdr control planeの価値が下がる
- project workloadがほぼmechanical/localizedになりtop-level parallelismの利用価値がなくなる
