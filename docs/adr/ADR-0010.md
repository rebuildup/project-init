# ADR-0010: Evidence-First Design Refinement and Decision Frontiers

- Status: Accepted
- Date: 2026-09-12
- Extends: ADR-0006
- Superseded by: None

## Context

ADR-0006 established a project-local decision hierarchy and required agents not to escalate self-evident implementation choices. The `engineering-decisions` Skill now defines when project evidence is sufficient and when genuine product/architecture decisions should reach the user.

One gap remains before implementation starts: a non-trivial request can contain unknown facts, hidden assumptions, and multiple dependent decisions without making their boundaries explicit. An agent may either start implementing from an assumption or compensate by asking a broad interview-style list of questions, including questions the repository could have answered.

Document-backed “grilling” patterns are useful because they force an agent to read existing project context before asking. For project-init, however, the desired behavior is narrower: integrate the evidence-first and dependency-aware parts into the existing decision hierarchy rather than introducing an external interview Skill as a mandatory dependency.

## Decision

### 1. Add a dedicated `design-refinement` Skill

Non-trivial feature, architecture, and product-design work receives a pre-planning refinement phase when meaningful uncertainty exists.

Its operating principle is:

> read relentlessly, ask minimally

The goal is not complete specification or a large interview. The goal is to remove only the uncertainty that can materially change implementation.

### 2. Read repository-controlled evidence before asking

Before forming user questions, inspect the relevant subset of:

- current request / Issue / acceptance criteria
- project-wide policy / canonical architecture / invariants
- design / specification
- ADRs and project-local Skills
- multiple relevant implementation locations
- tests / fixtures / schemas / contracts
- Git history / PR discussion when decision intent is not recoverable from current files
- current official framework/runtime/API/tool documentation when version-sensitive
- existing domain vocabulary / glossary

Conversation impressions or generic ecosystem convention do not substitute for project evidence.

### 3. Classify unknowns before escalation

Unknowns are separated into:

- **Fact**: discoverable from repository state, official sources, executable probes, or current system state
- **Determined decision**: effectively resolved by the existing project decision precedence
- **Unresolved consequential decision**: multiple meaningful options remain and the choice changes product semantics, architecture, public contract, risk, cost, release scope, or another escalation boundary

Facts are investigated autonomously. Determined decisions are resolved through `engineering-decisions`. Only unresolved consequential decisions may become user questions.

### 4. Hidden assumptions are explicit refinement input

An assumption that materially affects implementation is not allowed to remain implicit merely because it makes the first implementation easier.

Refinement pays particular attention to:

- user-visible behavior and domain semantics
- ownership / responsibility boundaries
- source of truth
- persistence and lifecycle
- failure behavior
- compatibility / migration
- security / privacy / permissions
- performance / cost budgets
- release / rollout behavior

If an item is a fact, investigate it. If it is a decision, place it in the decision graph.

### 5. Dependent decisions form a graph, not a flat questionnaire

When one decision depends on another, record that dependency.

Only unresolved nodes whose decision prerequisites are resolved belong to the current **decision frontier**.

Do not ask downstream questions whose answer would be invalidated or reshaped by an unresolved upstream decision.

Independent frontier decisions may be grouped when the user can answer them together.

### 6. User questions include synthesized evidence

A consequential frontier question should provide, where available:

- already-established evidence
- remaining meaningful alternatives
- consequences that differ between alternatives
- the agent's recommended option and rationale
- why project evidence cannot resolve the decision autonomously

This preserves user attention for actual decisions rather than repository lookup work.

### 7. Persist selectively

Long-lived results may be written to:

- design / specification
- ADR
- project-local Skill
- architecture / development documentation
- schema / contract / test
- domain glossary / domain context

Local reversible implementation details and transient research do not become documentation merely because they appeared during refinement.

Domain-vocabulary documentation is conditional. Projects with a meaningful shared domain may maintain a glossary or context document, but project-init does not require a fixed `CONTEXT.md` filename or an extra document for simple domains.

### 8. Keep `design-refinement` and `engineering-decisions` separate

The Skills are intentionally complementary:

- `design-refinement` discovers uncertainty, assumptions, and decision dependencies
- `engineering-decisions` resolves or escalates individual decisions using canonical precedence

This separation supports progressive disclosure and prevents every implementation task from loading a larger interview-oriented context.

### 9. Do not make an external grilling Skill mandatory

External Skills may be used as references or optional tooling under the normal dependency/tool-adoption policy, but the core behavior is project-local and repository-controlled.

Initialization must be able to produce the same refinement semantics without relying on a globally installed external Skill.

## Consequences

### Positive

- implementation begins with fewer hidden assumptions
- agents ask fewer repository-answerable questions
- user attention is concentrated on genuine product/architecture choices
- dependent decisions are resolved in a stable order
- domain decisions survive conversation loss when they have long-lived value
- the workflow composes with the existing decision hierarchy instead of replacing it

### Negative / Trade-offs

- non-trivial tasks may spend more time reading before implementation
- agents must judge when uncertainty is consequential enough to justify refinement
- decision graphs can become unnecessary overhead if applied mechanically to small reversible tasks
- selective persistence requires judgment to avoid both documentation loss and documentation noise

## Re-evaluation triggers

Re-evaluate when:

- agents still ask many questions that repository evidence could answer
- escaped implementation errors repeatedly trace back to hidden assumptions
- refinement becomes routine overhead for trivial tasks
- domain vocabulary repeatedly diverges across contributors/agents
- a standardized agent platform provides a stronger native requirement/refinement mechanism
- `engineering-decisions` and `design-refinement` responsibilities become difficult to distinguish
