# ADR-0010: AIエージェント開発の実績ベースDelivery Forecast

- Status: Accepted
- Date: 2026-09-14
- Extends: ADR-0003, ADR-0005, ADR-0007, ADR-0008
- Superseded by: None

## Context

AI coding agentは、実際のproject状況に根拠を持たないまま、もっともらしいcalendar estimateを生成できてしまう。

multi-agent開発のwall-clock deliveryは実装量だけでは決まらず、dependency構造、並列実行、model/provider usage limit、CI、人間のreview/decision、external wait、retry、reworkにも左右される。

このrepositoryでは既にweekly release cadence、isolated parallel execution、quality gate、recovery semanticsを定義している。一方で、中長期の完了日やcapacityを、これらの実態からどのように導くかはcanonical policyとして定義していなかった。

## Decision

中長期delivery forecastのcanonical progressive-disclosure policyとして `skills/agent-delivery-estimation/SKILL.md` を導入する。

このpolicyでは最低限、次を要求する。

- calendar estimateより先にrelative Work Unitとdependency graphを構築する
- Work Unit weightはproject-localな完了済みanchorから校正する
- 数値入力にはobserved throughput等のevidenceとprovenanceを持たせる
- agent capacity、human capacity、CI/internal queue、external wait、usage limitを分離する
- controlled evidenceなしにagent countの線形speedupを仮定しない
- historical evidenceがある場合はriskをrework / block / delayへ接続する
- unknownを `complete / conditional / unavailable` のforecast statusへ明示的に反映する
- sample qualityが十分な場合の確率forecastはempirical bootstrap resamplingを標準とする
- P50 / P80 / P95を公開できるsample-size quality tierを定義する
- projectに適する場合はobservation / forecastを永続化し、継続的に再校正する

ADR-0008の通常1週間sprintはplanning cadenceとして維持する。ただし、選択したscopeが1週間で完了するというevidenceとしては扱わない。

forecastを達成可能に見せるためにexecution isolation、recovery fencing、quality gate、release gateを弱めてはならない。

## Integration

- `github-delivery` はrelease / roadmap date、scope / capacity、carry-over判断で本Skillを使用する。
- `parallel-orchestration` はactive agent / WIP / blocking / resource observationを提供し、scheduleを理由としたagent scaling claimの前に本Skillを使用する。
- `quality-gate` はvalidation / CI wait / retry等の観測値を提供するが、required verificationのcanonical policyであり続ける。
- initialization promptにはSkill選択条件とinvariantだけを置き、詳細なestimation algorithmはprogressive disclosureのためSkill側をcanonical sourceとする。

## Consequences

利点:

- modelの直感ではなく実際のdelivery behaviorからproject planを作れる
- human review、wait、usage limit等のbottleneckを明示できる
- agent scaling効果を仮定ではなく観測・検証対象にできる
- forecastを継続的に再校正・監査できる

trade-off:

- 新規projectでは、便利な日付を捏造せず `insufficient data` を返す場合がある
- 有用な確率forecastには一定数の観測が必要
- calibrated Work Unitとobservationの維持に小さなplanning costが生じる
- cross-project一般化よりproject内historical calibrationを優先するため、project間比較には向かない

## Revisit when

より強い外部検証済みforecast modelを採用した場合、canonical planning unitをWork Unit / Issueから変更した場合、またはprovider-native telemetryによってcapacity / forecastを十分な精度で直接観測できるようになった場合に再検討する。
