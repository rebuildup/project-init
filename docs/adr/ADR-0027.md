# ADR-0027: Autonomous Ticket Landing with a Guarded Release Merge Boundary

- Status: Accepted
- Date: 2026-09-30
- Extends: ADR-0008, ADR-0016, ADR-0018
- Supersedes: ADR-0012 for non-release ticket PR landing
- Preserves: ADR-0012 explicit authorization semantics for release PRs targeting `main`

## Context

The previous merge-authorization model treated ticket PR landing and release PR landing as the same class of side effect. In practice this produced several kinds of delivery drift:

- ticket PRs reached Ready/mergeable state but accumulated because an Agent waited for per-PR merge permission
- durable ticket branches existed without a corresponding PR
- merged ticket PRs left stale remote branches behind
- linked Issues remained open after their changes had already landed on the target release trunk
- release PRs could be included accidentally in generic merge activity unless every caller remembered to distinguish them manually

These behaviors conflict with the release-driven operating model. Ticket PRs are ordinary integration work inside an already selected target release. The actual release boundary is the transition from the release branch to `main`.

The delivery policy therefore needs two different landing classes rather than one universal merge-authorization rule.

## Decision

### 1. Classify every PR before landing

Before any merge/landing operation, re-fetch the current PR and classify it from its actual head/base refs.

**Release-class PR**

- `base == main`
- `head == current release-*`

This is the only normal PR class allowed to update `main`.

**Ticket-class PR**

- does not target `main`
- belongs to the current ticket/release integration topology
- normally lands into the target `release-*` branch or an immediate predecessor ticket branch

A PR with `base == main` whose head is not the current release branch is invalid for landing and MUST be rejected.

A `release-*` PR MUST NOT be silently treated as a ticket PR merely because it appears in a bulk merge set.

### 2. Ticket-class landing is autonomous

A ticket PR does not require per-PR user merge authorization.

Once its applicable readiness/quality gates are satisfied and no real blocker remains, the Agent/Coordinator SHOULD continue through landing rather than stop at ready-to-merge.

Ticket-class landing:

- uses merge-commit semantics
- respects dependency order and current-SHA validation
- may use an equivalent stack landing only when merge-commit semantics and target-release-trunk correctness are preserved
- must not broaden into a release-class merge

Generic requests such as implementation, review response, conflict resolution, cleanup, or “finish this work” may therefore complete a ticket through target-release-trunk landing without a separate merge question.

### 3. Release-class landing requires explicit current authorization

`release-x-y-z -> main` remains a protected release boundary.

The Agent MUST NOT merge or enable auto-merge for a release-class PR unless the user explicitly authorizes that release PR or clearly bounded release action in the current interaction.

The following do **not** authorize a release merge:

- the release PR being Ready/mergeable
- green validation
- approval/review completion
- a generic “merge ready PRs”, “clean up PRs”, “finish the sprint”, or similar ticket-level instruction that does not explicitly include the release
- standing permission for autonomous ticket landing

Before executing an authorized release merge, re-fetch the PR and verify:

- `base == main`
- `head ==` the intended current `release-*` branch
- the current head SHA is the validated release candidate
- blocking review conversations are resolved
- the explicit authorization still applies to this release candidate

Release PRs are excluded from automatic/bulk ticket landing and from autonomous auto-merge.

### 4. Durable ticket branches must have a PR

After the first meaningful durable commit is published, the branch must have a corresponding PR.

Repository/recovery reconciliation MUST detect a non-release durable branch that has meaningful unlanded changes but no PR. The Agent must reconstruct the intended Issue/base/stack context from repository evidence and create the missing PR.

If the intended base cannot be determined safely, this is a delivery blocker; silently leaving the branch without a PR is not an acceptable steady state.

### 5. Ticket PRs must be linked to their Issue

The Issue-to-branch-to-PR relationship is mandatory durable state.

At PR creation/recovery, ensure the corresponding GitHub Issue is discoverably linked through native linkage where available and/or an explicit Issue reference in the PR metadata/body.

Do not assume that a closing keyword will close the Issue when the PR lands on a non-default release branch.

### 6. Landing includes Issue reconciliation

Ticket Done is reached when the ticket changes have reached the target release trunk, not merely an intermediate predecessor branch.

After target-release-trunk landing succeeds, the delivery loop MUST:

1. verify the landed commit/change is reachable from the target release branch
2. explicitly close the linked GitHub Issue as completed
3. reconcile dependency/PR metadata
4. continue to branch cleanup

This post-landing reconciliation is part of the ticket operation, not an optional housekeeping task.

### 7. Landed branches are cleaned up

A merged ticket branch should not remain as stale remote state.

After the ticket reaches the target release trunk, delete the ticket head branch when:

- no open PR still uses it as head or base
- no downstream stack member still depends on that branch identity
- the landed changes are recoverable from the target release trunk / Git history

If a downstream PR still depends on the branch, first rebase/retarget/reconcile that dependent PR to a durable surviving base and revalidate it, then delete the obsolete branch.

Release branches are not deleted by ticket cleanup. They may be deleted by the release-completion flow only after the release merge and required publication/post-release verification are complete.

### 8. Recovery performs delivery-state garbage collection

At recovery, onboarding, and completion boundaries, reconcile repository state for at least:

- durable ticket branch with no PR
- Draft PR whose readiness gate is already satisfied
- Ready ticket PR with no blocker that has not landed
- ticket changes on target release trunk with linked Issue still open
- merged/landed ticket PR whose obsolete branch still exists
- release PR accidentally queued for autonomous/bulk merge

Repair safe drift immediately. Report only blockers that cannot be resolved from repository evidence or available authority.

## Consequences

### Positive

- ticket PRs no longer accumulate waiting for redundant merge permission
- Issues and branches converge automatically with actual delivery state
- orphan branches without PRs become recoverable policy violations rather than silent drift
- the release boundary is safer because it is the only merge class requiring explicit human authorization
- generic bulk cleanup cannot accidentally release to `main`

### Trade-offs

- Agents are permitted to perform more ticket-level repository mutations autonomously
- stack cleanup requires careful dependency/base reconciliation before deleting branches
- implementations must correctly classify PRs from current refs before landing

These costs are intentional: ticket integration is routine execution inside an approved release scope, while `release-* -> main` is the explicit release decision.

## Re-evaluation triggers

Revisit this ADR if the project removes release branches, changes the meaning of `main`, adopts a platform-enforced merge queue with equivalent release classification, or changes the organizational decision about which boundary requires human authorization.
