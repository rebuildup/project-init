# ADR-0011: Agent Policy as an Evaluated Executable Contract

- Status: Accepted
- Date: 2026-09-12
- Extends: ADR-0001, ADR-0003, ADR-0005, ADR-0006
- Superseded by: None

## Context

project-init already compiles a large initialization policy into concise root instructions, project-local Agent Skills, deterministic quality gates, durable GitHub delivery state, and recovery metadata.

That architecture reduces ordinary context cost and makes execution reproducible, but it leaves a separate failure mode: a policy can be syntactically present and internally consistent while a fresh model still interprets it incorrectly.

Examples include:

- a critical rule being understandable only when the author remembers surrounding conversation
- model-generation changes altering how a Skill is routed or prioritized
- a grader rewarding surface keywords while missing the exact unsafe behavior the rule was written to prevent
- deterministic transformations being repeatedly re-reasoned in natural language
- small tasks receiving unnecessary multi-agent fan-out because orchestration strength is not separated from verification strength
- builder self-assessment leaking into review instead of evaluating the completed artifact cold
- progressive disclosure remaining structurally intact while the always-loaded root contract grows without measurement

Documentation review alone cannot reliably detect these failures.

## Decision

### 1. Agent policy is an executable contract

Significant Agent policy / Skill changes must be evaluated according to the behavior they are intended to produce, not only by prose consistency.

A policy change is divided into:

- **deterministic space**: behavior that can be checked from stable inputs using scripts, commands, parsers, schemas, metadata, exact Git relationships, or fixtures
- **latent space**: behavior that requires a fresh agent to read policy and make a judgment such as decomposition, escalation, prioritization, or qualitative review

Deterministic behavior should move toward deterministic tooling instead of being re-derived through model reasoning on every run.

### 2. Latent policy behavior uses cold evals

When wording, model generation, policy routing, or judgment can materially change behavior, keep a repository-controlled eval scenario.

A cold eval provides a fresh agent only the minimum policy required to perform the scenario.

Do not provide:

- the author's hidden reasoning
- the grader implementation
- expected answers
- irrelevant policy sections that accidentally supply the answer

The model invocation mechanism is not standardized. Manual agents, local runners, CI services, or future providers may all execute the scenario. The scenario and deterministic scoring/control artifacts remain repository-controlled.

### 3. Graders require controls

A grader is not trusted merely because a positive fixture passes.

At minimum, relevant evals must distinguish:

1. a naive negative answer that must fail
2. a regression fixture representing a previously broken or specifically unsafe behavior that must fail
3. a current valid answer that must pass

Critical must-not behavior is a hard failure and cannot be offset by a high aggregate score.

If the controls stop discriminating, eval scores are not accepted as quality evidence until the grader is repaired.

### 4. Execution profile is distinct from verification profile

Before using multi-agent orchestration, classify the execution behavior required by the task.

Default profiles:

- **mechanical**: deterministic local transformation; solo execution and focused checks
- **localized**: one bounded area with limited judgment; solo implementation with applicable validation
- **cross-boundary**: multiple system/policy boundaries and integration risk; dependency decomposition and selective parallelism
- **judgment-heavy**: architecture, product semantics, policy interpretation, visual quality, or trade-offs; evidence/rubric first and cold review

This profile determines orchestration/review strength.

The adaptive quality profile remains responsible for selecting test and verification levels from change risk. A mechanical change may still need strong verification if it touches a high-risk boundary, and a judgment-heavy documentation change may not need runtime E2E.

### 5. Judgment-heavy review is artifact-first and cold

For cross-boundary or judgment-heavy work, use an independent reviewer when the additional signal is worth the cost.

The reviewer receives:

- objective / acceptance criteria
- canonical reference or frozen rubric
- completed artifact / diff / immutable snapshot
- relevant validation evidence
- known limitations

The reviewer does not need the builder's private chain-of-thought or self-justification.

Numeric self-rating is not a required quality signal.

### 6. Progressive disclosure includes a context budget

Progressive disclosure is measured, not inferred only from directory structure.

When initialization policy is compiled or the root agent contract changes materially, inspect:

- root instruction word/byte/token estimate
- total always-loaded instruction cost
- conditional Skill sizes
- duplicated rules
- examples or reference material that can be loaded conditionally

No universal token ceiling is mandated.

Growth in always-loaded context requires a justification that the added content is truly always-on; otherwise it should move into a Skill, reference, or other conditional surface.

Critical invariants must not be deleted solely to reduce context size.

### 7. Repeated successful reasoning is also a codification signal

Codification is triggered not only by failure.

When the same non-trivial operation recurs:

- stable deterministic work -> script / command / config
- reusable judgment workflow -> Agent Skill
- long-lived project invariant -> policy / ADR
- verification behavior -> quality profile / test / eval

One-off local choices remain local and should not create policy noise.

## Consequences

### Positive

- policy changes can be regression-tested against real agent behavior
- model-generation changes can be evaluated without coupling project policy to one provider
- graders are less likely to become keyword bingo
- repeated deterministic work moves out of token-expensive natural-language reasoning
- simple tasks avoid unnecessary fan-out
- qualitative work gains cleaner independent review
- progressive disclosure can detect context growth quantitatively

### Negative / Trade-offs

- meaningful policy changes may need scenario and fixture maintenance
- latent eval execution can consume model/runtime cost
- deterministic graders can still overfit and therefore require controls and periodic review
- execution profile introduces another classification that must remain separate from quality/test risk
- context budget measurements are estimates and differ by tokenizer/provider

## Re-evaluation triggers

Re-evaluate this ADR when:

- model-generation changes produce materially different policy behavior
- a policy regression escapes existing evals
- controls no longer distinguish positive and broken fixtures
- a provider-neutral eval runner becomes practical enough to standardize
- root contract size grows materially
- orchestration overhead repeatedly exceeds task value
- execution-profile routing conflicts with actual project risk
