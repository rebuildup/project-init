# ADR-0035: Enforce dedicated Supervisor/Worker authority outside prompts

- Status: Proposed
- Date: 2026-11-02
- Layer: Operating Model + Practice
- Extends: ADR-0019, ADR-0025, ADR-0034
- Issue: #145

## Context

`project-init` already distinguishes Supervisor, Coordinator, Worker, and Reviewer as logical roles and provides external route resolution and partial Claude hooks. However, a Supervisor agent with direct Edit/Write/Bash/connector/credential access can perform implementation itself, even when instructed to delegate. Existing `claude-guard.mts` addresses native subagent substitution, not direct authoring.

The mechanical/localized `solo execution` optimization may be read as permission for a Supervisor to bypass delegation. Neither prompt wording nor a Git worktree by itself prevents direct side effects.

## Decision

1. Introduce a **dedicated non-authoring Supervisor execution profile** separate from the logical Supervisor role. When enabled, its process may decide, coordinate, observe, review and accept evidence, but may not write implementation artifacts itself.
2. Dedicated Supervisor cannot self-promote to Worker on the basis of difficulty, quota exhaustion or expedience. For small tasks, route to a lightweight Worker or deterministic executor instead; if unavailable, block. In a project not using dedicated separation, combined actor topologies remain possible under normal ownership and authority rules.
3. Enforce through capability separation at launch/runtime: read-only source access; no write-capable Git/remote/device credentials; separate Worker write identity; and a narrow policy-checking broker for spawn, observation and result admission. Direct integration mutation remains broker-executed with the existing immutable SHA/fencing/validation/release authorization checks.
4. Apply deny-by-default at harness tool level where available. For Claude Code provide a dedicated-checkout-only `PreToolUse` guard, restrict direct shell/edit and unknown MCP tools, and optionally allow exact trusted broker names. A general shell tool is **not** an acceptable broker capability.
5. Explicitly distinguish **adapter control** from **security enforcement**. Hook settings and prompts are modifiable by an actor with writable source or equivalent process control; read-only mounts do not protect remote side effects; credential separation and broker authorization must be verified independently. No implementation may claim enforced isolation from the hook unit tests alone.
6. Any alternate harness/sandbox implementation is allowed if it achieves the same capability and authority separation. Provider/model and Herdr panes remain Practice details, not constitutional requirements.

## Verification / rollout

- Unit regression for denied Write/Edit/Bash, unknown/MCP tools, malformed tool events, exact broker allowlist, and isolated guard installation.
- Claude Code `PreToolUse` hooks must fail closed on crashes/timeouts (`onFailure: block` requires Claude Code >= 2.1.295).
- Before real adoption, validate the specific macOS, WSL, or Linux launch mechanism: Supervisor local filesystem cannot be altered, GitHub/remote/device mutation cannot be done through direct or alternate tool/API, and authorized Worker/Broker paths do work.
- Initial reference adapter **does not implement a privileged broker or OS sandbox** and must not be called production-enforced. A project only using this adapter is a guarded preview, not a verified capability-separated Supervisor.
- Keep independent evidence of denied attempts and positive delegated completion; do not interpret Herdr `done` or an arbitrary PR as sufficient proof.

## Consequences

- Low-cost/small work may require an extra bounded execution attempt but avoids authority drift.
- A missing broker or failed enforcement preflight blocks work rather than silently reverting to local implementation.
- Tool-specific hooks are replaceable. Per-harness support and deployment are deliberately separate from the stable logical role policy.

## Re-evaluation

Re-evaluate if a future agent runtime provides verifiable delegated capabilities, immutable source access and scoped remote mutation natively; replace the adapter without weakening separation.
