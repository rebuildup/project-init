# ADR-0019: Logical Worker / Supervisor Roles and Tiered Execution Attempts

- Status: Accepted
- Date: 2026-09-23
- Extends: ADR-0003, ADR-0007, ADR-0011, ADR-0017
- Superseded by: None

## Context

project-init has treated multi-agent execution primarily through implementation workers, isolated runtimes, immutable snapshots/results, generation fencing, and Issue/PR delivery.

Those mechanisms are appropriate for independent mutable implementation, but they are unnecessarily heavy for short-lived research/review subagents and too concrete as a permanent organizational model. Native subagents, agent teams, external supervisors such as Herdr, remote/cloud agents, and future runtimes may provide different lifecycle mechanisms while preserving the same organizational guarantees.

The organization therefore needs stable logical roles and execution-attempt semantics that do not assume one task granularity, one process topology, one provider, or one workspace mechanism.

## Decision

### 1. Worker and Supervisor are logical roles

A **Worker** performs a delegated work unit and returns an observable result/evidence to its caller or organizational state.

A **Supervisor** owns lifecycle authority for execution attempts that require supervision: spawn/start, wait/observe, cancel, fencing/reassignment, recovery reconciliation, resource/policy application, and result admission.

These are roles, not mandatory processes. One native agent runtime, an external control plane, a CLI session manager, or separate actors may implement them.

A **Coordinator** owns decomposition, dependency ordering, routing, and integration planning. Coordinator and Supervisor may be the same actor, but their responsibilities are conceptually distinct.

A **Reviewer** is a specialized Worker whose default output is evaluation evidence rather than source mutation. Independent review requirements remain defined by policy-evaluation / parallel-orchestration.

### 2. Execution attempts are classified by required guarantees

A work unit is assigned the lightest execution class that preserves applicable constitutional properties.

#### Observational attempt

Typical uses:

- repository exploration
- research
- independent review
- read-only diagnostics
- bounded analysis

Default guarantees:

- task/attempt identity
- bounded authority and tool access
- evidence provenance
- no assumption that a branch, PR, sandbox, or durable checkpoint exists

If it mutates project source or shared mutable runtime state, it is no longer observational.

#### Mutable attempt

Typical uses:

- independent implementation
- code/test generation
- migration or stateful runtime changes
- any delegated work that owns writable project/runtime state

Additional guarantees:

- explicit mutable ownership boundary
- isolation, serialization, transaction, or equivalent conflict-prevention mechanism
- base/input identity
- result identity
- validation bound to the result artifact
- stale result rejection

A mutable attempt does not require a Git worktree specifically.

#### Durable attempt

Typical uses:

- Issue-level implementation
- long-running/background agent work
- remote/cloud execution
- work expected to survive parent/session/runtime loss
- work with consequential external side effects

Additional guarantees:

- durable discoverability
- recovery/checkpoint boundary
- fencing/ownership token or equivalent stale-attempt exclusion
- durable result/evidence references
- side-effect reconciliation where applicable

The current `execution_generation` integer is one implementation of fencing, not the permanent organizational API.

### 3. Durability is independent from Issue/task granularity

A GitHub Issue is a current durable planning unit, not the definition of a Worker.

A Worker may execute:

- a short subtask inside one parent session
- a review of one immutable candidate
- an independent implementation node
- an entire Issue
- a release-level or cross-repository work unit

The execution class follows mutable-state, continuity, authority, and evidence needs rather than ticket size.

### 4. Native subagents do not inherit heavyweight contracts automatically

A native subagent used for observational research/review does not need a branch, Draft PR, isolated mutable runtime, recovery generation, or durable checkpoint merely because it is a subagent.

If a native subagent performs mutable implementation, it must satisfy the Mutable attempt guarantees.

If it owns long-running/durable work, it must additionally satisfy the Durable attempt guarantees.

### 5. Supervisor APIs are capability-oriented

Project policy refers to logical capabilities such as:

- `spawn_worker`
- `observe_worker`
- `wait_worker`
- `cancel_worker`
- `recover_worker`
- `get_worker_result`
- `admit_worker_result`

Native APIs, MCP/ACP, CLI adapters, Herdr, external daemons, or future runtimes may implement them.

Provider-specific command shapes belong to Practice/adapter documentation.

### 6. Result admission is stricter than result production

A Worker may produce a result, but only the actor holding integration/admission authority may treat it as current organizational state.

Admission verifies, as applicable:

- task/attempt identity
- expected base/input identity
- current ownership/fencing identity
- artifact/result identity
- validation evidence binding
- authority for consequential side effects

### 7. Existing safety guarantees remain

This ADR does not weaken:

- Mutable Ownership Safety
- Identity Integrity
- Authority Integrity
- Evidence Integrity
- Organizational Continuity
- cold independent review requirements
- explicit human authorization boundaries for merge/landing

It changes which attempts require which mechanisms.

## Consequences

### Positive

- native subagents remain lightweight when they are truly ephemeral/read-only
- independent implementation still receives strong ownership and result guarantees
- Herdr and future external runtimes can implement Supervisor capabilities without becoming constitutional dependencies
- Issue-driven delivery remains useful without defining the ontology of all work
- Windows/native/device verification can be modeled separately from implementation workers
- current fencing mechanisms can evolve without changing organizational semantics

### Trade-offs

- orchestration must classify execution attempts before spawning them
- policies must distinguish role, execution class, and delivery unit
- adapters must expose enough state to prove the guarantees they claim
- an attempt may need promotion from observational to mutable/durable if its behavior changes

## Re-evaluation triggers

Re-evaluate when:

- native runtimes expose a broadly portable lifecycle/fencing/result protocol
- execution-class promotion becomes too complex in practice
- Worker/Supervisor separation duplicates a stronger standard protocol
- capability negotiation can be expressed more directly than current policy text
