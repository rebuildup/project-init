# ADR-0031: worktree lifecycleをfrontendから独立させ、Orcaを任意のfrontendとして併用する

- Status: Accepted
- Date: 2026-10-17
- Related: ADR-0017, ADR-0024, ADR-0025
- Supersedes: None
- Superseded by: None

## Context

Orca（stablyai/orca）は、並列worktreeの一覧、agent terminal、diff review、mobileからの通知と操作をまとめるdesktop appである。利点は大きいが、worktreeの作成からsetup、削除までを自分で持つ設計である。標準のWorktrunkとは、worktreeの作り方とsetupの置き場所で衝突する。

Orcaを前提にすると、次の問題が起きる。

- Orcaのない環境（別machine、CI、cloud agent）で同じ状態を作れなくなる。
- Orcaのworkspace状態やorchestration状態が、作業の正本のように扱われやすくなる。

一方、2026-10-17時点のOrcaには、Orcaに依存しない構成を取れる機能がある（commit `3813104` で確認）。

- `git worktree add` やWorktrunkで作った外部のworktreeを「Non-Orca worktrees」として表示できる。外部worktreeの置き場を、絶対pathで登録することもできる。
- `orca.yaml` の `scripts.setup` / `scripts.archive` で、作成時と削除時に任意のcommandを呼べる。Worktrunkにも、同じ役割の `pre-start` / `pre-remove` hookがある。
- `.worktreeinclude` は、Orcaと、Worktrunkの `wt step copy-ignored --require-include` の両方が読む。ただしOrcaはliteralなpathだけを扱う。

## Decision

1. worktreeのsetup / teardownとport決定は、frontendに書かず、repository-controlledな入口（例：`mise run worktree:*`）に置く。Worktrunk、Orca、plain gitのどれもが同じ入口を呼ぶ。入口は何度実行しても同じ状態になるようにする。
2. `.worktreeinclude` は、両方のfrontendが同じ意味で読めるよう、literalなpathだけで書く。
3. Orcaは任意のfrontendとする。Orcaに持たせないものは次の3つ。
   - lifecycleの処理
   - 作業の正本（Issue / branch / PR）
   - orchestrationの完了判断（telemetryとして扱う）
4. Orcaの `sharedDirectories` やWorktree Shared Pathsは、symlinkで共有する。そのため、並行して変わるpathには使わない。
5. Orcaを使う時の扱いは `orca-frontend` Skillに書く。このSkillは、Orcaを使うprojectでだけ発火する。

## Consequences

- 参照実装はproject-initの `scripts/worktree/setup.sh` / `teardown.sh`、`mise.toml`、`.config/wt.toml`、`orca.yaml` である。setupはbranch名から `.worktree.env`（`WORKTREE_KEY` / `PORT`）を決め、projectにmise.tomlがあればtoolchainを用意する。Worktrunk 0.80.0では、`wt switch --create` の `pre-start` でsetupが、`wt remove` の `pre-remove` でteardownが動くことを確認した。Orca上での動作は未確認である。

- Orcaをuninstallしても、移行作業なしで同じworkflowを続けられる。
- worktree作成時の処理は、projectの入口を一度用意すれば、どのfrontendでも同じになる。
- `worktree-workflow` のdev server例で使っていた `{{ branch | hash_port }}` のようなfrontend固有のtemplateは、複数frontendを併用するprojectでは使わない。portは入口の中で決める。
- Orcaのorchestrationとper-workspace environmentは、Herdrやsandbox-runtimeの代替候補として記録するにとどめる。採用は比較してから決める。

## Re-evaluate / remove

- Orcaが外部のlifecycle定義（共通の入口やhook）を標準で読むようになった場合は、`orca.yaml` の重複を見直す。
- Orcaのorchestrationがexperimentalでなくなった場合は、`supervisor-runtime` の担当として比較する。
