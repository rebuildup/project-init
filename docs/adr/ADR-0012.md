# ADR-0012: PR Merge as an Explicit Human-Authorized Side Effect

- Status: Accepted
- Date: 2026-09-12
- Extends: ADR-0004, ADR-0006, ADR-0008, ADR-0011
- Superseded by: None

## Context

project-init intentionally allows Agents to perform substantial GitHub delivery work autonomously: create branches, publish commits, open Draft PRs, update metadata, respond to review, resolve conflicts, run validation, and prepare release candidates.

The existing delivery model also described ticket landing and release-PR merge as ordinary steps in the autonomous flow. At the same time, the engineering-decision policy required escalation for irreversible or destructive operations.

That left an authorization ambiguity. A fresh Agent could reasonably interpret a green, approved, mergeable PR—or a user request such as "review対応して", "conflictを解消して", or "最後まで進めて"—as permission to complete the documented delivery flow and merge the PR.

GitHub credentials make this especially important: an Agent can act with the user's repository authority, while GitHub records the resulting merge as an action by that authorized account. Repository quality gates can determine whether a PR is safe enough to merge, but they do not determine whether an Agent was authorized to execute the merge side effect.

## Decision

### 1. Readiness and authorization are separate states

A PR can be technically mergeable, fully validated, approved, free of unresolved review conversations, Ready for review, and ready-to-merge without the Agent being authorized to merge it.

Quality/readiness answers **whether the candidate is acceptable to merge**.

Merge authorization answers **whether the Agent may execute the integration side effect**.

One state must not be inferred from the other.

### 2. Merge-class side effects require explicit user authorization

Agents, subagents, Coordinators, and Supervisors require explicit user authorization for the identified PR or clearly bounded PR set before they execute:

- merge commit
- squash merge
- rebase merge
- native stacked-PR / contiguous-stack landing
- auto-merge enablement
- a direct update of the integration target that is operationally equivalent to merging the PR

Repository policy, sprint plans, Issue metadata, CI, approvals, mergeability, or release-gate success are not substitutes for this authorization.

### 3. Generic completion requests do not imply merge permission

Requests such as `対応して`, `レビューして`, `conflictを解消して`, `リリース準備して`, and `最後まで進めて` authorize the work they explicitly request, but not merge/landing.

An instruction such as `このPRをマージして` or `問題がなければ #123 をマージして` does authorize the named merge side effect, subject to applicable quality gates and stated conditions.

The Agent does not need to ask for merge permission merely because a PR became ready. If no authorization exists, ready-to-merge is a valid stopping state.

### 4. Authorization is scoped and cannot silently propagate

Authorization is bound to the identified PR or bounded PR set and the task scope.

It does not automatically apply to another ticket PR, a sibling/successor in a PR stack, a release PR, or later unrelated PRs.

Expected review fixes may change the head SHA while remaining within an already explicit conditional instruction such as "fix the review and merge if checks pass". Applicable validation must still run against the current SHA.

If the base, target release, scope, included changes, or other material integration conditions change—or if it is unclear whether the new state remains within the authorized scope—the old authorization is not reused without confirmation.

### 5. The autonomous delivery loop stops at ready-to-merge without authorization

Without explicit authorization, the Agent may autonomously implement, commit/push, create/update Draft PRs, maintain metadata, address review comments, resolve conflicts, run validation, transition to Ready when appropriate, and report a ready-to-merge candidate.

The completion report records the target PR, current head SHA, relevant gate state, and remaining blockers.

Ticket landing, stacked landing, release merge, and auto-merge enablement occur only after the separate authorization gate passes.

### 6. Policy evaluation preserves this boundary

The repository keeps a cold scenario and deterministic grader controls for this failure mode.

The regression control represents the unsafe behavior of treating a review/fix request plus green mergeability as permission to merge.

The positive control requires review/fix-only requests to stop at ready-to-merge, an explicit named merge request to authorize the side effect, authorization to remain scoped to the identified PR, auto-merge to use the same authorization boundary, and changed integration state to trigger authorization revalidation rather than blind reuse.

## Consequences

### Positive

- Agents can continue doing nearly all delivery work autonomously without accidental integration.
- Quality gates remain strict while authorization semantics become unambiguous.
- A successful CI/review state cannot silently escalate repository mutation authority.
- The rule applies consistently to ticket PRs, release PRs, stacked PRs, and auto-merge.

### Trade-offs

- Fully autonomous end-to-end delivery now requires the user to state merge intent explicitly.
- Some tasks may finish in a ready-to-merge state rather than with the branch landed.
- Material changes after authorization may require a new user confirmation.

These costs are intentional because merge is a durable integration boundary rather than an implementation detail.

## Re-evaluation triggers

Revisit this ADR if a machine-verifiable merge-authorization capability is introduced, the delivery platform exposes a stronger actor boundary between human and Agent execution, release automation is deliberately granted separately approved blanket merge authority, or real incidents show these scope/invalidation rules are too permissive or unnecessarily blocking.
