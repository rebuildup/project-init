# ADR-0016: Canonical Release Governance for Linear, Version Intent, Main Protection, and Worktrunk

- Status: Accepted
- Date: 2026-09-21
- Revises: ADR-0004, ADR-0008, ADR-0013, ADR-0014
- Preserves: ADR-0012 explicit merge authorization boundary
- Reclassified by: ADR-0017 as the current release-driven operating profile
- Superseded by: None

## Layer classification

ADR-0017により、本ADRのLinear / SemVer intent / main protection / release-only integration / Worktrunk decisionsはConstitutionではなく、current release-driven solo-development Operating Model / Practiceとして分類する。

これらのdefaultは現在の標準として維持する。ただし、Identity / Authority / Evidence / Mutable Ownership / Organizational Continuity / Canonical Consistency / Progressの上位guaranteeを同等以上に満たすalternativeが成立する場合、tool/workflow固有部分はre-evaluateできる。

## Context

release workflowには、現在の運用と食い違う複数のdefaultが残っていた。

- Worktrunkが導入されていてもnative `git worktree`へ戻りやすい。
- target versionを毎回operatorへ質問し、release intentから決められる場合でも判断を外部化していた。
- GitHub ProjectsとLinearをplanning control planeの選択肢として残していた。
- 個人開発repositoryでrequired approvalを要求するとauthor自身がapproveできずmerge不能になりうる。
- required status check名を固定すると、実在しないCI/checkをrulesetが待ち続けるfailure modeがある。
- 一方で、review conversationを未解決のままmergeすること、ticket branchから`main`へ直接入ることは防ぐ必要がある。

## Decision

### 1. Linear is the standard release planning control plane

- Git: source state SoT
- GitHub Issues: durable implementation scope / acceptance criteria / dependency SoT
- GitHub PRs: review / integration / validation evidence
- Linear Projects / Initiatives: release goal / date / health / portfolio

GitHub Projectsは標準運用へ導入・要求・同期しない。GitHub IssueをLinear Issueへ全面mirrorせず、Linearはrelease-level control planeとして使う。

### 2. Select SemVer bumps from release intent by default

release versionを選ぶためだけの質問を通常は行わない。

- production / stable release boundary: MAJOR bump
- normal sprint release: MINOR bump
- adjustment within a sprint, or an adjustment added after that sprint was introduced: PATCH bump

explicit user version、external ecosystem compatibility、package contract等と衝突する場合はその制約を優先する。

release branchは従来通り `release-<major>-<minor>-<patch>` とする。

### 3. Main protection baseline is optimized for individual development

GitHubの保護機能を利用できるrepositoryでは、`main`に次を設定する。

- Pull Request required
- required approving review count = 0
- conversation resolution required
- required status checks = none by default
- direct push / direct web edit / force push / deletion prohibited in normal operation
- routine bypass disabled

CIやvalidationを廃止する決定ではない。project-specific quality gateはcurrent SHAへ実行する。GitHub Actionsが存在する場合はevidenceとして利用するが、存在しないcheck名や他repository由来のcheck名をrequired status checkとして固定しない。

### 4. Only the current release branch may merge to main

canonical pathは `current release-x-y-z -> main` のrelease PRだけとする。

ticket branch、stack intermediate branch、arbitrary branchから`main`へのPRはmergeしない。

GitHubのbranch protection/rulesetだけではPRのhead branch patternを直接制約できない。架空のrequired status checkを生成して補わず、merge executor / release automation / agent policyは `base == main` のmerge前に `head == current release-*` をpreflightし、違反を拒否する。repository固有の実在guardを使う場合も、そのcheck名をportable policyとして固定しない。

initializer / readiness reviewは、`release-only main integration` が **GitHub rulesetでmachine-enforcedされている** と誤報してはいけない。外部guard / merge executorがないrepositoryでは、この制約はGitHub UI自体では完全強制できないplatform limitationとして明示し、Agentが実行するmergeでは必ずpreflightする。

### 5. Worktrunk is the default WSL/Linux worktree frontend

WSL/LinuxでWorktrunkが利用可能・互換なら、通常のworktree create/switch/list/review/removeは `wt` を使用する。native `git worktree` はWorktrunk unavailable / incompatible / provisioning blockedの場合のfallbackとする。

Worktrunkはworkspace lifecycle adapterであり、runtime isolation boundaryではない。ADR-0013のisolation / port / tether / project-local config semanticsは維持する。

## Consequences

- version選択の不要なoperator round-tripが減る。
- LinearとGitHub Projectsの二重planningがなくなる。
- solo repositoryで自己approval不能によるmerge deadlockを作らない。
- unresolved review conversationは引き続きmerge blockerになる。
- nonexistent required checkによるruleset deadlockを避ける。
- release-only main integrationはpolicy / merge executor側でも明示的に検証する。
- Worktrunkが単なる「利用可能な選択肢」ではなく日常worktree pathになる。

## Verification

initializer / policy reviewでは最低限次を確認する。

- Linearがrelease planning control planeとして記載され、GitHub Projectsを要求していない
- version bump defaultがmajor/minor/patchのrelease intentへ対応している
- main protectionがPR required / approvals 0 / conversation resolution required / no fixed required checksになっている
- non-release source -> main mergeを禁止している
- Worktrunk available時にnative git worktreeより優先される
- project-specific validation自体は維持されている
