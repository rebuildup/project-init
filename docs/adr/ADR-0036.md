# ADR-0036: Verification placement for high-throughput agentic release trains

- Status: Proposed
- Date: 2026-11-16
- Layer: Operating Model + Practice
- Issue: #164
- Revises: ADR-0005 (ticket gate breadth), ADR-0006 (verification timing), ADR-0009 (CI trigger default), ADR-0033 (optional worker scheduling); does not repeal their evidence/correctness guarantees
- Canonical operational rules: `organization/profiles/release-driven-solo.md`, `skills/quality-gate/SKILL.md`, `skills/github-delivery/SKILL.md`

## Problem and evidence

Project-init's release-driven topology allows autonomous ticket → release landing, but ticket readiness can inherit E2E, native GUI, full platform CI, build and deploy obligations. If each small ticket waits for a device session or full release-grade check, the intended release aggregation boundary loses its purpose. Test existence, test applicability, execution frequency, evidence validity, and user acceptance are separate concepts.

This is a **gate placement** correction, not a claim that code can be proven correct by static checks alone. A release trunk is an integration line, not an always-green release candidate.

## Decision

### 1. Verification obligation has five dimensions

Every required check in a project-local quality profile must identify:
- **property**: behavior, interface, security, packaging, or runtime assertion it supports;
- **boundary**: worker, ticket, release integration health, frozen release candidate, human acceptance/publication;
- **trigger and cost**: the minimal event where evidence is needed, with measured or estimated runtime/resource impact;
- **identity**: source SHA / candidate artifact / execution environment it actually examined;
- **failure semantics**: PASS, FAIL, NOT_RUN, DEFERRED, BLOCKED, or NOT_APPLICABLE without representing skipped checks as green.

A required gate remains blocking **at its assigned boundary**. Moving it to release candidate is a deliberate policy revision, not falsely marking the prior gate passed.

### 2. Build and ticket integration prioritize cheap, sufficient evidence

- Worker feedback defaults to focused unit/property/contract checks, lint/type/static diagnostics and targeted build only if needed to prove the changed boundary.
- At ticket landing, run minimum sufficient, risk-selected deterministic checks on the actual integration candidate; ensure acceptance criteria, conflicts, staleness, current identity, and blocking findings are resolved.
- Do **not** make full-suite E2E, full OS/device matrix, GUI/session screenshots, production deploy or complete package build implicit prerequisites for every ticket. An existing required CI check is not automatically equivalent to release-grade proof.
- Tests and oracle/contract work may be added early even when their expensive execution is deferred. Do not replace meaningful real-boundary tests entirely with mocks or claim unit PASS proves wiring.
- Independent code review is defect-seeking and risk-sensitive, not a fixed number of rounds or agents; high-signal reviews complement deterministic tests.
- Non-release ticket PRs satisfying their actual gate land autonomously and close their linked Issue on release-trunk reachability. Human manual acceptance is not a hidden ticket Done condition.

### 3. Release trunk receives changes continuously; freeze creates the release candidate

- A release branch may contain unverified combined behavior while tickets integrate. Ordinary release-trunk push should not trigger a complete release gate or deployment; optional cheap integration-health signals are allowed.
- At an adaptive, meaningful checkpoint, declare a release candidate, freeze scope and immutable SHA, and execute full applicable integration, E2E, packaging, compatibility, native/device, deployment rehearsals and security controls.
- Freeze cannot convert an omitted test to PASS. If a required candidate check fails or is unavailable, candidate readiness is blocked or an explicitly authorized risk decision is needed.
- Changes to a frozen candidate invalidate **affected** evidence, not unrelated immutable results. Revalidation follows the actual dependency/blast radius; no stale green is attached to a new SHA.
- Manual/visual/native acceptance generally belongs to a consolidated candidate and can be owned by the human operator. Its state stays distinct from agent validation; project-local exceptional pre-integration checks must name the actual risk and evidence.

### 4. Earlier high-risk gates remain possible

Do not defer evidence required to prevent an unacceptable release-trunk side effect, e.g. destructive shared-schema change, irreversible migration, exposed vulnerability, breaking protocol or unsafe external write. Specify the failure mechanism, affected boundaries, smallest adequate early test, and why release-only verification is insufficient. A universal "native-related path changed => full matrix every PR" rule is not an acceptable substitute for that decision.

### 5. CI and branch-protection compilation

The quality profile and workflows must agree on which checks are **required for ticket landing** versus **required for release readiness**. Do not configure a release-only check as a mandatory ticket required status. Trigger release-grade CI only for an explicit candidate/freeze event or a provably equivalent bounded release mechanism, not every push to `release-*`. Keep push/PR duplicate full runs disabled; keep cheap checks and correct GitHub required-check semantics. Path-filtered required workflows can remain pending, and job-level skips may report success: avoid both false blocking and false green. A skip is not proof.

### 6. Authority and source of truth

The source-of-truth hierarchy remains Constitution > Operating Model > Practice > Skill; repo Issues own acceptance, PRs own integration evidence. Release integration does not imply publication or human acceptance. Current default: ticket PR → release trunk uses autonomous authority; `release-* → main` needs the explicit current interaction release authorization, except where a project-specific explicit decision legitimately changes its authority boundary.

### 7. Learn from the ecosystem, do not import it wholesale

Original poteto pstack emphasizes *subtract before add*, boundary discipline, behavior-oriented tests, verifiable units and proving claims. Use its engineering principles, not Cursor-specific routing, model choices, obligatory all-stage GUI execution or mandatory swarm sizes. OpenAI harness engineering demonstrates a minimal-gate high-throughput environment, not a universal free pass to bypass security. Code review has a different detection surface than runtime tests; their outputs must not be conflated.

## Operational migrations / evaluation

1. Inventory every active CI trigger, required status, pre-push hook, test matrix and GUI acceptance condition. Classify each as **Retained at boundary**, **Moved to freeze**, **Risk-triggered exception**, or **Intentionally removed** with justification. No silent deletion.
2. Recompile project-local quality profiles and GitHub rulesets; repair now-invalid required-check identities. Do not disable security/required guarantees without replacing their assigned assurance.
3. Add negative scenarios: ordinary GUI ticket no native executor, release trunk push no full matrix, frozen SHA fails a required E2E, skip reported green, high-risk migration needing early test, stale SHA after scope change, and ticket vs release merge authority.
4. Benchmark across comparable release trains: time-to-ticket-landing, agent wait, CI runner-minutes, device occupancy, repeated runs, release freeze duration, escape defects, incident/rollback rate. Compare before and after; do not infer effectiveness from CI spend alone.
5. Downstream rollout is project-specific, respects their existing Issue/ADR/CI/branch contract and does not silently replace live pipelines.

## Consequences and constraints

Positive: preserves cheap frequent feedback, concentrates expensive evidence on the artifact that ships, shortens the integration feedback cycle, makes unverified state explicit.

Risk: late detection may increase blast radius and release repair time; mitigate via early contract checks, explicit risky-boundary exceptions, test oracle quality and rollback/freeze discipline. High-frequency release trains may favor broader per-PR tests if measured trade-offs justify them.

## Re-evaluation

Revisit when candidate defect escape / rollback or freeze repair grows, when measurable per-ticket cheap gates stop predicting release failures, when native acceptance cannot be safely batched, or when the release branch itself produces irreversible production-side effects.
