# ADR-0015: Active source security audit and advisory maintenance separation

- Status: Accepted
- Date: 2026-09-16

## Context

project-initの `security-maintenance` は既知advisoryのintake、project reachability、priority、Issue / remediation / releaseを所有する。一方、source codeから未知のsecurity invariant failureを能動的に探索するときのcoverage、candidate state、independent verification、source外factの扱いはcanonicalに定義されていなかった。

Cloudflare `security-audit-skill` のreconnaissance、coverage-led hunting、candidate validation、structured output、independent verificationはこの不足を埋める有力なdesign referenceだが、upstream固有runtimeをそのまま導入するとproject-init既存のorchestration/sandbox/recoveryと二重化する。

## Decision

1. `skills/security-audit/` をactive source auditのcanonical Skillとして追加する。
2. principal / trust boundary / entry surface / attack classからcoverage unitを作る。
3. hunterはcandidateを発見できるが、自身でconfirmedへ確定できない。fresh verifierが反証する。
4. verdictを `confirmed / needs_validation / rejected` に分離し、severityはconfirmedだけに付ける。
5. source/local fixtureから決まらないprovider/deployment/runtime factは推測せず `needs_validation` とする。
6. audit中のtarget-controlled executionは `sandbox-runtime`、fan-outは `parallel-orchestration`、fix verificationは `quality-gate`、deliveryは `github-delivery` を再利用する。
7. audit Skill自身はtarget sourceを修正しない。confirmed findingを `security-maintenance` へ渡し、project-aware priority後に通常のIssue / remediation / releaseへ接続する。
8. `blocked / deferred / out_of_scope` をcovered扱いせず、quick/scoped runからfull coverageを推論しない。

## Consequences

- auditのcoverage gapと「findingなし」を区別できる。
- false positiveをindependent verifierで抑制できる。
- deployment-only uncertaintyを推測せず残せる。
- advisory起点とsource-audit起点のsecurity workを同じdelivery workflowへ収束できる。
- standard/deep auditではagent/review costとstructured artifact maintenanceが増えるが、profile/scopeでbreadthを調整し、evidence barは下げない。
