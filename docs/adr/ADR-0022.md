# ADR-0022: mise as the Default Project Toolchain and Bootstrap Practice

- Status: Accepted
- Date: 2026-09-25
- Extends: ADR-0004, ADR-0005, ADR-0006, ADR-0017
- Classification: Current release-driven Practice
- Superseded by: None

## Context

project-init requires cross-platform development, repository-controlled reproducibility, fresh-agent onboarding, and validation that does not depend on undocumented machine state.

Projects currently use language-native version files, host package managers, Nix, containers, and ad-hoc bootstrap instructions in different combinations. These mechanisms solve different layers. Requiring Nix for every project-level runtime or development CLI is unnecessarily heavy, while relying on globally installed tools creates hidden dependencies and version drift.

A lightweight project-local layer is needed to declare and materialize development runtimes and CLI tools consistently across macOS, WSL/Linux, Linux/NixOS, CI, and agent environments without making the host operating-system mechanism part of the project contract.

## Decision

### 1. mise is the default project-local toolchain/bootstrap Practice

For the current release-driven profile, project initialization SHOULD provision or detect mise and use it as the default project-local toolchain/bootstrap layer when compatible with the project and target hosts.

The repository SHOULD commit a root `mise.toml` when the project has runtime or development CLI prerequisites that mise can manage usefully.

The normal entry points are:

- `mise install` to materialize configured project tools when no committed mise lockfile is the reproducibility mechanism
- `mise install --locked` when a committed mise lockfile provides the reproducible resolution; locked mode MUST fail rather than silently resolve a missing required lock entry
- `mise exec -- <command>` to run an existing command with the project tool environment
- `mise run <task>` for repository-defined cross-platform task entry points

Interactive shell activation is optional. CI, automation, and agents SHOULD prefer `mise exec` or `mise run` so correctness does not depend on shell startup files.

An external or otherwise untrusted PR checkout is a different trust boundary. Before an agent runs `mise install`, `mise exec`, or `mise run` against repository-controlled configuration from that checkout, it MUST either complete a documented trust review of the active mise configuration/tasks or execute inside a bounded sandbox appropriate for untrusted project code. For inspection-only operations where supported, `MISE_SAFE=1` SHOULD be preferred before trust is established. A trust review or safe-mode check MUST NOT treat mise itself as an isolation boundary.

### 2. Repository-controlled tool identity must remain reproducible

A project MUST NOT use an unbounded moving version such as `latest` as the only reproducibility contract for a required tool.

Use one of the following as appropriate:

- an exact version request in `mise.toml`
- a bounded version request plus a committed mise lockfile, installed in strict mode with `mise install --locked`
- an existing ecosystem-native canonical version file consumed or respected by mise

Upgrade operations are explicit maintenance changes and must update the relevant committed configuration/evidence together.

### 3. Do not create competing version authorities

mise is an aggregation/bootstrap layer, not a reason to duplicate canonical toolchain declarations.

When the ecosystem already has a canonical development-version source required by the project, preserve one authority and configure mise around it where supported. Examples include:

- Rust `rust-toolchain.toml`
- package-manager declarations such as the project's canonical `packageManager` metadata
- other language/tool specific version files whose semantics are already part of the project contract

Do not keep two independent pins that can silently disagree. If mise cannot consume or safely mirror the canonical source, document which file is authoritative and add verification that detects divergence.

Compatibility-range fields are not automatically development-version pins. A minimum supported runtime range MUST NOT be treated as the version the project is built and validated with unless the project explicitly defines that meaning.

### 4. mise does not replace ecosystem dependency managers

mise manages development tools and runtime selection. It does not replace application dependency resolution or its lockfiles.

Examples:

- Node/Bun/pnpm dependencies remain governed by the selected package manager and its lockfile
- Rust dependencies remain governed by Cargo and `Cargo.lock`
- Python project dependencies remain governed by the selected project dependency manager and its lockfile

A mise task MAY wrap these commands to provide a stable repository entry point without changing their ownership semantics.

### 5. mise does not replace system/runtime isolation layers

mise is not an OS dependency manager, container runtime, sandbox, secret manager, or implementation-worker isolation boundary.

Continue to use the appropriate layer for:

- OS packages, kernel capabilities, native system libraries, drivers, and host integration
- Nix/NixOS configuration where system-level reproducibility or host provisioning requires it
- devcontainers/containers/remote sandboxes where execution isolation is required
- Worktrunk for the current WSL/Linux worktree lifecycle Practice
- Infisical or the selected secret-management Practice for secret values

A successful `mise install` is evidence that project tools were materialized, not evidence that the whole execution environment is isolated or production-equivalent.

### 6. Canonical tasks should be discoverable and non-duplicative

When a repository benefits from stable cross-stack commands, `mise.toml` MAY define tasks such as `bootstrap`, `dev`, `test`, `lint`, `check`, or `ci`.

Tasks SHOULD delegate to existing canonical scripts rather than reproduce large command bodies in multiple places. For example, if `package.json`, `Cargo.toml`, or a repository script already owns validation semantics, the mise task should call that entry point.

The quality gate remains defined by project policy and repository evidence; adding a `mise run ci` wrapper does not weaken or redefine required validation.

### 7. Fresh-clone onboarding uses the repository contract

Onboarding documentation SHOULD identify mise as the standard project tool bootstrap path when adopted and provide the smallest deterministic sequence required to reach the canonical run and validation commands.

Personal/global mise configuration MUST NOT be required for correctness. Project-shared configuration belongs in the repository; personal overrides belong in local-only configuration and must not become a hidden prerequisite.

### 8. Fallback is explicit, not silent

If mise is unavailable, incompatible, or cannot manage a required tool correctly on a supported environment, the project MAY use an ecosystem-native or platform-specific fallback.

The fallback MUST preserve the same version/reproducibility guarantees and be documented as an explicit compatibility path. Agents MUST NOT silently bypass a repository-declared mise toolchain with arbitrary host-global versions.

### 9. mise remains replaceable

mise is a current Practice, not a Constitutional invariant.

The invariant is that required project tools are discoverable, reproducible, repository-controlled, portable across supported environments, and usable by fresh humans/agents without undocumented global state.

A future mechanism may replace mise under ADR-0017 refinement rules if it preserves or strengthens those guarantees without violating explicit project decisions.

## Consequences

### Positive

- one lightweight bootstrap surface across macOS, WSL/Linux, Linux/NixOS, CI, and agents
- fewer hidden host-global tool dependencies
- runtime and CLI versions become easier to discover and reproduce
- Nix/container use can stay focused on system-level and isolation concerns
- repository tasks can expose consistent commands without replacing ecosystem-native build systems
- agents can invoke deterministic project tools without relying on interactive shell configuration

### Negative / Trade-offs

- mise becomes another developer prerequisite
- projects must avoid duplicate version pins between mise and native ecosystem files
- not every system dependency or platform-specific tool is suitable for mise
- lockfile/version configuration must be maintained during tool upgrades
- repositories with no meaningful managed tool prerequisites may gain little from adding mise

## Verification

Initialization / onboarding / policy review SHOULD check:

- required development runtimes and CLIs are declared in repository-controlled configuration
- `mise install` succeeds on supported hosts where mise is the selected path; when a committed mise lockfile is the reproducibility mechanism, `mise install --locked` succeeds and the lockfile contains the required entries for every configured supported tool/platform used by the gate
- `mise exec` / `mise run` do not depend on undocumented global shell state
- external/untrusted PR checkouts require a documented trust review or bounded sandbox before project-controlled mise execution, and mise is never treated as the isolation boundary
- required tools are exact-pinned or reproducibly locked
- native canonical version files and mise configuration do not conflict
- ecosystem dependency lockfiles remain canonical for application dependencies
- system packages, secrets, and runtime isolation are not incorrectly delegated to mise
- documented fallback paths preserve equivalent guarantees
- CI and local canonical commands resolve equivalent tool versions/semantics

## Re-evaluation triggers

Re-evaluate this decision when:

- mise materially changes configuration, lockfile, trust, or tool-resolution semantics
- a first-class language/workspace mechanism covers the same cross-language bootstrap problem with lower complexity
- supported platforms cannot use mise reliably
- the project moves to a fully image-based or remote environment where project-local host tool installation no longer adds value
- ADR-0017 refinement analysis shows another mechanism provides equivalent or stronger guarantees with lower policy cost
