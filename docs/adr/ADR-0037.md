# ADR-0037: 要求保存・全体改善と実成果物の品質制約

## Decision

要求充足、全体再構成、候補間改善、既知欠陥排除、最適性の保証を独立した能力として扱う。既知アンチケースを排除しても最適性は成立しない。要求変更時は現状修正案と要求からの構成案を扱い、要求を保存する改善関係を実証する。

`system-quality`はこれらの接続を担当する。設計判断はdesign-refinement / engineering-decisions、成立証拠はcorrectness-assurance、実成果物の受理条件はquality-gate、評価はpolicy-evaluationが所有する。指示を重複して別の正本にせず、参照を接続する。アンチケース・改善関係は共通の出発点をSkillに同梱し、具体的制約は意味を所有するコード・解析設定へ配置する。

## Concrete changes

- TypeScriptの対象をディレクトリ別の五つの列挙から全体パターンへ変更する。新配置のソースも対象に入り、Skill内の実行コードも検査される。
- JSON/YAML/TOMLは既存parser、shellはbash構文確認とShellCheck、Markdown参照は構文木で検査する。未知のfile種別とTypeScript抑制は明示的な契約変更なしに通さない。依存はbun.lockへ固定する。
- 独立したファイル列挙とTypeScript設定の解析結果を比較し、対象外ソースを拒否する。local Markdown参照の切断も検出する。意図的な壊れた参照fixtureはその一ファイルだけを除外する。
- PRのpath列挙を除去し、品質検査の入口が新しい配置や文書変更で欠落しないようにする。検査内容はsource-levelに保ち、release全体の検証へ拡張しない。
- 違反混入executorはbaseline、正当変更、拒否、異常、通過を区別する。元コードを変更せず、caseごとのコピーを使い、対象とsuiteのdigestを返す。
- 廃止済みshell commandへの指示を実在するTypeScript commandへ更新する。

## Evidence and limits

型検査範囲の改善は、既存の型検査オプションを保持したうえで、新配置ソースを取り込めることと、除外の再導入を検出できることで検証する。コード行数や違反件数を最適化目標にはしない。

challengeの成功は既知ケースの識別であり、検査器の完全性・要求の完全性・実プロジェクトの最適性の証明ではない。sourceコピーはOS sandboxではない。適用先で独立強制を主張するには、trusted revisionの検査器・suiteと、候補が迂回できない受理権限を別に確立する。

C1/C2/C5/C6の意味判断とモデル対応は、指示の存在だけでは保証されない。評価時には実成果物と元要求を与え、縮小・証拠すり替え・既存構造の無根拠な維持を具体的に検証する。形式化可能な対象は対応を確立して証明し、未証明を合格の言い換えで隠さない。

## Re-evaluation

新要求で適用条件や比較関係が変われば規則と構造を再評価する。重複する機構や旧構造は移行後に撤去する。Skill・検査・文書の追加数は成果ではない。より良い構成が実証された場合は、既存の責務分割も置換する。

## Context budget

新しい責務の正本はsystem-qualityに置き、既存Skillへは境界と参照を追加する。engineering-decisions、quality-gate、skill-selectionの増加を再基準化し、新Skillを基準へ加える。その他の既存baselineは保持する。閾値自体は変更しない。
