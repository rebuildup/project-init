# ADR-0021: Herdr as an Optional Agent Runtime Practice

- Status: Accepted
- Date: 2026-09-23
- Extends: ADR-0019, ADR-0003, ADR-0007, ADR-0017
- Superseded by: None

## Context

project-init now separates logical Worker / Supervisor roles from concrete agent/runtime topology.

Herdr provides a useful external runtime surface for long-lived terminal agents. It can organize workspaces/tabs/panes, recognize supported coding agents, start agents in existing panes, prompt/read/wait on them, expose lifecycle state, and keep terminal processes alive across client detach.

Those capabilities map well to project-init's logical Supervisor role, especially when several independent Claude Code / Codex / OpenCode sessions are active.

However, Herdr state is still runtime-local state. Pane/workspace IDs, lifecycle labels, and terminal persistence are not sufficient substitutes for project-init's durable task/artifact/evidence/recovery state.

## Decision

### 1. Herdr is an optional Practice

Herdr is adopted as a supported agent/session runtime Practice, not as a constitutional dependency and not as the only Supervisor implementation.

The Operating Model must continue to work with:

- native subagents
- native agent-team/runtime features
- direct single-agent execution
- another external Supervisor/runtime
- remote/cloud workers

### 2. Herdr implements selected Supervisor capabilities

When Herdr is selected, it may implement or assist:

- Worker session creation
- agent start/discovery
- observe/read
- wait on lifecycle state
- human attach/takeover
- prompt delivery
- terminal/process organization
- transient worker registry

Project-init still owns the semantic requirements for:

- attempt class
- mutable ownership
- fencing
- immutable result identity
- validation evidence
- result admission
- durable recovery
- integration authority

### 3. Herdr lifecycle state is telemetry, not canonical organizational state

Herdr agent states such as `working`, `blocked`, `done`, `idle`, and `unknown` are operational signals.

They do not by themselves prove:

- acceptance criteria are satisfied
- result artifact is current
- validation passed
- a durable checkpoint exists
- integration is authorized
- the task is complete

In particular, `unknown` is not success, and `done` / `idle` mean the agent is ready for input rather than organizational completion.

### 4. Herdr identity is mapped to execution-attempt identity

A Herdr workspace/pane/agent name may be recorded as transient execution metadata.

The durable identity remains the project-init work unit / execution attempt / artifact relationship.

A durable attempt must remain reconstructable when Herdr-local IDs are lost.

### 5. Native subagents remain internal unless they need independent execution ownership

Herdr manages the top-level coding-agent process in a pane.

A Claude Code/OpenCode/Codex native subagent does not need its own Herdr pane merely because it exists.

Promote work to a separate Herdr-managed Worker only when independent lifecycle, mutable ownership, durable background execution, provider separation, or human observability justifies it.

### 6. Worktrunk and Herdr have separate responsibilities

Current preferred responsibility split:

- Worktrunk: Git worktree/workspace lifecycle Practice on supported WSL/Linux environments
- sandbox/runtime layer: mutable process/service/resource isolation
- Herdr: terminal/agent session lifecycle and observability
- project-init Supervisor semantics: routing, fencing, recovery, admission, authority

Do not replace Worktrunk with Herdr worktree commands merely because Herdr exposes worktree helpers. Such a replacement requires normal refinement evidence.

A Herdr workspace may point at a workspace/worktree materialized by the selected Git workspace Practice.

### 7. Herdr persistence is an optimization

Client detach/reattach persistence is useful transient continuity.

It is not the durable recovery boundary. A Herdr server restart, host loss, or runtime failure can still lose processes.

Durable attempts therefore continue to use project-init recovery/checkpoint semantics and immutable result identities.

### 8. Ambiguous prompt delivery is reconciled before retry

A timeout or prompt-stalled result is not proof that the prompt was not sent.

Before resending a consequential instruction, inspect the current agent/terminal state and reconcile side effects to avoid duplicate work or duplicated external actions.

## Consequences

### Positive

- independent coding-agent sessions gain a unified operational surface
- humans can keep only the active Worker visible while observing others by state
- a parent agent or script can coordinate other top-level agents without embedding terminal emulation
- Herdr can coexist with native subagents rather than replacing them
- detach/reattach improves local continuity

### Trade-offs

- another local runtime/tool must be maintained
- Herdr status detection may be imperfect or provider-dependent
- session-local IDs and state need explicit mapping to durable attempt identity
- external runtime automation can create duplicate prompts/actions if ambiguous failures are retried blindly

## Remove / re-evaluate

Re-evaluate or remove this Practice when:

- native agent runtimes provide equal or stronger cross-agent lifecycle/observability
- a standard agent control protocol replaces Herdr-specific adaptation
- Herdr lifecycle detection becomes unreliable for the selected agents
- maintaining the adapter costs more than the operational value
- project execution moves primarily to a remote control plane where Herdr adds no useful layer
