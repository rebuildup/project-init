# ADR-0024: Rust/Cargo worktree build output isolation and bounded cache reuse

- Status: Accepted
- Date: 2026-09-27
- Layer: Practice
- Refines: Mutable Ownership Safety, Progress
- Related: ADR-0013, ADR-0017, ADR-0019, ADR-0020, ADR-0022
- Superseded by: None

## Context

current release-driven profileでは、WSL/Linux上のmutable authoring workspaceをWorktrunkでmaterializeし、複数worktreeを並行利用できる。

Rust/Cargo projectでは各workspaceの `target/` がdependency artifact、incremental state、debug information、複数profile/targetの成果物を保持するため大きくなりやすい。worktreeごとに同じartifact setを再生成すると、host disk usageはactive worktree数に応じて増える。

ただし、容量削減だけを目的に複数のconcurrent mutable worktreeへ同じ `target-dir` または `build-dir` を直接共有することも標準解にはしない。

current Cargoではtarget directory全体を対象としたlockingが並列buildを直列化し得る。さらに2026年時点でも、異なるGit worktreeが同一build directoryを共有した場合にfingerprint / mtime等の相互作用から必要なrebuildを行わず、別worktree由来のartifactを実行し得るcorrectness issueが報告されている。

project-initの既存原則である「immutable/cacheable stateは共有できるが、concurrently-mutated build outputは隔離する」をRust/Cargoにも明示的に適用する必要がある。

## Decision

### 1. Cargo mutable build output is worktree-local by default

concurrentにbuildされ得るRust worktree間では、次を共有しない。

- Cargo `target-dir`
- Cargo `build.build-dir`
- `target/` へのsymlink
- incremental compilation state
- build-script / proc-macro / linker等が生成するmutable build artifacts

repositoryやuser configで全worktreeを単一の `CARGO_TARGET_DIR` へ向ける設定をcurrent defaultにしない。

Cargo 1.91+ の `build.build-dir` を利用する場合も、これは「共有build cache」ではなくintermediate artifact placement mechanismとして扱う。external directoryへ移す場合は少なくともworkspace pathごとに一意なdirectoryを使用し、そのlifecycle/cleanup ownershipを明示する。異なるmutable worktreeが同じbuild directoryを同時利用してはならない。

### 2. Share cacheable layers instead of target directories

worktree間で共有してよい標準候補は次とする。

- Cargo registry / git dependency download cache
- read-only toolchain cache
- compiler result cache such as `sccache`

`sccache` を採用するprojectでは、Cargoの `build.rustc-wrapper` または `RUSTC_WRAPPER` から利用する。repository-required local toolとして扱う場合はcurrent mise Practiceに従い、version/provisioningを再現可能にする。

parallel checkout / Git worktreeのabsolute path差でcache hitを失わないよう、compatibleなsccache versionでは `SCCACHE_BASEDIRS` / `basedirs` によるsource-path normalizationを検討する。ただしabsolute machine pathはrepository truthにせずhost/user/runtime configurationへ置く。

local sccache storageは無制限にしない。project/hostのdisk capacityとobserved cache effectivenessに応じてbounded cache sizeを設定する。同じlocal storageを複数の独立sccache serverから同時使用するとraceし得るため、同一`SCCACHE_DIR`では単一serverを共有するか、serverごとにstorageを分離する。sccache自体をbuild correctnessやartifact identityのSoTにはしない。

### 3. Seed target only through verified copy-on-write, never direct sharing

Worktrunkの `wt step copy-ignored` は、APFS / btrfs / XFS / ReFS等のreflink対応filesystemではgitignored fileをcopy-on-write cloneできる。これは複数worktreeが同一mutable directoryを共有する方式ではなく、各worktreeに独立pathを持たせたままinitial disk blocksを共有するため、条件が合えばRust `target/` のcold-start costとinitial disk amplificationを同時に抑えられる。

ただしext4 / NTFS等reflink非対応filesystemではfull copyになる。巨大な `target/` をfull copyすると容量問題を悪化させる。

したがってcurrent defaultは次とする。

- filesystem / Worktrunkがreflinkを実際に使用できることを確認できたhostでは、compatible base worktreeから `target/` をCoW seedすることを許容する
- Worktrunk output等で `(reflinked, no extra disk)` 相当を確認できないhostでは `target/` をcopy対象から除外する
- ext4 / NTFS等full-copyになるfilesystemでは `[step.copy-ignored] exclude = ["target/"]` を標準候補とする
- symlinkや単一 `target-dir` 共有へ置き換えてはならない
- seed後もCargo自身のfingerprint/rebuild判断を通し、copied artifactをcurrent sourceのvalidation evidenceとしてそのまま扱わない

`.worktreeinclude`を使う場合も、target inclusionはreflink capabilityを確認したproject/hostだけで有効化する。

### 4. Treat incremental compilation according to workspace lifetime

Cargo dev profileのincremental compilationはedit/rebuild latencyを下げる一方、worktree-local disk usageを増やし、incremental crateはsccache cacheabilityともtrade-offを持つ。

そのため一律にon/offを固定しない。

- long-lived interactive development checkout: Cargo defaultのincremental buildを維持することを標準候補とする
- short-lived / disposable agent worktree: reuse期間が短くdisk amplificationが大きい場合、`CARGO_INCREMENTAL=0` または相当設定を優先候補とする
- project-wide `[profile.dev] incremental = false` への変更は、代表的なbuild/rebuild timingとdisk usageを比較してから行う

incrementally compiled Rust crateはsccacheでcacheできない。そのためshort-lived agent worktreeでcross-worktree compiler-cache reuseを目的にsccacheを採用する場合、`CARGO_INCREMENTAL=0`を明示することを標準候補とする。

agent worktreeでincrementalを無効化する場合も、人間のprimary interactive checkoutまで機械的に同じ設定へ強制しない。

### 5. Use cargo clean as selective reclamation, not a build ritual

`cargo clean` をbuild/testの前後へ常時挿入しない。cache reuseを破壊し、容量問題をI/O/compile-time問題へ置き換えるためである。

disk pressureまたはstale artifact調査では、まず対象と効果を確認し、必要に応じて狭いcleanupから行う。

標準候補:

- `cargo clean --dry-run -v`: 削除対象の事前確認
- `cargo clean --doc`: 不要なdoc artifactだけを削除
- `cargo clean --release` / `cargo clean --profile <name>`: inactive profileを削除
- `cargo clean --target <triple>`: stale cross-target artifactを削除
- `cargo clean -p <package>`: 特定package artifactが明確な原因の場合だけ使用

full `cargo clean` は次のような場合に限定する。

- build cache corruption / stale artifact recovery
- toolchain/profile/build-modeの大きな変更後に旧artifactを保持する価値が低い
- active worktreeのdisk pressureが高く、再build costよりreclamation benefitが大きい
- externalized per-worktree build directoryを明示的にretireする

通常のworktree-local `target/` はworktree directoryとともに削除されるため、`wt remove` の直前にfull `cargo clean` を二重実行する必要はない。

Cargo global cache auto-GCはregistry/git等のglobal cacheを対象とし、current Cargoでは一般的なtarget build artifactのlifecycle管理を代替しない。

### 6. Reduce artifact production only with project evidence

容量削減のために依存featureやdebug informationを見直すことは推奨するが、genericな一括変更は行わない。

Rust project initialization / refinementでは必要に応じて次を調査する。

- `cargo tree -e features` / inverse feature inspectionで有効featureの理由を確認
- `cargo tree -d` でduplicate dependency versionを確認
- `cargo build --timings` でcostly compile unitsを確認
- virtual workspaceを含めappropriate resolver（resolver 2/3）が有効か確認
- direct dependencyでdefault featureが不要と証明できる場合だけ `default-features = false` + explicit featuresを検討
- project MSRVとdebugger requirementが許す場合、Cargo公式build-performance guidanceの`[profile.dev] debug = "line-tables-only"` + `[profile.dev.package."*"] debug = false` + opt-in full-debug profileを優先候補として計測する

libraryのdefault feature変更等、downstream/public behaviorへ影響し得る変更は単なるdisk optimizationとして扱わず、public contract / semver obligationsを評価する。

### 7. Third-party cleaners are optional host tooling

recursive cleaner / sweeper等のthird-party toolをproject correctnessの必須依存にしない。

maintained toolをhost-level convenienceとして使用してよいが、repository policyはbuilt-in Cargo lifecycleとworktree lifecycleだけでもrecovery可能でなければならない。unmaintained toolをcurrent defaultへ固定しない。

## Operational default

Rust/Cargo projectを検出したcurrent release-driven environmentでは、次をdefault shapeとする。

```text
worktree A -> local mutable Cargo build output
worktree B -> local mutable Cargo build output
worktree C -> local mutable Cargo build output

shared:
  Cargo registry/git download cache
  read-only toolchain cache
  bounded sccache compiler cache (when adopted)
```

これは「artifactを一切共有しない」方針ではなく、correctness-sensitive mutable graph/build stateとsafe cacheable compiler/dependency stateの境界を分ける方針である。

## Evidence and measurement

optimizationを導入する際は、少なくとも変更前後の代表的な次のsignalから必要なものを記録する。

- worktree / target disk footprint
- clean build time
- representative incremental rebuild time
- sccache hit/miss effectiveness when used
- required debug/test behavior
- CI/local parityへの影響

universalなGB thresholdやcache sizeをproject-init全体へ固定しない。host capacity、project size、worktree concurrency、lifetimeに応じてproject-specific thresholdを選ぶ。

## Consequences

### Positive

- parallel worktree間のCargo artifact correctness riskを増やさずにdisk amplificationを抑制できる
- dependency/compiler workの再利用をtarget-directory sharingから分離できる
- disposable agent worktreeとlong-lived human checkoutを同じoptimizationへ無理に揃えずに済む
- worktree removalでlocal build outputを自然に回収でき、reflink対応hostではcold-startも抑えられる
- future Cargo artifact GCへ移行しやすい

### Costs

- worktree-local Cargo metadata/artifactは一定量重複する
- sccacheにはhost-level cache lifecycleが必要
- incremental on/offやdebug/profile tuningはproject-specific measurementを要する
- shared target-dirほど単純な見かけ上の容量削減にはならない

## Rejected alternatives

### One shared target directory for all worktrees

Rejected as current default.

Cargo target-dir lockingによりparallel buildを直列化し得るうえ、divergent worktree間でartifact/fingerprint correctnessを保つ十分なguaranteeをcurrent Cargoが提供しているとは扱えない。

### Full cargo clean on every worktree/build lifecycle

Rejected.

rebuild costとcache churnが大きく、active development throughputを不必要に下げる。

### Disable all default dependency features globally

Rejected.

feature semanticsはdependency/packageごとに異なり、別dependencyから再enableされる場合もある。public behaviorを壊す可能性もあるためevidence-drivenに行う。

### Mandatory third-party sweeper

Rejected.

host convenience toolをorganizational correctnessへ昇格させず、maintenance healthに依存しないbaselineを維持する。

## Re-evaluate

次の場合はこのPracticeを再評価する。

- Cargoがconcurrent divergent worktree向けにcorrectness-safeなshared artifact storeを正式提供する
- Cargoがtarget/build artifactsを含むstable automatic GCを提供する
- target-dir locking / fingerprint semanticsが変わり、shared directoryのparallel correctnessが公式に保証される
- compiler cacheまたはremote build systemがcurrent approachより強いreproducibility / concurrency / storage guaranteesを提供する
- project/runtime modelがlocal mutable worktreeを使用しなくなる
