# ADR-0029: 能力の一覧と候補記録による、再現可能なSkill選定

- Status: Accepted
- Date: 2026-10-17
- Related: ADR-0001, ADR-0028
- Supersedes: None
- Superseded by: None
- Revised by: ADR-0030（writing-disciplineの担当をwriting-skillsへ移す）

## Context

初期化promptは「必要なSkillを導入する」と求めていたが、何をどう選ぶかの手順も、選んだ結果を再現する方法もなかった。

外部のスキル集（pstack、mattpocock/skills、obra/superpowers等）は、それぞれ自前の入口を持つ。pstackの `poteto-mode`、superpowersの `using-superpowers`、mattpocockの `ask-matt` がそれにあたる。特に `using-superpowers` は、少しでも当てはまるSkillを応答前に必ず呼ばせる。packを丸ごと併用すると、入口同士がroutingを奪い合い、同じ能力を担当するSkill（TDD、debugging、worktree運用など）が互いの指示を打ち消す。

固定の導入一覧にすると、一覧にない良いSkillを取りこぼし、評価もすぐ古くなる。一方で、毎回ゼロから探索すると、前回の評価が再利用されず、projectごとに選定がばらつく。

自作の `rebuildup/design-skills` と `rebuildup/writing-skills` は、project-initから参照されていなかった。

## Decision

### 1. 3つの層に分ける

- **能力の一覧**（`catalog/capabilities.tsv`）：必要な能力、それが必要になる条件、担当を1つに絞るか（`single` / `multi`）。変化が遅い。
- **候補の記録**（`catalog/candidates.tsv`）：Skillごとの出典、評価したrevisionと日付、読んだ深さ、採否と理由。許可リストではなく評価のキャッシュとする。記録にないSkillも探索して評価してよい。
- **projectの導入結果**：project-localに入れたSkill fileと `skills-lock.json`。projectのrepositoryにcommitする。

### 2. 入口はroot contractだけにする

外部packのrouterは `excluded` とし、導入しない。pack内の個別Skillは部品として `--skill` で導入する。手動起動（`disable-model-invocation: true`）のSkillは自動では起動しないので、採用時はroot contractの担当表にpathを書く。

### 3. `single` の能力は担当を1つにする

同じ能力に `default` を2つ置かない。代替は `alternative` として記録し、併用しない。

### 4. 導入はcopyしてcommitする

2026-10-17時点で確認した `skills` CLIの挙動は次のとおりだった。

- `skills experimental_install` は、`skills-lock.json` の `computedHash` を書き換えても警告なしに復元する。配布元の現在の内容を取得しており、内容の固定にはならない。
- 復元先は `--agent` を指定しても `.agents/skills/` だった。

このため、`skills-lock.json` だけでは再現性の根拠にしない。`--copy` で導入したSkill fileをcommitし、更新は `skills update` のdiffをPRで確認して取り込む。再配布を禁じるlicenseのSkillは、commitせずlockにだけ記録する。

### 5. 評価を還元する

project固有でない評価結果は、project-initの `catalog/` へPRで戻す。`reviewed_rev` と `reviewed_on` は、実際に読んだrevisionと日付にする。

### 6. 整合を機械的に検査する

`evals/policy-evaluation/skill-catalog-contract.sh` で次を確認する。

- 列の形式と値の語彙
- `single` の能力の担当が1つであること
- routerを担当にしないこと
- 自作Skillの記録漏れがないこと
- promptから `skill-selection` へroutingしていること

## Consequences

- 初期化agentは、能力の判定から始めて、記録と探索の両方から候補を選ぶ。選定理由は記録に残る。
- 外部Skillの中身がprojectのrepositoryに入るため、更新はdiffとしてreviewされる。repository容量は増える。
- 初回の記録は、多くが `listed` / `skimmed` の深さにとどまる。`evaluated`（比較評価済み）の候補はまだない。採用時にその場で読み直す運用で補い、比較評価の結果が出たら記録を更新する。
- design-skillsは82 Skillの網羅型で、descriptionから正しいSkillを選べるか検証されていないため、全体を `watch` とした。`design-intent` と `motion-system` だけを担当にしている。
- writing-skillsの `writing-discipline` は、project-init版と内容がずれた複製であるため、一本化までは `alternative` とした。

## Re-evaluate / remove

- `skills` CLIが、lockのhash照合と内容の固定に対応したら、copyしてcommitする運用を見直す。
- 候補の記録が大きくなり、TSVで扱いにくくなったら、形式を見直す。
