# ADR-0008: Weekly Release Sprints and Dependency-Aware Stacked Pull Request Delivery

- Status: Accepted
- Date: 2026-09-08
- Extends: ADR-0004, ADR-0007
- Superseded by: None

## Context

ADR-0004 established GitHub Issues / Projects as durable planning state, one semantic-version release branch per sprint, one top-level Issue per number-only ticket branch and ticket Pull Request, and early Draft PRs targeting the release branch.

Daily operation exposed two gaps.

First, hard dependencies between Issues were represented in planning state but not in the Git/PR topology. A dependent ticket normally had to wait for its prerequisite to merge into the release branch even when a reviewable immutable predecessor snapshot already existed. This serialized implementation and review unnecessarily.

Second, several ordinary GitHub delivery practices were described as recommendations rather than invariants. Under autonomous and multi-agent execution this allowed active branches without durable PR surfaces, incomplete assignee/reviewer/label metadata, and inconsistent sprint cadence.

The delivery model therefore needs to make dependency-aware stacked PRs explicit while strengthening the basic lifecycle around every durable branch and PR.

## Decision

### 1. Sprint cadence is one week by default

A normal sprint lasts one week.

Each sprint still maps 1:1 to one target semantic version and one release integration branch:

`release-<major>-<minor>-<patch>`

The sprint starts from a defined release baseline and ends at the planned weekly boundary unless an explicit release decision changes the date or scope.

Emergency patch releases and explicitly approved exceptional releases may use a shorter or longer cycle, but the normal planning cadence remains one week.

### 2. GitHub Issue dependency state remains canonical

GitHub Issues / Projects remain the durable source of truth for priority, target release, status, and dependency relationships.

A stacked PR is an execution and integration projection of a linear path in that dependency graph. Git branch topology does not replace Issue dependency metadata.

### 3. Independent tickets still target the release branch

A ticket with no hard predecessor in the same release uses the target release branch as its direct PR base.

```text
main
└─ release-x-y-z
   └─ 123
```

PR:

`123 -> release-x-y-z`

### 4. Hard dependency chains may use stacked PRs

When top-level Issues in the same target release form a meaningful linear hard-dependency chain, the dependent ticket MAY use its immediate predecessor ticket branch as its PR base.

```text
main
└─ release-x-y-z
   └─ 123
      └─ 124
         └─ 125
```

PR bases:

- `123 -> release-x-y-z`
- `124 -> 123`
- `125 -> 124`

All tickets in one stack share the same target release branch as the stack trunk.

The standard mapping remains:

`1 top-level Issue = 1 durable number-only ticket branch = 1 ticket PR`

Stacked PRs do not justify splitting one durable Issue into multiple durable PRs without another explicit reason.

### 5. Stack eligibility is constrained

Use stacked PRs only when:

- tickets are in the same repository
- tickets share the same target release
- a real hard dependency exists
- the dependency can be represented as an ordered chain for the stacked segment
- the predecessor has a reviewable immutable commit/snapshot suitable as a base

Do not force an arbitrary dependency DAG into one linear stack. The canonical Issue dependency graph may branch even when each GitHub PR stack is linear.

### 6. `stack-ready` allows safe dependent work before predecessor merge

A dependent ticket does not need to wait for its predecessor to merge into the release branch when a reviewable immutable predecessor snapshot exists.

Conceptually, dependency execution has three states:

- `blocked`: prerequisite implementation/contract is not yet usable
- `stack-ready`: a pinned reviewable predecessor snapshot exists and dependent work may start
- `integrated`: predecessor has merged into the target release branch

These are dependency semantics and do not require replacing the standard Project Status flow.

A worker started from a stack-ready predecessor MUST record the exact predecessor commit SHA or immutable snapshot identity used as its base.

### 7. Upstack changes invalidate affected validation

When a predecessor changes after review feedback, downstream stack branches are rebased or otherwise updated onto the new predecessor state in dependency order.

Any validation result is valid only for the exact validated SHA/snapshot. A downstream branch changed by cascading rebase/update MUST rerun all affected required validation before merge. Old green results are not reused for a different snapshot.

### 8. Every active durable work branch must have a Draft PR

Creating a durable work branch and opening its Draft PR are one operational start procedure.

GitHub cannot create a PR before the head differs from its base, so the canonical sequence is:

1. create the durable branch
2. make the first meaningful commit immediately
3. open the Draft PR immediately
4. do not continue active implementation without that Draft PR

A durable branch MUST NOT remain active as hidden work without a corresponding Draft PR.

This rule applies equally to coordinators, human contributors, implementation workers, and subagents. If a subagent is permitted to create a durable branch, it is also responsible for ensuring the Draft PR exists as part of the branch-start contract, or for returning control immediately to the Supervisor/Coordinator to create it before further implementation proceeds.

Ephemeral immutable worker refs/results that are not promoted to durable repository branches are not Pull Requests and are outside this rule.

### 9. Release branches also get an early Draft release PR

The release branch is created at sprint start. GitHub cannot open the release PR while the branch is identical to `main`, so the Draft release PR is opened immediately after the release branch first contains a meaningful integrated release difference.

The release Draft PR remains the durable release-level integration/review surface until release completion.

### 10. PR metadata is required operational state

When a PR is created, the creator/Coordinator MUST populate all applicable GitHub metadata rather than leaving the PR as an unclassified diff.

At minimum evaluate and set:

- linked Issue
- assignee / accountable owner
- requested reviewer(s) and CODEOWNERS-derived reviewers when applicable
- labels representing the repository's established taxonomy
- target release/version context
- stack predecessor/successor context when stacked
- acceptance criteria
- validation status/results
- known blockers/limitations

Metadata is maintained when scope, ownership, reviewer requirements, or stack position changes.

Do not invent labels or reviewers merely to fill fields. Use repository-established taxonomy, ownership rules, Issue context, and CODEOWNERS. If no meaningful reviewer exists, record that fact rather than silently omitting review expectations.

### 11. Draft and Ready have distinct semantics

Draft means implementation/integration is active and review context is durable; it is not a completion signal.

Move to Ready for review only after:

- acceptance criteria are implemented
- required ticket-level validation is complete for the current SHA
- blocking known problems are resolved or explicitly scoped out
- PR body and metadata match the current implementation
- required reviewers are requested
- target release / immediate stack predecessor staleness is handled
- stacked downstream branches have been reconciled when required

### 12. Merge follows dependency order unless an atomic stack merge is intentionally used

The normal stacked merge order is bottom-up from the earliest predecessor toward downstream tickets.

After each ticket PR is successfully integrated into its intended release/stack path, the linked Issue is closed and Project state is moved to Done according to the delivery policy.

If platform capabilities and repository policy allow a reviewed stack to land atomically, that MAY be used only when every included ticket satisfies its own acceptance criteria, required review, and current-SHA validation. The Coordinator then reconciles every included Issue/Project item explicitly.

### 13. Branch/PR creation is part of the agent execution contract

When an implementation worker/subagent may create a durable branch, the spawn/output contract must include enough information to construct and maintain its PR correctly:

- Issue identity
- target release
- immediate PR base / stack predecessor
- immutable base SHA
- branch identity
- expected Draft PR identity
- assignee/reviewer/label expectations

A worker must not create untracked durable branches as private execution state.

## Consequences

### Positive

- review latency can overlap with dependent implementation
- Issue dependency state and Git topology can reinforce each other without changing the canonical planning SoT
- every active durable branch has a visible review/integration surface
- agents cannot silently omit ordinary GitHub ownership/review/classification metadata
- weekly sprint cadence makes release planning and capacity boundaries predictable
- validation remains tied to immutable code identity after cascading stack updates

### Negative / Trade-offs

- stacked branches require disciplined rebase/update handling
- predecessor review changes may cause repeated downstream validation cost
- PR metadata maintenance adds operational work
- release branches cannot technically receive a PR until they differ from `main`, requiring the explicit first-difference exception
- a one-week default cadence may require explicit exceptions for emergency or unusually large releases

## Re-evaluation triggers

Re-evaluate when:

- GitHub stacked PR capabilities or merge semantics materially change
- the project adopts continuous deployment and release sprints no longer provide value
- stacked dependency chains create more rebase/review cost than parallelism benefit
- another durable work tracker replaces GitHub Issues / Projects
- repository ownership/review automation makes part of the manual metadata contract redundant
