# ADR-0014: Optional Linear Release Control Plane over GitHub Execution

- Status: Accepted
- Date: 2026-09-14
- Extends: ADR-0004, ADR-0008
- Superseded by: None

## Context

project-initのdelivery modelは、Gitをsource state、GitHub Issues / Pull Requestsをdurable implementation / review / dependency state、release branchをintegration stateとして扱う。

release-drivenな複数repository開発では、release goal / target date / health、cross-repository blocker、release-level checkpoint、portfolio viewをticket executionとは別の粒度で俯瞰したい。

GitHub IssueをLinear Issueへ全面同期すると、同じwork itemのpriority / status / dependency / acceptance criteriaが二重化し、canonical ownerが曖昧になる。Linearはticket trackerの置換ではなくrelease planning / control planeとして利用する。

## Decision

### 1. Linear integrationはoptional profileとする

Linearはproject-initの必須dependencyにしない。Linearが利用可能で、project/teamがrelease planningをLinearへ置く場合のみLinear profileをcompileする。利用しないprojectではGitHub Projects / repository documentationへfallbackする。

### 2. Source of Truthをfield ownershipで分離する

- released source state: Git `main`
- active release integration state: Git `release-x-y-z`
- implementation scope / acceptance criteria: GitHub Issue
- implementation dependency graph: GitHub Issue dependency metadata
- ticket review / validation / merge evidence: GitHub Pull Request / checks
- release integration evidence: release Pull Request
- release goal / target date / release-level health / portfolio grouping: Linear Project / Initiative
- release-level status update: Linear Project Update
- long-lived project knowledge: repository-controlled documentation

同じfieldをGitHubとLinearの両方で手入力してcanonicalにしない。GitHub Issueのtarget versionはticket branch / release trunk / stacked PR topologyを決めるexecution metadataとして維持し、Linear Projectのrelease identityと一致させる。

### 3. Default mappingは 1 release train = 1 Linear Project

Linear Projectは原則1つのversion-bearing release trainを表す。複数repositoryが同じversion / release date / release decisionを共有する場合は1 Projectでまとめてよい。独立version / cadenceならProjectを分ける。

Projectにはrelease goal、version、target date、health、release PR / repository / release docsへのresource link、release-level blocker / limitationを持たせる。

### 4. Linear IssueをGitHub Issueへ全面mirrorしない

GitHub Issue -> Linear Issueの全件同期をdefaultにしない。Linear Issueは、単一GitHub implementation ticketと1:1で表現しにくいcross-repository blocker、external dependency、release decision、distribution/signing/store review、non-code deliverable等に限定する。

code changeが必要な場合、canonical implementation scope / acceptance criteriaはGitHub Issueへ置き、Linear側はそのGitHub Issue / PRへlinkする。同じtechnical statusを両方へ複製して手動同期しない。

### 5. Linear Project progressはGitHub evidenceから更新する

Project UpdateはGitHub actual stateを根拠に、`onTrack / atRisk / offTrack`、merged / pending work、blocking PR / CI / external dependency、release gate state、next checkpointを要約する。PR本文、CI log、review discussionは転載せずcanonical evidenceへlinkする。

### 6. Milestoneはrelease-level checkpointに限定する

標準候補は `Scope frozen`、`Implementation complete`、`Release candidate verified`、`Released`。必要なものだけ使い、ticket groupingの代替にしない。Project Completedはactual release / distribution availability確認後を標準とする。

### 7. Cycleはdefaultでは使用しない

project-initでは通常1週間のrelease sprintとtarget versionが1:1で対応するため、Linear Cycleをduplicate planning containerとして必須化しない。1 releaseが複数planning windowを跨ぐ、複数Project間でcapacityを管理する、release cadenceと独立したiteration metricが必要な場合のみ使う。

### 8. Initiativeは複数releaseを束ねるgoalに使用する

Initiativeは単一releaseではなく複数Projectを束ねるproduct / roadmap goalに使う。上位groupingが不要な小規模projectでは作らない。

### 9. Agent accessはroleごとに最小権限化する

ChatGPT等のinteractive PM surfaceではLinear connector/pluginを利用してよい。external coding agentではLinear公式MCPをoptional capabilityとして利用できる。

- Coordinator / release manager: read-write MCP (`https://mcp.linear.app/mcp`)
- implementation worker: 原則Linear不要。必要ならread-only MCP (`https://mcp.linear.app/mcp/readonly`) を優先
- release integration agent: GitHub evidence確認後にProject health / updateをreconcile可能

認証情報やuser-global MCP設定をrepository truthにしない。repositoryにはLinearが利用可能な場合のbehavior contractだけを保持する。

### 10. Linear writeはGitHub evidenceを上書きしない

agentはLinear Project更新前にcanonical GitHub stateを確認する。PR未mergeなのにimplementation completeと推測する、CI failureをLinearだけでDoneにする、Linear statusからGitHub execution stateを推測する、GitHubとLinearで別dependency graphを独立管理する、という運用は禁止する。不一致はGitHub execution evidenceを優先してLinearをreconcileする。

### 11. Linear built-in coding sessionsはbaselineにしない

project-initはSupervisor-controlled isolated runtimeと `1 top-level Issue = 1 number-only branch = 1 ticket PR` / release-stack topologyをcanonical execution modelとして持つ。Linear coding sessionsを標準worker runtimeにはせず、branch / snapshot / validation / PR metadata contractを完全に満たせる場合だけadapterとして再評価する。

### 12. Loopsはoptional optimizationとする

Loopsはplan / AI credits / connector configurationへ依存するためbaselineにしない。利用する場合もrelease status summarizationやnotification等のderived automationに限定し、GitHub execution stateを置き換えない。

### 13. Project-local Skillでprogressive disclosureする

Linear profile採用projectでは `linear-release-control` Skillを生成・導入する。SoT boundary、Project / Initiative / Milestone / Cycle / Issueの使い分け、GitHub evidence -> Linear reconciliation、MCP role policy、release start / checkpoint / completion procedureを扱う。

通常implementation taskで無条件に読ませず、release planning / status / portfolio / blocker management時だけ読み込む。

## Consequences

### Positive

- release PR中心のGitHub workflowを変更せずLinearのplanning UXを利用できる
- GitHub IssueとLinear Issueの二重管理を避けられる
- Free planでも大量のmirrored Issueを作らず運用しやすい
- cross-repository release healthを1 Projectで俯瞰できる
- ChatGPT connectorとexternal coding-agent MCPの両方から同じcontrol planeを操作できる
- implementation workerへ不要なLinear write権限を渡さずに済む
- Linearを導入しないprojectも同じproject-init policyを利用できる

### Negative / Trade-offs

- LinearのIssue-derived automatic progressを最大限には利用しない
- Project health / updateはGitHub evidenceからreconcileする必要がある
- GitHub ProjectsとLinearを併用する場合はfield ownershipを明確にする必要がある
- Linearだけではcanonical source / execution stateを完全復旧できない

## Re-evaluation triggers

- LinearがGitHub release PR / dependency stateをlosslessにproject-level projectionできる
- GitHub側のplanning機能だけでrelease portfolio / health用途を十分に満たす
- Linear coding sessionsがproject-initのbranch / sandbox / PR lifecycle contractを直接設定可能になる
- Linearがportableなcanonical execution-state standardを提供する
