# ADR-0034: Explicit route resolution for delegated agents

- Status: Proposed
- Date: 2026-10-28
- Layer: Operating Model + Practice
- Extends: ADR-0019, ADR-0021, ADR-0025
- Related: rebuildup/project-init#132

## Problem

Supervisorがdelegationを選んでも、特定のharness / provider / budgetでの起動は保証されない。Herdrの`agent start --kind pi`は標準Piを起動し、dotfilesの`agent pi openrouter-free`とは同じ経路ではない。native subagentを選ぶとAPI契約・quota・独立監視の境界も失われる。会話で毎回providerを指定する運用は再現性がない。

## Decision

1. 1つのtask roleについて、spawn前に明示的なroute selection（supervisor / harness / provider key / fallback / native delegation permission）をresolveする。特定のproviderがConstitutionの要件にはならない。機械的taskへの不要なspawnも増やさない。
2. roleからprovider routeを選ぶproject-local configとprovider/model/authのcanonical sourceを分離する。current profileでは前者は`templates/agent-routing/`にある例示、後者はdotfilesの`config/agents.toml`と統一`agent` launcher。モデル名やsecretを二重管理しない。
3. external routeを必要とするroleのdelegationにはHerdr-managed top-level Workerを使う。短いnative research helperはそのroute要件がない場合だけ許可する。失敗・quota・認証欠落時にnative/別provider/paidへ切り替えることを禁止する。例外はユーザー認可のある明示的な再計画のみ。
4. Herdrのcanonical executable startはprovider-scoped launcherの代替ではない。Herdrでshell paneを作り、そこで`agent <harness> <provider>`を起動してagentを検知し、prompt/readする。runtime-specific hook/permissionは可能な箇所に設置し、指示書だけで実行強制できたと主張しない。
5. mutable ownershipはexisting workspace/fencing semanticsに従い、Herdr session lifecycleをcanonical resultにしない。launcherの起動成功もmodel/credential/worker acceptanceの証明にはならない。

## Verification / rollout

- 配布テンプレートはroutingのpositive/negative unit testsを持つ。既存projectへ初期化/reconcile時に必要な設定・entrypointを導入する。unconfigured roleはfail-closed。
- 対象マシンでHerdr/Pi/Infisical/provid​erのend-to-end model identityと認証を確認する。未確認ならreadyと宣言しない。
- Claude Codeの`Agent`/`Task` toolをexternal routeの代用にできないよう、適切なhooks/permissionsをproject-localに設定する。ただし任意shell execution経由の完全な強制にはsandboxなど別の境界が必要で、model指示だけでは十分でない。

## Consequences

- role設定の継続的保守と一時的なHerdr/agent path依存が生じる。
- 別providerへ無断で切り替えないため、quota枯渇時はworkerが停止する。これは意図した安全な失敗である。
- 参照実装のHerdr/Pi実機検証が完了するまで、このADRのruntime integrationは試験段階である。
