# ADR-0023: Infisical-First Application Secret Management

- Status: Accepted
- Date: 2026-09-23
- Extends: ADR-0017
- Classification: Current release-driven Operating Model / Practice
- Superseded by: None

## Context

application / service の環境変数・secret管理には、個人開発、複数人開発、複数agent、CI/CD、production runtimeをまたいで同じ運用モデルを維持できることが望ましい。

SOPS + age は encrypted secret-in-Git が明示的な要件である場合には有効だが、application env の標準として使うと、復号keyの配布、CIへの長期credential配置、workerごとのleast-privilege、team onboarding/offboardingが運用負担になりやすい。

一方でcentral secret managerを採用すると、Gitだけで全stateが完結しなくなる。さらにWeb UIを日常操作の必須surfaceにすると、人間とagentが扱うcontrol planeが増え、project-initのprogressive disclosureとagent-operable organizationに反する。

このため、secret valueのcentral SoTとrepository-controlled schemaを分離し、InfisicalをCLI-firstのreplaceable Practiceとして採用する。

current release-driven profileではInfisicalのcontrol planeとしてself-hosted instance `https://secrets.rebuildup.dev` を使用する。CLIのvendor default endpointへ依存するとfresh machineやsession失効時にmanaged Cloudへ誤接続し得るため、current provider Practiceではsite/API endpointをnon-secret metadataとして明示する。

## Decision

### 1. Application secret values use Infisical as the default canonical SoT

current release-driven profileでは、application / service のsecret valueの標準SoTをInfisicalとし、current default control planeを `https://secrets.rebuildup.dev` とする。

対象例:

- API key / OAuth client secret
- database credential
- auth/session secret
- external service credential
- deployment-specific confidential environment value

secret value自体はGit、Issue、PR、checkpoint、agent memory、generated documentationへ保存しない。

### 2. Secret schema remains repository-controlled

secret valueと、applicationが必要とするenvironment contractを分離する。

repository側には少なくとも次をdiscoverableに保つ。

- key name
- required / optional
- type / shape
- non-secret default
- environment applicability
- validation rule
- owning component

実装方法はproject stackに合わせてよく、typed env schema、config schema、`.env.example`、generated metadata等を使用できる。

fresh agentはsecret valueを読むことなく必要keyとvalidation contractを理解できなければならない。

### 3. CLI-first; Web UI is optional

通常workflowのprimary interfaceはInfisical CLIとする。

current default control plane:

```text
site: https://secrets.rebuildup.dev
api:  https://secrets.rebuildup.dev/api
```

current defaultで使用するsite/API URL、project ID、environment/path mapping等のnon-secret provider metadataを、project repositoryからdiscoverableにする。secret value、token、session、cookie、client secretは含めない。

human loginはcurrent default instanceを明示する。

```bash
infisical login --domain=https://secrets.rebuildup.dev
```

runtime commandは `INFISICAL_API_URL=https://secrets.rebuildup.dev/api` 等でtarget APIを明示し、Infisical Cloudのdefault endpointへ暗黙fallbackさせない。

標準local executionは、可能な限りsecretをdiskへmaterializeせず、runtime injectionを使用する。

```bash
INFISICAL_API_URL=https://secrets.rebuildup.dev/api \
  infisical run --env=dev --path=/backend -- <command>
```

tracked project bindingが既に存在するrepositoryでは、fresh setupのたびに `infisical init` で別projectを再選択しない。bindingが欠落・staleな場合だけreconcileする。

Web UIは次の用途に限定可能なoptional surfaceとする。

- inspection
- emergency administration
- onboarding
- access-control review
- manual recovery

agentが通常taskを完了するためにWeb UI操作を必須としてはいけない。

project / environment / path / identity / OIDC trust等のcontrol-plane configurationも、可能な範囲でCLI / official API / Terraform・OpenTofu等のautomationから再構築可能にする。Web UIだけに存在する未記録configurationをnormal operationの前提にしない。IaCを使う場合もsecret valueをpersistent stateへ保存しない。

### 4. Plaintext .env is not the canonical store

平文`.env`の常設を標準にしない。

tool compatibility等でexport/materializationが必要な場合:

- repositoryへcommitしない
- `.gitignore`等で明示的に除外する
- lifecycleをboundedにする
- command output / logs / checkpointへ値を残さない
- task完了後に不要なmaterialized copyを残さない

### 5. Machine access uses scoped identities

human user accountとmachine/agent identityを分離する。

Machine Identityはcurrent default self-hosted control plane上でproject / environment / path / operationの必要最小scopeへ制限する。

- generic implementation worker: secretなしをdefault
- secretが必要なworker: taskに必要なdev/test pathだけ
- deployment worker:対象environmentのdeploy pathだけ
- secret maintenance actor: explicit write scopeだけ

Supervisor / worker sandboxへhost-wide credentialを無差別にinheritさせない。

### 6. GitHub Actions prefers OIDC

GitHub ActionsからInfisicalへaccessする場合、利用可能ならGitHub OIDC + current self-hosted Infisical Machine Identityを標準とする。OIDC/clientは `https://secrets.rebuildup.dev` 側のidentityへ向け、managed Cloud側へ同名identityを二重canonical化しない。

- long-lived Infisical client secretをGitHub repository secretへ置く構成をdefaultにしない
- workflowには必要最小限の `id-token: write` とrepository read permissionを与える
- OIDC trustはrepository / branch / environment等のclaimsで可能な限り限定する
- generic CIへproduction secretを渡さない
- production secretはdeployment/release boundaryのjobだけへ限定する
- OIDCはworkflow sourceの改ざん防止を代替しない。secret-bearing workflowのbranch/environment/review boundaryを保護し、untrusted PR codeをsecret取得後のjobで実行しない

OIDCが利用できないruntimeではUniversal Auth等を使用できるが、static credentialは最小scope・bounded lifetime・rotation可能なfallbackとして扱う。

### 7. Secret values must not become durable agent evidence

agent / worker / reviewerはsecret valueを次へ保存してはいけない。

- Issue / PR body or comment
- commit message
- source code / fixture
- recovery checkpoint
- test artifact
- CI log
- chat-derived durable documentation

validation evidenceにはsecret valueではなく、key presence、schema validity、access result、redacted fingerprint、exit status等を使用する。

### 8. Provider-specific behavior stays below the Constitution

InfisicalはConstitutional invariantではない。

同等以上のguaranteeを持つproviderへ置換可能とする。

deviation例:

- NixOS / dotfiles / bootstrapでencrypted secret-in-Gitがexplicit requirement -> SOPS等
- offline-first environment
- external platformがstronger native secret storeを要求
- regulatory / hosting constraintでInfisicalを使用できない

deviation時も、least privilege、non-plaintext persistence、recoverability、schema discoverability、agent-safe evidenceを維持する。

### 9. Migration is explicit and verifiable

既存の`.env`、GitHub Actions Secrets、SOPS等から移行する場合:

1. secret name/schemaをinventoryする。値をIssue/PRへ転写しない
2. Infisical側へtarget environment/pathを作る
3. secret valueを移行する
4. consumerをruntime injection / scoped identityへ切り替える
5. current runtimeで検証する
6. old storeから不要なduplicateを削除する
7. 過去にplaintext exposureがあったsecretは必要に応じてrotateする

old store削除はconsumer切替とcurrent validationの後に行う。

## Consequences

### Positive

- 個人開発からteam/agent/CIへsecret modelを変えずに拡張できる
- GitHub Actionsへmaster decryption keyを置く必要がなくなる
- worker単位のleast privilegeを構成しやすい
- secret valueとenvironment contractを分離できる
- Web UIを日常workflowへ追加せずCLI中心で運用できる
- Infisicalをreplaceable Practiceとして扱うためtool lock-inを上位policyへ持ち込まない

### Negative / Trade-offs

- secret valueのSoTがGit外になる
- online accessとself-hosted Infisical control planeのavailabilityへ依存する
- DNS/TLS/application/database/backup/upgrade等のself-host運用責務を持つ
- initial project / identity / OIDC configurationが必要になる
- access-control driftはGit diffだけでは検出できないため別のreconciliationが必要になる
- emergency/offline workflowはprojectごとに明示する必要がある

## Verification

initializer / security review / CI reviewでは最低限次を確認する。

- secret valueがGitへcommitされていない
- repository-controlled env schemaから必要keyを発見できる
- plaintext `.env` がcanonical storeになっていない
- normal local executionがCLIから完結できる
- current default profileではprovider metadataが `https://secrets.rebuildup.dev` / `https://secrets.rebuildup.dev/api` を明示し、Cloud defaultへ暗黙fallbackしない
- project ID等のprovider pointerがrepository-controlled non-secret metadataとしてdiscoverable
- generic CIがproduction secretへaccessしない
- GitHub ActionsでOIDCが利用可能な場合、static Infisical credentialよりOIDCを優先している
- Machine Identity scopeがproject/environment/path/operationの必要範囲を超えていない
- agent/checkpoint/logへsecret valueが永続化されない
- migration後に不要なduplicate secret storeが残っていない
- Infisicalが利用できないprojectではexplicit deviationと同等以上のguaranteeが記録されている
