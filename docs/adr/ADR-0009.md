# ADR-0009: Cost-Aware GitHub Actions Without Weakening Quality Gates

- Status: Accepted
- Date: 2026-09-10
- Extends: ADR-0005
- Superseded by: None

## Context

ADR-0005 established that quality gates are compiled per project and that worker, ticket integration, and release gates may intentionally have different breadth and cost.

In practice, GitHub Actions usage can still grow rapidly even when every individual check is technically justified. Common causes include:

- the same commit receiving equivalent `push` and `pull_request` validation
- expensive Windows/macOS/native matrices running on every feature-branch update even when the changed surface is platform-independent
- comment/review-triggered automations allocating a runner before discovering that no explicit command was requested
- obsolete runs continuing after a newer commit supersedes them
- hung jobs relying on a large provider default timeout
- one-minute billing granularity making many tiny independent jobs more expensive than their wall-clock duration suggests
- optimization being attempted from workflow-run counts instead of actual job/runner usage

The wrong response is to weaken or disable required verification. CI exists to preserve deterministic delivery quality, and platform-specific validation may be essential for native or cross-platform products.

The policy therefore needs an explicit resource-efficiency invariant: preserve the required verification signal while avoiding duplicate, mistimed, or unnecessarily expensive execution.

GitHub billing and included-usage rules also change over time. Static prices or quota values are therefore unsuitable as repository policy constants.

## Decision

### 1. CI resource efficiency is part of quality design

A quality profile must treat CI execution cost, quota pressure, and latency as design constraints alongside correctness and coverage.

The objective is not "run fewer tests". The objective is:

> execute each required verification signal at the cheapest appropriate boundary, exactly as often as needed for the project's risk model.

### 2. Usage decisions require actual runner/job measurements

Do not infer cost from workflow-run count alone.

When Actions usage matters, evaluate at least:

- repository visibility
- triggering event and branch
- job count
- runner OS/architecture/label
- billed or observed job duration
- success/failure/cancelled/skipped state
- duplicate runs for the same commit SHA
- artifact/cache usage when storage is relevant
- current account/org/repository billing and included-usage model

A useful planning approximation is:

```text
expected CI usage ≈ trigger frequency × started jobs × billed duration × runner cost/weight
```

Exact billing semantics and prices must be checked against current official GitHub documentation rather than embedded permanently in this policy.

### 3. Equivalent `push` and `pull_request` validation must not be a default

Feature/ticket branches normally receive integration feedback through `pull_request`.

`push` should normally be reserved for responsibilities that are semantically distinct, such as:

- post-merge validation on `main`
- release-trunk validation
- tags/releases
- deployment or publish workflows

If both events execute the same full validation for the same commit, the duplication must be justified explicitly or removed.

This applies to independent and stacked PR topologies.

### 4. Separate fast PR feedback from expensive platform verification

The project should distinguish:

- fast representative PR gate
- change-sensitive platform/native gate
- release-wide compatibility gate

Windows/macOS/native/device/browser matrices are not removed merely because they are expensive. Instead, they should run where their signal is needed, for example when:

- relevant platform/native paths changed
- packaging/process/runtime behavior changed
- a release candidate or release trunk is being validated
- a manual full-verification command or label explicitly requests them
- scheduled compatibility verification is justified

Projects whose normal change risk genuinely requires every-platform verification on every PR may keep that policy, but it must be an explicit measured decision.

### 5. Reject unnecessary work before expensive runner allocation

Prefer filters that prevent unnecessary jobs from starting:

- workflow event/branch filters
- `paths` / `paths-ignore`
- job-level `if`
- lightweight preflight outputs feeding dependent expensive jobs when the decision cannot be expressed directly

Do not allocate a high-cost runner and rely on a later step to discover that the job should have been a no-op.

A preflight job is itself not free; do not add one when direct workflow filtering is sufficient.

### 6. Comment/review automations must gate explicit intent early

Automations driven by `issue_comment`, `pull_request_review_comment`, `pull_request_review`, or similar noisy event streams must not start substantive runner work for every event and defer trigger detection to an action step.

Where possible, job-level conditions should verify:

- explicit command/trigger phrase
- intended event type
- actor/permission requirements when relevant
- bot-generated noise exclusion

before the substantive runner executes.

### 7. Superseded feedback runs should be cancellable

For validation where a newer commit invalidates the value of an older run, configure `concurrency` with an identity tied to the same feedback stream and enable cancellation of superseded work.

Do not blindly apply cancellation to deployments, migrations, publishing, or other side-effecting operations. Those require their own idempotency and recovery semantics.

### 8. Job timeouts must reflect measured behavior

Each CI job should define a realistic timeout based on observed normal duration plus reasonable margin.

Large provider defaults are not a substitute for failure handling. Hung processes, deadlocks, unavailable services, and broken setup should stop within a bounded period.

### 9. Artifact/cache policy must target the actual bottleneck

PR/debug evidence and release deliverables may use different retention rules.

Do not upload artifacts that are not consumed, and do not keep ephemeral CI evidence longer than necessary.

Caches should be used when they measurably improve execution time or reliability.

Storage optimization and Actions-minute optimization are separate concerns and must not be conflated.

### 10. Budgets are a guardrail, not the primary optimization mechanism

For metered private-repository usage, account/org/repository budgets and alerts may be configured to bound unexpected spend.

The normal sequence is:

1. measure current usage
2. remove duplicate/unnecessary execution
3. preserve and reposition required expensive verification
4. observe an optimized baseline over a meaningful period
5. set budget with reasonable headroom
6. re-measure by job/runner when usage spikes

### 11. Self-hosted runners require a security decision, not only a cost decision

Moving work to a self-hosted runner may reduce hosted-runner usage, but it introduces host persistence and trust concerns.

Before adopting one, evaluate:

- untrusted code execution
- credential exposure
- host isolation
- persistence between jobs
- availability and maintenance
- recovery and patching

Self-hosting must not be treated as a mechanically free replacement for hosted CI.

### 12. The compiled quality profile records execution policy

When GitHub Actions is used, the project-local quality profile should record, where applicable:

- trigger semantics
- required checks
- runner/platform policy
- expensive/platform-specific gate conditions
- concurrency/cancellation policy
- timeout policy
- artifact retention policy
- repository visibility and current billing model references
- expected CI usage/cost model or budget guardrail

This keeps ordinary development agents from independently reconstructing CI policy on every task.

## Consequences

### Positive

- required verification remains intact while duplicate work is removed
- high-cost platform checks move to risk-appropriate boundaries instead of being silently deleted
- PR feedback becomes faster and more predictable
- billing/quota incidents are investigated with actual usage rather than workflow-count guesses
- comment-driven AI/automation workflows are less likely to consume resources because of unrelated bot activity
- CI cost policy becomes reproducible project state rather than account-side folklore

### Negative / Trade-offs

- quality-profile compilation requires knowledge of repository visibility and current billing semantics
- path-sensitive/platform-sensitive workflows are more complex than unconditional matrices
- some projects will still legitimately require expensive per-PR cross-platform validation
- usage models are estimates and must be recalibrated as the repository and provider pricing change
- aggressive cancellation or filtering can hide required signals if conditions are designed incorrectly

## Re-evaluation triggers

Re-evaluate this ADR when:

- GitHub materially changes Actions billing, included usage, runner pricing, or rounding semantics
- repository visibility changes
- a new platform/architecture target is added
- CI usage exceeds the compiled baseline materially
- expensive checks become sufficiently fast/cheap that the gate split no longer helps
- escaped regressions show that a check was moved too late in the delivery lifecycle
- the project adopts another CI provider or self-hosted runner model
