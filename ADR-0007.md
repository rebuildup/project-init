# ADR-0007: Durable Agent Interruption Recovery

- Status: Accepted
- Date: 2026-09-05
- Extends: ADR-0003, ADR-0004, ADR-0005, ADR-0006
- Superseded by: None

## Context

AI coding agents fail differently from ordinary developer processes.

A task may be interrupted by model/session context loss, IDE or terminal restart, agent process failure, container/VM destruction, parent-agent failure while child agents continue, network/provider failure, context-window exhaustion, or control-plane restart.

Vendor runtimes may provide native session/thread resume, but that state is not always portable, durable, or available after sandbox/provider loss. Treating the conversation transcript as the only resumable state causes large tasks to restart from scratch or forces the next agent to infer unfinished work from partially modified files.

Parallel agent execution adds additional failure modes:

- orphaned children after parent failure
- stale child results integrated after a newer execution has taken ownership
- two recovered agents continuing the same ticket simultaneously
- external side effects repeated after an ambiguous timeout
- validation results reused after the underlying code state changed

The project therefore needs a recovery model that does not depend on preserving the original model context.

## Decision

### 1. Conversation resume is an optimization, not the canonical recovery mechanism

Native thread/session/subagent resume may be used when available.

However, a fresh agent with no prior conversation must be able to reconstruct work from durable project state.

### 2. Recovery state is split into durable and transient layers

Canonical durable evidence includes:

- GitHub Issue and Project state
- target release branch
- ticket branch and Git commit graph
- Pull Request, review, and CI state
- repository-controlled design/ADR/Skills/docs
- immutable worker/subagent results
- durable structured recovery checkpoints

Transient optimization state includes native conversation IDs, agent IDs, local Supervisor state, shell history, IDE state, and in-memory model context.

Transient state must never be the only representation of unfinished work.

### 3. Long-running work emits structured recovery checkpoints

A checkpoint stores operationally necessary facts, not private chain-of-thought.

It should record enough information to reconstruct:

- task identity
- target release / ticket branch / PR
- base and checkpoint snapshot
- execution generation
- completed and next steps
- pending validation
- child-agent state
- integrated child results
- blockers
- external side effects
- decision/artifact references

The exact storage mechanism is project/runtime specific.

### 4. Soft and hard checkpoints are distinct

Soft checkpoints optimize same-host/same-sandbox recovery and may use local immutable Git refs, filesystem/container snapshots, Supervisor journals, or native session persistence.

Hard checkpoints form the provider-loss recovery boundary and must leave meaningful code/work state reachable from durable infrastructure such as Git/GitHub or another explicitly durable store.

Projects should choose checkpoint frequency according to acceptable recovery point objective rather than committing every trivial edit.

### 5. Recovery is deterministic reconciliation

A recovering agent does not guess what the previous agent was thinking.

It reconstructs current state from Issue/PR/Git/checkpoint data, reconciles children and external side effects, recreates the workspace from an immutable snapshot, re-evaluates validation, and continues only after the reconstructed state is internally consistent.

### 6. Parent-agent death does not automatically destroy child work

Child lifecycle belongs to the Supervisor/control plane rather than the parent model process.

When safe, children continue or remain discoverable after parent failure. A recovered parent/coordinator reconciles running/completed/failed/orphaned children and consumes only valid immutable results.

### 7. Execution generations prevent split-brain continuation

Each resumable task has an execution lease/generation or equivalent fencing mechanism.

Recovery advances ownership. Results or side effects from stale generations must not be integrated automatically.

This prevents an old agent that reconnects after a network partition from racing the recovered agent.

### 8. External side effects require idempotent recovery semantics

Operations outside Git such as deploys, migrations, publishing, releases, cloud mutation, notifications, and cost-producing operations must be treated as potentially ambiguous after interruption.

Where supported, use idempotency keys. Record durable intent and resulting remote identifiers around consequential operations. On recovery, inspect actual remote state before retrying.

A timeout or missing response is not evidence that the operation did not occur.

### 9. Validation state is tied to a code snapshot

Partial validation success is not equivalent to a complete gate pass.

Recovery records distinguish completed, failed, and not-run checks. Integration/release success from an older code snapshot must not be reused blindly after code changes.

### 10. Context exhaustion is handled as planned handoff

Approaching context limits should trigger structured state externalization before failure.

The handoff stores concise objective, accepted decisions, relevant references, current checkpoint, completed work, next work, validation state, and blockers. It does not attempt to preserve full conversational reasoning.

### 11. Recovery capability should be tested

Where practical, projects should periodically stop an agent/sandbox intentionally and verify that a fresh agent can resume from durable state without duplicate mutation or lost child results.

Recovery/chaos drills may be incorporated into infrastructure verification for projects that rely heavily on autonomous agents.

## Consequences

### Positive

- work survives model/context/session replacement
- provider and sandbox failure no longer imply full task restart
- parent crashes do not automatically discard child-agent progress
- duplicate continuation can be fenced
- ambiguous external side effects are handled safely
- context compaction becomes explicit handoff rather than hidden conversational loss
- a different vendor/model can continue the same ticket from project state

### Negative / Trade-offs

- checkpoint generation and persistence add overhead
- recovery metadata needs schema/version maintenance
- durable checkpoints may add Git/object-store traffic
- execution leases/generations require Supervisor support
- side-effect journaling requires integrations to expose reliable identifiers/idempotency where possible
- frequent hard checkpoints can increase branch/history noise unless implemented carefully

## Invariants

- session resume is optional; durable reconstruction is required
- no recovery record contains secrets or private chain-of-thought
- a fresh agent can identify current task, snapshot, next step, validation state, and blockers
- stale execution generations cannot integrate results normally
- child results are immutable and independently recoverable
- ambiguous external side effects are reconciled against remote state before retry
- recovery does not silently downgrade required quality gates

## Re-evaluation triggers

Re-evaluate when:

- a broadly portable agent-session protocol makes context/state migration durable across vendors
- Supervisor standards provide native persistent task graphs and fencing
- Git is no longer the primary durable source/integration mechanism
- sandbox providers guarantee durable suspend/resume semantics strong enough to replace current checkpoint layers
- recovery metadata overhead becomes a major development bottleneck
