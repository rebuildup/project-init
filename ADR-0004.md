# ADR-0004: GitHub Ticket-Driven Agile Delivery and Cross-Platform Local Runtime

- Status: Accepted
- Date: 2026-09-05
- Extends: ADR-0003
- Superseded by: None

## Context

ADR-0003 established isolated worker runtimes, immutable snapshot/result transfer, Supervisor-controlled lifecycle, and PR-oriented top-level integration.

Two additional requirements are needed for daily development:

1. Work state must remain durable and inspectable even when many agents execute concurrently. Local branches and Supervisor state alone are insufficient for sprint planning, prioritization, blocked work, review state, and release planning.
2. The local host is not fixed. Development must work on macOS/Apple Silicon as a first-class target while remaining compatible with Windows 11 + WSL2 and Linux/NixOS. Host-specific setup must not become hidden project state.

The initialization prompt is intentionally comprehensive, but ordinary agent sessions should not reload the entire initialization policy. Operational rules need a smaller progressive-disclosure form.

## Decision

### 1. GitHub Issues are the durable planning unit

Substantial independent work is represented by a GitHub Issue.

An Issue should contain, when relevant:

- objective / user-visible outcome
- acceptance criteria
- scope / non-scope
- dependencies / blocked-by
- priority
- size / estimate
- area / component
- sprint / iteration
- target release / milestone

Ephemeral research or nested worker subtasks do not need individual Issues. They may remain Supervisor tasks attached to a durable parent Issue.

### 2. GitHub Projects is the canonical work board

When available, GitHub Projects is the canonical board for work state.

Default state model:

`Backlog -> Ready -> In Progress -> In Review -> Done`

Recommended fields:

- Priority
- Size
- Iteration / Sprint
- Area / Component
- Target Release

WIP is bounded by real capacity. Ready tickets are selected according to dependency and capacity rather than unlimited concurrent start.

### 3. Development is sprint/iteration oriented

Each sprint has an explicit goal and timebox.

The standard cycle is:

1. define sprint goal
2. select Ready Issues
3. resolve dependency graph
4. allocate human/agent capacity
5. run isolated workers in parallel
6. review and verify through PR/CI
7. move completed work to Done
8. re-plan unfinished work explicitly

When a release date exists, sprint planning is connected to release/milestone goals.

### 4. One top-level Issue normally maps to one integration branch and one PR

Branch naming must contain the Issue number and a short slug.

Canonical pattern:

`issue/<issue-number>-<short-slug>`

Examples:

- `issue/123-add-oauth`
- `issue/418-fix-calendar-race`

Alternative branch prefixes may be used only when required by repository conventions, but the Issue number remains mandatory for normal ticket work.

Nested worker branches/refs are ephemeral implementation details and do not need this naming convention unless they are pushed as durable GitHub branches.

### 5. Open a Draft PR early

After an Issue begins and the integration branch has a meaningful initial commit, open a Draft PR early rather than waiting until implementation is nearly complete.

The Draft PR becomes the durable integration surface for:

- Issue linkage
- visible implementation progress
- CI feedback
- reviewer context
- agent/human discussion
- change scope inspection

The PR should link its Issue and use `Closes #<issue-number>` when merge should close the ticket.

Move the PR from Draft to Ready for review only when:

- Issue acceptance criteria are implemented
- required integration validation is complete
- known blocking problems are resolved or explicitly scoped out
- PR description reflects the current implementation

### 6. Merge is the Done boundary

A ticket does not become Done merely because a worker reports success.

Done normally requires:

- acceptance criteria satisfied
- required CI/checks green
- blocking review resolved
- canonical-base staleness handled
- PR merged
- Issue closed
- Project status updated

### 7. The full initialization prompt is compiled into short project-local Skills

The initialization prompt remains intentionally comprehensive.

Normal sessions should use concise project-local Skills instead of rereading it.

Default operational Skills:

- `parallel-orchestration`
- `sandbox-runtime`
- `github-delivery`
- `quality-gate`

The root agent file only points to these Skills and contains always-on invariants.

### 8. macOS/Apple Silicon is a first-class local host

Apple Silicon `arm64` is treated as a first-class architecture.

Portable Web/backend tasks should normally execute in Linux sandboxes on macOS as well as on Windows/WSL, reducing drift from Linux CI/remote execution.

Apple-native tasks that require Xcode/iOS/macOS tooling may use macOS-native workers, while retaining per-worker workspace isolation and immutable result semantics.

Docker Desktop is not a mandatory dependency. The actual local container/VM runtime is selected at initialization time based on current support and project requirements.

### 9. Windows + WSL2 remains a first-class host

Linux-oriented repositories should normally live in the WSL Linux filesystem rather than a Windows-mounted path for high-frequency build/watch workloads.

WSL is not itself an agent-isolation boundary. Multiple implementation workers inside WSL still require separate container/VM/sandbox environments.

Supervisor/runtime adapters hide Windows-host vs WSL/container port-forwarding differences where practical.

### 10. Host/provider differences must not alter project semantics

The repository should reuse the same declarative environment definition across macOS local, WSL/Linux local, CI, and remote providers where practical.

Architecture-sensitive differences such as `arm64` local vs `x86_64` remote/CI must be validated instead of ignored.

## Consequences

### Positive

- active work remains recoverable and visible independently of agent runtime state
- sprint/release progress can be managed using GitHub-native durable objects
- Draft PRs expose integration and CI problems earlier
- Issue-numbered branches make branch purpose traceable without hidden context
- ordinary agents consume short Skills instead of a large initialization prompt
- macOS migration does not require changing the project execution model
- WSL remains supported without becoming an implicit isolation mechanism
- local and remote worker environments stay conceptually interchangeable

### Negative / Trade-offs

- more GitHub metadata and lifecycle transitions must be maintained
- very small fixes may incur unnecessary Issue/PR ceremony if the project applies the policy mechanically
- Draft PRs increase the number of visible open PRs
- multi-architecture compatibility can increase build/test cost
- provider abstraction requires maintenance across host environments

## Re-evaluation triggers

Re-evaluate when:

- GitHub Projects or Issue/PR workflow capabilities materially change
- another durable work-tracking system replaces GitHub Projects
- development no longer uses sprint/iteration planning
- local development becomes macOS-only or Windows-only
- agent runtimes provide portable host-independent sandbox semantics directly
- the Skill standard changes enough to make the current split obsolete
