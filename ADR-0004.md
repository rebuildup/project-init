# ADR-0004: GitHub Ticket-Driven Release Sprint Delivery and Cross-Platform Local Runtime

- Status: Accepted
- Date: 2026-09-05
- Extends: ADR-0003
- Superseded by: None

## Context

ADR-0003 established isolated worker runtimes, immutable snapshot/result transfer, Supervisor-controlled lifecycle, and PR-oriented top-level integration.

Daily development additionally needs a durable agile delivery model that remains understandable while many agents run concurrently.

The previous draft used Issue-numbered branches with descriptive slugs and treated each Issue PR as targeting `main`. That leaves branch names unnecessarily verbose and does not model sprint integration explicitly.

The desired workflow is release-oriented:

- each sprint targets a concrete semantic version
- ticket branches are only identifiers, not descriptions
- ticket PRs integrate into the current release branch
- `main` represents released/integrated source state
- Issue and PR descriptions carry human-readable context

The local host is also not fixed. Development must work on macOS/Apple Silicon as a first-class target while remaining compatible with Windows 11 + WSL2 and Linux/NixOS. Host-specific setup must not become hidden project state.

The initialization prompt is intentionally comprehensive, but ordinary agent sessions should use smaller progressive-disclosure Skills.

## Decision

### 1. GitHub Issues are the durable planning unit

Substantial independent work is represented by a GitHub Issue.

Issue title/body are written in Japanese by default.

An Issue should contain, when relevant:

- objective / user-visible outcome
- acceptance criteria
- scope / non-scope
- dependencies / blocked-by
- priority
- size / estimate
- area / component
- target version
- release date

Ephemeral research or nested worker subtasks do not need individual Issues. They may remain Supervisor tasks attached to a durable parent Issue.

### 2. GitHub Projects is the canonical work board

When available, GitHub Projects is the canonical board for work state.

Default state model:

`Backlog -> Ready -> In Progress -> In Review -> Done`

Recommended fields:

- Priority
- Size
- Target Version
- Area / Component
- Blocked / dependency

WIP is bounded by real capacity. Ready tickets are selected according to dependency and capacity rather than unlimited concurrent start.

### 3. A sprint is identified by its target release version

A sprint is not named by an arbitrary sequence number.

Each sprint targets one semantic version and owns one release integration branch.

Canonical release branch pattern:

`release-<major>-<minor>-<patch>`

Examples:

- `release-0-1-0`
- `release-0-2-0`
- `release-1-0-0`

Hyphens are used instead of dots in the Git branch name.

The release branch is created from `main` at sprint start and acts as the integration line for all tickets selected into that release.

Conceptually:

```text
main
└─ release-x-y-z
   ├─ 123
   ├─ 124
   └─ 125
```

### 4. `main` represents released/integrated source state

Normal ticket PRs do not target `main` directly.

Ticket PRs target the current release branch.

After the release branch passes its release-level quality gate, a release PR is opened:

`release-x-y-z -> main`

Merging that PR advances the released source state.

### 5. One top-level Issue normally maps to one number-only branch and one PR

A durable ticket branch is named using only the GitHub Issue number.

Canonical pattern:

`<issue-number>`

Examples:

- `123`
- `418`
- `1024`

Do not add `issue/`, a slug, work type, or title to the standard ticket branch name.

The Issue number already provides the durable identity. Human-readable meaning belongs in the linked Issue and PR.

Nested worker branches/refs are ephemeral implementation details and do not need this naming convention unless promoted to durable GitHub branches.

### 6. Open a Draft PR early

After an Issue begins and the ticket branch has a meaningful initial commit, open a Draft PR early rather than waiting until implementation is nearly complete.

The PR base is the target `release-x-y-z` branch.

The Draft PR becomes the durable integration surface for:

- Issue linkage
- visible implementation progress
- CI feedback
- reviewer context
- agent/human discussion
- change scope inspection

PR title/body and review discussion are written in Japanese by default.

The PR should reference its Issue explicitly, for example `Issue: #<issue-number>`. Because the PR targets a non-default release branch, closing keywords such as `Closes #<issue-number>` must not be relied on to close the Issue when this PR merges.

Move the PR from Draft to Ready for review only when:

- Issue acceptance criteria are implemented
- required ticket-level validation is complete
- known blocking problems are resolved or explicitly scoped out
- PR description reflects the current implementation
- target release branch staleness/conflicts are handled

### 7. Ticket merge is the Issue Done boundary

A ticket does not become Done merely because a worker reports success.

Done normally requires:

- acceptance criteria satisfied
- required CI/checks green
- blocking review resolved
- release-branch staleness handled
- ticket PR merged into the target release branch
- linked Issue explicitly closed after the merge succeeds
- Project status updated to Done

The merge/close transition is an explicit workflow step: after confirming the ticket PR was merged into the intended `release-x-y-z`, the Coordinator or delivery automation closes the linked Issue and moves its GitHub Project item to Done. Do not depend on PR closing keywords for this non-default-base merge.

The Issue does not need to wait for `release-x-y-z -> main` to be considered Done. Its durable delivery boundary is integration into the target release branch followed by explicit Issue close/Project update.

### 8. Release completion has its own integration boundary

Before release, run the full applicable quality gate on the release branch.

The release PR from `release-x-y-z` to `main` should summarize:

- release goal
- included Issues / ticket PRs
- breaking changes
- migration notes
- full validation evidence
- known limitations
- version/release metadata

The release PR title/body are written in Japanese by default.

After merge, `main` represents the completed release state.

### 9. The full initialization prompt is compiled into short project-local Skills

The initialization prompt remains intentionally comprehensive.

Normal sessions should use concise project-local Skills instead of rereading it.

Default operational Skills:

- `parallel-orchestration`
- `sandbox-runtime`
- `github-delivery`
- `quality-gate`

The root agent file only points to these Skills and contains always-on invariants.

### 10. macOS/Apple Silicon is a first-class local host

Apple Silicon `arm64` is treated as a first-class architecture.

Portable Web/backend tasks should normally execute in Linux sandboxes on macOS as well as on Windows/WSL, reducing drift from Linux CI/remote execution.

Apple-native tasks that require Xcode/iOS/macOS tooling may use macOS-native workers, while retaining per-worker workspace isolation and immutable result semantics.

Docker Desktop is not a mandatory dependency. The actual local container/VM runtime is selected at initialization time based on current support and project requirements.

### 11. Windows + WSL2 remains a first-class host

Linux-oriented repositories should normally live in the WSL Linux filesystem rather than a Windows-mounted path for high-frequency build/watch workloads.

WSL is not itself an agent-isolation boundary. Multiple implementation workers inside WSL still require separate container/VM/sandbox environments.

Supervisor/runtime adapters hide Windows-host vs WSL/container port-forwarding differences where practical.

### 12. Host/provider differences must not alter project semantics

The repository should reuse the same declarative environment definition across macOS local, WSL/Linux local, CI, and remote providers where practical.

Architecture-sensitive differences such as `arm64` local vs `x86_64` remote/CI must be validated instead of ignored.

### 13. Language policy separates code history from collaboration context

- source code: English
- commit messages: English
- internal development documentation: Japanese
- GitHub Issue title/body: Japanese
- Pull Request title/body/review discussion: Japanese

Branch names carry identifiers/version state only and are not used as prose documentation.

## Consequences

### Positive

- branch names remain very short and machine-friendly
- Issue/PR contain the human-readable context instead of duplicating it in refs
- the sprint integration line is explicit
- `main` has a clear semantic meaning as released/integrated source state
- many Issue PRs can run concurrently against one target release
- release-level regression testing occurs before advancing `main`
- sprint planning and version planning become the same durable concept
- ordinary agents consume short Skills instead of a large initialization prompt
- macOS migration does not require changing the project execution model
- WSL remains supported without becoming an implicit isolation mechanism

### Negative / Trade-offs

- a release branch is an additional long-lived integration ref during each sprint
- ticket branches such as `123` are intentionally meaningless without GitHub context
- tickets integrated early into a release branch may need follow-up changes before release
- release branch divergence from `main` must be monitored
- release PRs add a second integration layer
- ticket PR merge requires an explicit Issue-close/Project-Done transition because the PR base is not the default branch
- multi-architecture compatibility can increase build/test cost

## Re-evaluation triggers

Re-evaluate when:

- GitHub Projects or Issue/PR workflow capabilities materially change
- another durable work-tracking system replaces GitHub Projects
- development no longer uses release-oriented sprint planning
- the project adopts continuous deployment where a sprint release branch becomes counterproductive
- the branching model causes unacceptable integration delay or merge complexity
- local development becomes macOS-only or Windows-only
- agent runtimes provide portable host-independent sandbox semantics directly
- the Skill standard changes enough to make the current split obsolete
