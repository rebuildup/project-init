# System Quality

対象は変更後のシステム全体であり、差分の小ささや追加物の少なさを先に目的にしない。Skill、設定、スクリプト、参照、検査、受理経路もシステムの振る舞いを決めるコードベースとして扱う。

## 成立させる能力

1. **要求保存**: 対象、現状の観測事実、新要求、維持条件、根拠のある制約を分ける。各成立条件を根拠へ対応付ける。既存構造や実装の都合を維持義務へ昇格させない。
2. **全体再構成**: 現状からの修正案と、要求から状態・責務・境界を構成する案を扱う。既存コードは振る舞い・移行条件の証拠であり内部構造の固定条件ではない。
3. **既知欠陥の排除**: 実装前に[アンチケース](references/anti-cases.md)を対象へ適用する。適用条件と根拠を確定し、既存違反の除去と再導入の拒否を一体で実現する。
4. **改善の構成**: 禁止事項に違反しない実装にも[改善関係](references/improvements.md)を適用する。単一変換だけでなく、状態・境界・利用側の複合変更を候補にする。
5. **保証**: 要求充足、個別候補の優位、既知違反の排除、最適性を別々に確立する。保証の論理は[契約](references/contract.md)に従い、具体的な検証は`correctness-assurance`へ接続する。
6. **独立した強制**: Skillの読み込み、自己申告、レビューの好評価を品質成立の証拠にしない。`quality-gate`が実成果物を検査し、`policy-evaluation`が拒否能力と改善能力を別々に評価する。

## 新規実装と機能追加で全体を整合する

機能を小さく実装してから後日まとめてリファクタリングする流れを品質戦略にしない。実装前に変更先の所有責務・同階層・利用側を調べ、**追加後の全体の完成形**を決める。新規ファイルを隣に積む案と、既存側も統合・再配置する案を比較する。

追加時点で影響する既存API・import・テスト・配置・名前を揃え、不要になった旧方式を撤去する。全repoの無関係な負債を修正する必要はないが、**今回生む不整合**を「後で整理する」Issue・メモで受理しない。新規コードの名前・階層は [code-naming](../code-naming/SKILL.md) に従う。兄弟entry数や共通prefixは調査の手掛かりであり、意味に基づく判断・framework規約・外部契約を優先する。

## 実行

要求と制約を先に固定する。入力範囲・失敗条件・並行性・互換性・性能・将来の拡張条件は根拠があるものを具体化する。未指定の未来を勝手に仕様化しない。根拠不足は調査し、実装を楽にする縮小で埋めない。

アンチケースと改善関係ごとに、適用箇所・条件・保存する性質・反例・検証経路を決める。適用しない理由は対象の事実で説明する。対象を調べていない状態を「該当なし」にしない。文書の追加自体は排除の実装ではない。

設計上の差が現れる範囲を実行可能にし、同じ要求・入力・環境で比較する。小さい試作の優位を全体へ一般化せず、移行、失敗経路、実行コスト、拡張時の波及まで確認する。候補数や多数決で設計の正しさを決めない。

採用後は利用側を移行し、不要になった旧API・重複状態・例外・設定・説明・テストを撤去する。互換性のため残す部分は実在する外部義務へ対応付ける。「後で整理する」で二方式を恒久化しない。

既存の型・言語機能・解析器で不正な状態や依存を排除する。残る違反は実成果物に対する検査にする。正当なケースも通し、全拒否を品質向上と誤認しない。

[scripts/challenge.mts](scripts/challenge.mts)は、隔離コピーへ既知の変更を加え、実検査の拒否／受理を確認する。使用条件とJSON形式は[ツール契約](references/challenge.md)を読む。プロセス異常を違反検出として数えない。ツールは任意プログラムの安全なsandboxではない。

## 完了と次の変更

- 要求・維持条件と、変更後全体の成立証拠が対応している。
- 適用したアンチケースについて、修正箇所と再導入の拒否範囲が明確である。
- 新規機能を最初から適切な責務・名前・階層に実装し、変更により影響する既存側も同じ変更で整合している。
- 比較から実証された改善が取り込まれ、旧構造の撤去まで整合している。
- 未処理の反例、実証された劣位、必須の未検証条件が残れば、その責務は未完了である。
- 違反不在、探索した候補での最良、全体最適を区別する。最適性を要求された場合、検査合格で代替して完了しない。
- 新要求が入れば適用条件と比較関係を再確認する。過去に採用した構造や禁止事項を永久の制約にしない。

このSkillは設計判断を助ける。遵守の保証はしない。機械化されていない意味判断を、文書や台帳の存在で強制済みに見せない。
