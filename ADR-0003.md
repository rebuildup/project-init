# ADR-0003: Isolated Multi-Agent Execution and Supervisor-Controlled Integration

- Status: Accepted
- Date: 2026-09-05
- Revises: ADR-0001 sections 7 and 8
- Extended by: ADR-0004
- Superseded by: None

## Context

ADR-0001 adopted local `main`, prohibited worktrees, and attempted to obtain parallelism through disjoint file ownership with serialized commits.

That model isolates repository paths but does not isolate execution state. Multiple agents can still collide through ports, databases, Redis, queues, dev servers, generated runtime state, container resources, credentials, and other mutable host-level state. It also makes the shared local working directory and Git index part of coordination, which weakens the Source of Truth once several agents are active.

A second issue is nested delegation. If a parent agent spawns a child while holding uncommitted work, the child needs a precise, reproducible view of the parent's state. Sharing the parent's dirty filesystem makes the delegation protocol implicit and creates new races.

The desired system should support local-first operation, inexpensive on-demand remote execution, nested subagents, deterministic integration, and recovery from canonical Git state without depending on a particular provider.

## Decision

### 1. Git is the canonical Source of Truth; a local directory is not

Canonical task state is defined by Git remote/ref/SHA plus repository-controlled environment definitions and durable task/dependency metadata.

Each implementation task records or can derive an immutable base snapshot such as `base_sha`.

### 2. Every implementation worker receives an isolated mutable execution environment

The default unit is:

`1 implementation worker = 1 isolated workspace/runtime`

The environment must isolate writable workspace and the mutable runtime resources required by the project, including ports/network routing, databases, caches/queues, process state, and mutable build/test output.

Immutable caches and read-only toolchain state may be shared.

### 3. Worktree is not an isolation boundary

Git worktree is no longer globally prohibited.

A worktree may be used inside an already isolated sandbox as an implementation detail. However, worktree-only separation must never be treated as sufficient execution isolation.

### 4. Agent lifecycle is controlled by a Supervisor outside worker sandboxes

The Supervisor is responsible for sandbox lifecycle, agent spawn/wait/cancel, snapshots, resource/depth budgets, credential injection, result collection, and integration support.

Workers must not receive unrestricted host Docker sockets, root-equivalent host capability, or master cloud credentials merely so they can create child environments themselves.

### 5. Parent-to-child delegation uses immutable snapshots

A parent agent does not implicitly share its dirty working tree with a child.

Before delegating state that is not already represented by a canonical commit/ref, the system creates an immutable checkpoint such as an ephemeral Git commit/ref or content-addressed filesystem/container snapshot.

### 6. Child-to-parent transfer uses immutable results

Implementation workers return an immutable result, normally a Git commit/ref or equivalent diff, together with summary and validation evidence.

Children do not directly mutate the parent workspace.

### 7. Top-level task integration is PR-oriented

Independent top-level tasks use independent integration branches/PRs.

Nested workers do not need individual GitHub PRs; their immutable results can be integrated into the top-level task branch by the Coordinator/Supervisor.

Multiple agents must not concurrently mutate/push the same task branch as the normal workflow.

The detailed Issue / branch naming / Draft PR / sprint lifecycle is defined by ADR-0004.

### 8. Parallelism follows a dependency graph, not shared-file ownership

Disjoint file ownership is no longer the fundamental condition for parallel execution.

Isolated workers may independently edit overlapping files when their tasks are logically independent. Integration order and interface dependencies remain explicit, and merge conflicts are not used as the default coordination strategy.

### 9. Subagent creation is exposed as a high-level capability

Where possible, the Coordinator and permitted parent agents receive logical operations such as `spawn_agent`, `wait_agent`, `get_agent_result`, `cancel_agent`, and `integrate_agent_result` through native APIs, MCP, ACP, CLI adapters, or an equivalent project-local interface.

Agent models should not need direct control-plane knowledge of Docker/VM/provider commands.

### 10. Runtime/provider remains replaceable

The policy does not require a specific vendor.

Local containers, Dagger-like runtimes, devcontainer-compatible environments, lightweight VMs, SSH/devbox providers, on-demand remote sandboxes, or native cloud-agent machines may be selected based on current project needs.

The same repository-controlled environment specification should be reused across local and remote execution when practical.

Cross-platform local-host details for macOS / Apple Silicon and Windows + WSL2 are defined by ADR-0004.

## Consequences

### Positive

- port/database/runtime collisions are removed from normal multi-agent coordination
- canonical project state no longer depends on one local working directory
- nested subagents receive reproducible parent state
- worker failures or provider loss can be recovered from Git/snapshots
- local and on-demand remote compute can share the same orchestration model
- parallelism can exceed file-level partitioning while preserving deterministic integration
- security boundaries improve because workers do not need host-level sandbox-management privileges

### Negative / Trade-offs

- sandbox creation has runtime and storage cost
- orchestration requires an additional Supervisor/control-plane layer
- snapshot/result integration becomes an explicit protocol
- full isolation may be slower than shared-process development for tiny tasks
- provider adapters and environment bootstrap require maintenance
- nested agent execution requires explicit cost/depth limits

## Migration from ADR-0001

The following ADR-0001 decisions are revised:

- Section 7 `Local main + no worktree`
- Section 8 `Maximum safe parallelism` where shared file ownership and serialized shared-Git operations were assumed

The remaining ADR-0001 decisions continue to apply unless revised by another ADR.

The new policy is:

- canonical remote/ref instead of shared local `main`
- isolated runtime per implementation worker
- worktree allowed only as an internal implementation detail, never as the isolation boundary
- immutable snapshots for delegation
- immutable commits/refs/diffs for results
- Supervisor-controlled branch integration
- top-level PRs as the main external integration boundary

ADR-0004 extends this with GitHub Issues/Projects as durable work state, Issue-numbered branches, early Draft PRs, sprint delivery, and cross-platform local runtime policy.

## Re-evaluation triggers

Re-evaluate this decision when:

- coding-agent platforms provide a broadly portable standard for isolated nested agents
- a standard protocol unifies agent lifecycle, snapshot, and result integration
- sandbox startup/runtime cost becomes the dominant development bottleneck
- the project's runtime no longer requires mutable local services
- Git ceases to be the appropriate canonical integration mechanism
- security requirements require stronger VM/hardware isolation than the current runtime provides
