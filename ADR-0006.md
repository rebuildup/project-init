# ADR-0006: Engineering Decision Hierarchy, Verification Taxonomy, Security Maintenance, and Onboarding

- Status: Accepted
- Date: 2026-09-05
- Extends: ADR-0005
- Superseded by: None

## Context

ADR-0005 made quality gates adaptive to the project's actual framework/runtime and current official guidance. Four remaining operational problems are still cross-project and need explicit policy.

1. Test labels such as unit/integration/E2E are often used inconsistently, so an agent can report “tests passed” without proving the changed boundary actually works.
2. Coding agents frequently ask users to resolve trivial implementation choices even when project-local evidence already determines the answer.
3. Framework/runtime vulnerability information changes over time and must be converted into prioritized project work rather than treated as an unranked alert stream.
4. Project knowledge can become trapped in chat history, implicit memory, or experienced contributors, making fresh onboarding unreliable.

## Decision

### 1. Verification levels are defined by responsibility

Each project compiles its own concrete test tooling, but the following conceptual responsibilities are distinguished:

- unit: local logic/component behavior with external boundaries minimized
- smoke/connectivity: startup, wiring, basic connectivity, and critical-path entry
- integration: multiple real components/boundaries working together
- contract/schema: interface compatibility where meaningful
- E2E/system: user/system critical flows through production-like boundaries
- manual/visual: explicit fallback only when automation is insufficient

A project-specific change-risk mapping determines which levels are required for each ticket and release.

### 2. Decision precedence is project-local and evidence-first

Engineering decisions normally follow this order:

1. project-wide policy / canonical architecture / invariants
2. design / specification / explicit task instruction
3. majority coherent existing implementation
4. current official framework/runtime/SDK guidance
5. established ecosystem convention
6. local best judgment

Existing code is evidence, not an authority capable of overriding a newer canonical design or policy.

### 3. Agents do not escalate self-evident decisions

If project-local evidence yields a practically unique, reversible implementation choice that does not alter acceptance criteria, public contracts, security/privacy posture, meaningful cost, or release scope, the agent decides and continues.

User escalation is reserved for genuine product/architecture choices, conflicts between canonical sources, irreversible/destructive operations, public contract decisions, material risk/cost acceptance, release-scope changes, or explicit design-first approval gates.

### 4. Security maintenance is source-prioritized and risk-prioritized

Security information is collected first from official framework/runtime/SDK advisories and release information, then ecosystem/GitHub advisory sources and trusted secondary evidence.

Prioritization considers not only severity but also exploitability, reachability in this project, external exposure, required privilege, impact scope, fix availability, workaround quality, regression risk, and release timing.

Meaningful advisories become GitHub Issues and are assigned to an appropriate target release. Critical exposed vulnerabilities may interrupt the current sprint and cause a patch release.

### 5. Security automation is project-specific

Dependency scanning, dependency review, code scanning/SAST, secret scanning, container scanning, SBOM generation, and related checks are enabled when they provide useful signal for the actual project.

Blocking policies must not be based on uncontrolled false-positive noise.

### 6. Onboarding documentation is part of initialization

A fresh contributor must be able to understand the project, bootstrap the environment, run the system, execute validation, discover architecture/design/ADR/Skills, select an Issue, follow the release/ticket branch workflow, and diagnose common failures without chat history or private memory.

Documentation is progressively disclosed rather than compressed into one oversized README.

### 7. Documentation is verified and maintained

Documented commands should be executable from a fresh environment where practical. Broken links, stale setup steps, and undocumented recurring troubleshooting knowledge are treated as maintenance defects.

Architecture, runtime, workflow, validation, and security-process changes update onboarding documentation in the same ticket when applicable.

## Consequences

### Positive

- “tests passed” has a clearer operational meaning
- wiring/configuration failures are caught by explicit smoke/connectivity gates
- agents ask fewer unnecessary questions and preserve user attention for real decisions
- implementation conventions remain coherent without allowing legacy code to override canonical policy
- security alerts become prioritized engineering work tied to release planning
- project knowledge becomes recoverable from repository-controlled documentation
- new contributors and new agents can enter the project without hidden context

### Negative / Trade-offs

- test taxonomy and change-risk mapping require initial design effort
- maintaining smoke/integration/E2E layers can increase CI cost
- security triage requires project-specific reachability analysis
- onboarding documents require maintenance when architecture and workflow change
- aggressive autonomy requires careful definition of true escalation boundaries

## Re-evaluation triggers

Re-evaluate when:

- the project changes its test architecture materially
- escaped regressions show the verification-level mapping is insufficient
- user escalation becomes too frequent or too rare
- security advisory sources/workflows materially change
- a different issue/release management system replaces GitHub
- contributor onboarding repeatedly fails despite documented steps
- an agent platform provides a stronger standardized project-governance mechanism
