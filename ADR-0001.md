# ADR-0001: Project-local AI Agent Initialization Policy

- Status: Accepted; sections 7 and 8 revised by ADR-0003
- Date: 2026-08-09
- Supersedes: None
- Superseded by: None
- Revised by: ADR-0003

## Context

AI coding agentの能力拡張は、global scopeへ多数のpluginやmemoryを導入すると、開発者ごとの差、agentごとの差、hidden state、context overheadが増えやすい。

一方、project-localなAgent Skills、plugin declarations、toolchain configuration、ADR、deterministic validationをリポジトリへ保持すれば、fresh cloneから同じ開発ルールを再現しやすい。

また、単一の巨大 `AGENTS.md` にすべてのルールを記述すると常時context costが増え、無関係なタスクへ専門ルールが干渉する。そのため、root instructionsはdispatcherとし、詳細をSkillへprogressive disclosureする構成が必要である。

## Decision

### 1. Project-localを唯一の標準scopeとする

AI agent plugin、Skill、設定は原則project-localで管理する。

global設定やpersistent memoryはproject truthとして利用しない。

### 2. Root agent fileは最小限にする

`AGENTS.md` 等には常時必要な不変条件だけを置く。

testing、UI verification、Git、architecture、dependency hygiene等の詳細はAgent Skillsへ分離する。

### 3. Plugin/toolは固定bundleにしない

`context-mode`、RTK、Superpowers、Context7、claude-mem等をmandatory bundleにはしない。

初期化時点でnative capabilityと現在のecosystemを調査し、projectに必要な能力だけを選定する。

選定・不採用理由は必要に応じてagent toolchain ADRへ記録する。

### 4. Deterministic verificationを標準completion gateにする

実装タスクでは、formatter、lint、type-check、dependency analysis、build、tests、coverage、container/IaC validation等、projectに含まれる適用可能な全検証を自動的に実行する。

skip、ignore、warning suppression等による見かけ上のgreenは認めない。

coverageは意味のあるtestable sourceについて原則80%以上とする。

### 5. 公式推奨architectureを強く優先する

platform/frameworkが明示的なrecommended architectureを提供している場合、具体的な要件と衝突しない限り原則準拠する。

公式が意図的にunopinionatedな領域では、存在しないofficial architectureを捏造しない。

逸脱や重大なarchitecture migrationはADRへ記録する。

### 6. Design-firstを採用する

design/specificationが存在する変更は、designをユーザーと合意してから実装する。

design documentは最終状態だけを表し、decision historyはADRへ分離する。

### 7. Local `main` + no worktreeを採用する — Revised by ADR-0003

当初decisionとして、local `main`だけで作業し、feature branch、temporary branch、Git worktreeを作らない方針を採用した。

並列化はworktreeではなくdisjoint file ownershipを持つsubagentによって行い、commit operationはshared index/HEAD競合を避けるため直列化するものとした。

**このdecisionはADR-0003でrevisionされた。現在のcanonical policyは、Git remote/refをSoTとし、implementation workerごとにisolated mutable runtimeを使用し、worktree単体をisolation boundaryとして扱わないことである。**

### 8. 最大安全並列化を採用する — Revised by ADR-0003

当初decisionとして、大規模タスクはdependency graphへ分解し、論理的に実行可能な最大数のsubagentを使うことを採用した。

logical executabilityにはdependencyだけでなく、file ownership、runtime concurrency、model availability、rate limit、quotaも含めるものとした。

**最大安全並列化という目的自体は維持するが、shared working tree上のfile ownershipを主要isolation mechanismとする部分はADR-0003でrevisionされた。現在はisolated sandbox、immutable snapshot/result、Supervisor integrationを前提とする。**

### 9. Codex model-role policyを時点付きで採用する

2026年8月時点では:

- Sol: coordinator / supervisor
- Terra: independent reviewer
- Luna: primary implementation worker

として利用する。

これはOpenAIによる職務定義ではなく、現在の公開上のmodel positioningとcost/speed特性に基づくproject policyである。

model、pricing、availability、routingが変われば再評価する。

### 10. Source/document/Git languageを分離する

- source code: English
- internal development docs: Japanese
- Git / GitHub communication: English
- locale resource: other languages allowed
- external README/LICENSE等: target audience / standardに合わせて例外可

### 11. Tooling conventions

- JS/TS package manager: Bun
- textual search: ripgrep
- new Python scripts: prohibited
- new container definitions: `Containerfile`
- CI/CD: GitHub Actions by default
- temporary artifacts: `.tmp/`
- external reference clones: `.reference/`

### 12. Environment file policy

actual values:

- `.env`
- `.env.development`
- `.env.production`

のみを許可しGit ignoreする。

committed schema/examples:

- `.env.example`
- `.env.development.example`
- `.env.production.example`

を許可する。

GitHub Secretsで利用するvariable名もexample filesへ反映する。

### 13. Pre-commit hooksは標準化しない

本ポリシーのためだけにpre-commit hookは作らない。

validationはproject scriptsとCI/CDから再現可能にする。

### 14. Foundation migrationはADRを条件に自動実行可能とする

Bun移行、Containerfile移行、test framework、CI/CD、architecture、agent tooling等の大きな変更は、具体的な理由がありADRに残す場合、自動実行可能とする。

designに関係する場合は別途design-first gateを守る。

### 15. `/init` はidempotent reconciliationとする

再実行時は既存の正しい状態を壊さず、missing / incomplete / staleな部分だけを調整する。

変更不要も成功結果とする。

## Consequences

### Positive

- developer/global environment差が小さくなる。
- agentごとの差をproject-local adapterで吸収できる。
- contextへ常時投入するrulesを小さくできる。
- plugin/tool選定の理由がrepositoryに残る。
- test/quality実行の指示を毎回繰り返す必要が減る。
- architecture decisionsが公式guidanceとADRに基づく。
- subagent parallelismを大きく利用できる。

### Negative / Trade-offs

- strict zero-warning / full-suite gateにより小さな変更でも検証costが増える。
- official architecture researchやADR作成に初期costがかかる。
- Python script禁止により、一部ecosystemでは代替toolingが必要になる。
- Codex role allocationはmodel lineupの変化に応じてmaintenanceが必要になる。
- multi-agent execution isolationのtrade-offはADR-0003を参照する。

## Re-evaluation triggers

以下のいずれかが発生した場合、このADRまたは後続ADRで再評価する。

- Agent Skillsの主要標準やproject-local path modelが大きく変化
- Codexのmodel lineup、pricing、routingが変更
- isolated multi-agent execution / agent protocol標準が大きく変化
- Bun / NixOS / WSL Containersを前提とする開発環境が変化
- deterministic validation policyがproject velocityに重大な問題を生む
- project-local plugin reproduction方式が標準化される
